# 配置メタデータの author・カスタム項目追加・反復調整・安全ゲート

帳票をorgのレコードページに載せる「中身」を author し、配備の実行は ti-metadata の機構へ渡す。**本スキルは中身（どの権限/配置/項目/資産が要るか）まで、配備の実行機構（取得→差分→検証→反映）は持たない。**

## 配置に要る中身（authorするもの）と機構の帰属

帳票をレコードページに載せる最小セットの「中身」を author する。配備の実行は ti-metadata へ渡す。

| 成果物 | 中身をauthorするのは | 配備の機構 |
|---|---|---|
| データ供給クラス（生データを返す） | ti-report | ti-metadata（テスト・カバレッジ要件つき） |
| 描画面（データを差し込んだHTML/CSSをブラウザへ配信する画面。PDF化はしない）＋そのコントローラ | ti-report | ti-metadata |
| 添付の処理（Apexやフロー。帳票PDF生成サービスを呼び出し、返されたPDFをレコードへ添付する。サービスの提供開始後のみ） | ti-report | ti-metadata |
| 薄い出力ボタン | ti-report | ti-metadata |
| 角印画像・CSS資産 | ti-report | ti-metadata |
| 帳票に出す項目の項目レベルセキュリティ（権限セット） | ti-report（どのロール/項目に権限を与えるか） | ti-metadata |
| ボタンのレコードページ配置 | ti-report（どのオブジェクトのどの画面か） | ti-metadata（配置は要ユーザー確認・専用の新規アプリ割当で既存運用に影響を与えない） |
| 出力トリガー等の追加項目（必要時） | ti-report | ti-metadata |

**配備の渡し方（一方向参照）**: 帳票が author したメタデータ束を、ti-metadata（配備機構スキル）の中核ループへ渡して実行する。ti-metadata は帳票固有の中身を知らず、本スキルは配備機構を再実装しない（機構の二重管理を避ける）。機構の詳細（差分デプロイ・型ごとの安全弁）は ti-metadata 側にあり、本スキルは委譲の指示に留めて再掲しない。

**配置の方針**: 独自デザインのレコードページは起こさない。本番では既存パッケージのレコードページを複製コピーし、その複製へ軽量帳票ボタンを追加する（既存踏襲の複製に追加＝製品体験の一貫性）。既存の定型帳票ボタンとは棲み分ける。

## 描画とPDF化の方式 [REQUIRED]

**描画はChromiumだけで行う。Visualforceでは描画しない。** VisualforceのPDF化（ページの`renderAs="pdf"`・Apexの`PageReference.getContentAsPdf()`）はSalesforceの旧いPDFエンジンを使い、flexbox・grid・角丸・影・背景などのモダンなCSSを描画できない。同じテンプレートと同じデータで比べると、テンプレートどおりに再現できる範囲が、エンジンの仕組みの上でChromiumより狭い（CSSの工夫では埋められない）。自動添付が必要な場合も、VisualforceのPDF化を代替手段として使わない。

| 用途 | 方式 | 添付 |
|---|---|---|
| 画面から1件ずつ出力する | データを差し込んだHTMLを利用者のブラウザ（Chromium）で開き、ブラウザの印刷でPDFに保存する | 利用者が手動で添付する |
| AIへの指示で出力する・利用者の端末で定時に実行する（当面の自動添付） | 利用者の端末のChrome（画面なしのヘッドレスモードで起動する。以下「端末のChrome」）で、データを差し込んだHTMLをPDF化する（Puppeteerの`page.pdf()`など） | 作成したPDFを、ti-local-automationのファイル添付のレシピでレコードへ添付する |
| Salesforce上で起動する自動添付・自動出力（画面のボタン・承認・項目の更新・スケジュールされたフローなど） | ツバイソが提供する帳票PDF生成サービス（サーバ側のChromium）でHTMLをPDF化する | 帳票PDF生成サービスが返したPDFを、添付の処理（Apexやフロー）がレコードへ添付する |

- **Salesforceの中ではChromiumを実行できないので、Salesforce上で起動する自動添付・自動出力は、帳票PDF生成サービスの提供開始後に対応する機能とする。**
- **帳票PDF生成サービスの提供開始前に自動化を求められた場合は、端末のChromeでPDF化して添付する方式を示す。** AIへの指示（「承認済みの注文書をPDFにして添付して」）か、利用者の端末での定時実行（例: 承認済みの注文書を15分ごとにPDF化して添付する）で、PDF化から添付までを自動で実行できる。利用者の端末が起動し、Chromeが動作することが前提で、端末が停止・スリープすると処理も止まることを伝える。承認と同時に必ず出力・送付されることが業務の前提なら、帳票PDF生成サービスの提供を待つ。VisualforceのPDF化を代替手段として実装しない。
- **端末のChromeも、ブラウザの印刷と同じ系統の描画エンジン（Chromium）を使う。** 画面なしで起動した端末のChromeが作成したPDFのデータはスクリプトで受け取れるので、「テンプレートどおりの描画」と「自動添付」を同時に実現できる（出典: Puppeteerの`page.pdf()`は印刷用のCSSでPDFを作成し、データを返す。https://pptr.dev/api/puppeteer.page.pdf ）。顧客のデータは端末の外へ出ない。添付は組織への書き込みなので、下の §安全ゲート の確認を経てから添付する。
- ブラウザの印刷が作成するPDFのデータは、JavaScriptから受け取れない。このため、ブラウザの画面からの操作だけでは「テンプレートどおりの描画」と「自動添付」を同時に実現できない（Webの仕様による制約。本スキルでは実機で検証していない）。
- **変更する箇所は、データを差し込んだHTMLをPDF化する処理の1か所に限る。** テンプレート・データの取得と差し込み・添付は、ブラウザの印刷・端末のChrome・帳票PDF生成サービスのいずれの方式でPDF化しても変更しない。このため、押印とDRAFTの表示の切り替えもテンプレートで定義する（`template-and-mapping.md` §押印/DRAFT判定）。
- **描画面はサーバから配信し、ブラウザで開く。** 画面部品（LWC）からHTMLの文字列をiframeへ直接差し込む方式（`srcdoc`・Blob・data URL）は、Lightningのセキュリティ制約で遮断される。Visualforceページを描画面に使う場合はHTML/CSSの配信にだけ使い、`renderAs="pdf"`も`getContentAsPdf()`も呼ばない。条件付き表示（`rendered`）で押印/DRAFTの表示を切り替えることもしない。
- 本節に挙げた制約（VisualforceのPDFエンジン・iframeへの直接の差し込みの遮断）は、Salesforceのリリースで緩和されることがある。断定する前に能力の出典を確認し、実証状態を注記する（`salesforce-platform-capabilities`・`code-investigation`）。
- **添付はランタイム（メタデータ配備でない）**: 生成PDFのレコードへの添付は実行時のレコード書込で、設計時のメタデータ配備ではない。帳票が唯一行うレコード書込がこの添付で、描画済みPDFのため書込前の構造チェックの対象外。添付先は帳票の見出（master）レコード。

## カスタム項目追加の副フロー

帳票に出す項目を増やすとき。

1. 対象オブジェクトへカスタム項目を追加する（配備は ti-metadata）。
2. 権限セットで当該項目の項目レベルセキュリティ（参照/編集）を付与し割り当てる。
3. 描画コントローラの取得項目とテンプレの差込点に1行追加し、再描画で帳票へ反映する。

手前のマッピング・テンプレ・プレビューはローカルで自由に回し、org書込（項目追加・デプロイ）だけ安全ゲートを通す。

## 反復調整

一発生成器ではなく「調整→プレビュー→反復→確定」。(1) ローカルの高速プレビューで差込点を調整、(2) 実データで流し込み目視確認、(3) 確定版だけをorgへ載せてデプロイの往復を減らす。

## 安全ゲート [REQUIRED]

- org書込（メタデータ配備・カスタム項目追加・本番反映・生成PDFの添付）の直前は、ti-core の安全ゲート（ドラフト提示＋承認＋PIIマスキング）を通す。承認は利用者の明示承認で得る。
- 検証（非コミット）を先行させ、本番反映は承認後。型ごとの配備制約（本番のテストカバレッジ・改変不可境界・全置換型の変更のドリフト監視 等）は ti-metadata の安全弁が担う。**共通の承認・PIIマスキングは ti-core、型ごとの配備制約は ti-metadata** と役割で分ける（二重ホームにしない）。
- 検証/トライアル org は失効に注意する（失効後の再実証は org 更新が要る）。
