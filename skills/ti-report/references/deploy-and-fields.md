# 配置メタデータの author・カスタム項目追加・反復調整・安全ゲート

帳票をorgのレコードページに載せる「中身」を author し、配備の実行は ti-metadata の機構へ渡す。**本スキルは中身（どの権限/配置/項目/資産が要るか）まで、配備の実行機構（取得→差分→検証→反映）は持たない。**

## 配置に要る中身（authorするもの）と機構の帰属

帳票をレコードページに載せる最小セットの「中身」を author する。配備の実行は ti-metadata へ渡す。

| 成果物 | 中身をauthorするのは | 配備の機構 |
|---|---|---|
| データ供給クラス（生データを返す） | ti-report | ti-metadata（テスト・カバレッジ要件つき） |
| 描画面＋そのコントローラ | ti-report | ti-metadata |
| 添付クラス（描画面をPDF化しレコードへ添付） | ti-report | ti-metadata |
| 薄い出力ボタン | ti-report | ti-metadata |
| 角印画像・CSS資産 | ti-report | ti-metadata |
| 帳票に出す項目の項目レベルセキュリティ（権限セット） | ti-report（どのロール/項目に権限を与えるか） | ti-metadata |
| ボタンのレコードページ配置 | ti-report（どのオブジェクトのどの画面か） | ti-metadata（配置は要ユーザー確認・専用の新規アプリ割当で既存運用に影響を与えない） |
| 出力トリガー等の追加項目（必要時） | ti-report | ti-metadata |

**配備の渡し方（一方向参照）**: 帳票が author したメタデータ束を、ti-metadata（配備機構スキル）の中核ループへ渡して実行する。ti-metadata は帳票固有の中身を知らず、本スキルは配備機構を再実装しない（機構の二重管理を避ける）。機構の詳細（差分デプロイ・型ごとの安全弁）は ti-metadata 側にあり、本スキルは委譲の指示に留めて再掲しない。

**配置の方針**: 独自デザインのレコードページは起こさない。本番では既存パッケージのレコードページを複製コピーし、その複製へ軽量帳票ボタンを追加する（既存踏襲の複製に追加＝製品体験の一貫性）。既存の定型帳票ボタンとは棲み分ける。

## 描画経路のプラットフォーム制約

描画とPDF化はプラットフォームの制約を受ける。これらは実機で実証済みだが、プラットフォーム更新で緩和されうるドリフト対象でもある。断定する前に能力の出典を確認し、実証状態を注記する（`salesforce-platform-capabilities`・`code-investigation`）。

- **描画面はサーバ配信＋埋め込み読み込みへ寄せる**: クライアント側で HTML 文字列を直接埋め込む方式はプラットフォームのセキュリティ制約で遮断されるため、描画面をサーバから配信し埋め込みで読む方式に寄せる。
- **PDF化は用途で2経路**: 高精細版はブラウザ印刷、自動添付版はサーバ側でPDF化する。サーバ側PDFは旧レンダラのため CSS 制約が強い（`report-aesthetics.md` のサーバPDF節）。
- **添付はランタイム（メタデータ配備でない）**: 生成PDFのレコードへの添付は実行時のレコード書込で、設計時のメタデータ配備ではない。帳票が唯一行うレコード書込がこの添付で、描画済みPDFのため書込前の構造チェックの対象外。添付先は帳票の見出（master）レコード。

## カスタム項目追加の副フロー

帳票に出す項目を増やすとき。

1. 対象オブジェクトへカスタム項目を追加する（配備は ti-metadata）。
2. 権限セットで当該項目の項目レベルセキュリティ（参照/編集）を付与し割り当てる。
3. 描画コントローラの取得項目とテンプレの差込点に1行追加し、再描画で帳票へ反映する。

手前のマッピング・テンプレ・プレビューはローカルで自由に回し、org書込（項目追加・デプロイ）だけ安全ゲートを通す。

## 反復調整

一発生成器ではなく「調整→プレビュー→反復→確定」。(1) ローカルの高速プレビューで差込点を調整、(2) 実データで流し込み目視確認、(3) 確定版だけをorgへ載せてデプロイの往復を減らす。

## 安全ゲート [REQUIRED]

- org書込（メタデータ配備・カスタム項目追加・本番反映・生成PDFの添付）の直前は、ti-core の安全ゲート（ドラフト提示＋承認＋PIIマスキング）を通す。承認は利用者の明示承認で得る。
- 検証（非コミット）を先行させ、本番反映は承認後。型ごとの配備制約（本番のテストカバレッジ・改変不可境界・全置換型の変更のドリフト監視 等）は ti-metadata の安全弁が担う。**共通の承認・PIIマスキングは ti-core、型ごとの配備制約は ti-metadata** と役割で分ける（二重ホームにしない）。
- 検証/トライアル org は失効に注意する（失効後の再実証は org 更新が要る）。
