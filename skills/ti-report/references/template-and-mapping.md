# テンプレの差込DSL・流し込み・意味定義マッピング・押印/DRAFT判定

帳票の「中身」を作る中核。テンプレの差込点にデータを流し込み、源データを差込キーへ対応づけ、承認状態で押印/DRAFTを切り替える。配備の機構は持たず、`deploy-and-fields.md` で ti-metadata へ渡す。

> 帳票テンプレを新規作成・改修して Write する直前は、`report-aesthetics.md` §美観セルフチェック（帳票テンプレのWrite直前）を必ず通す（新規作成経路がセルフチェックを素通りしないための導線）。

## テンプレの差込DSL＋流し込みエンジン

帳票テンプレは HTML/CSS に「差込点」を属性で宣言し、エンジンは標準の DOM API だけで値を流し込む。

| 記法の役割 | 意味 |
|---|---|
| スカラ値の差込先 | 要素のテキストに値を設定する。画像の差込先は画像の参照先を差し替え、対応するプレースホルダを非表示にする |
| 配列の繰り返しコンテナ | 明細など、内部の行テンプレートを行ごとに複製し、各行へスカラを流し込む |
| DRAFT表示の制御クラス | ドラフト判定で透かしの表示・非表示を切り替える |

**体裁と押印/DRAFTの切り替えはテンプレートで定義する [重要]**: ローカルのプレビューでも、orgの描画面からブラウザで開く場合でも、描画はChromiumで行う。テンプレートはHTML/CSSのまま使う。orgの描画面（Visualforceページ等）がコントローラで値を取得・整形して配信する場合も、体裁・押印/DRAFTの切り替えはテンプレートで定義し、描画面の条件付き表示へ移さない。PDF化の方式（ブラウザの印刷・端末のChrome・帳票PDF生成サービス）を切り替える際の変更箇所を、1か所に限るためである（`deploy-and-fields.md` §描画とPDF化の方式）。プレビューで体裁を調整し、確定したテンプレートをorgへ反映する。

**落とし穴**: 合計など「明細の外側のスカラ」を繰り返しコンテナの内側に置くと、行内スカラ扱いで流し込みから外れる。合計行は繰り返しコンテナの外へ分離する。

## 意味定義マッピング

SOQL で取得した生データの項目を差込キーへ対応づける。

- **標準帳票・標準項目のマッピングは標準スキル層が保持する**（意味定義）。整形（桁区切り・和暦/西暦・通貨記号の前置/後置・住所結合・税率別集計）は流し込み側で行い、テンプレは差込点だけを持つ。
- **顧客独自項目・帳票固有列**は、源が標準に無い場合があるため、会社固有層で describe 実証してから対応づける。源が無い列は空欄になる＝テンプレの形とデータの形の整合確認が取込の要点。
- この「源の有無・整形」の写像が、そのまま `report-design-cycle.md` の項目マッピング設計書の素になる。

## 押印/DRAFT判定（本スキルローカル）

承認状態を判定する項目で、押印（角印）と DRAFT 透かしを切り替える。

- 承認済み → 角印を表示・透かし無し。未承認 → 角印プレースホルダ＋DRAFT 透かし。
- 既定は承認状態からの自動判定。UI/URL で明示上書きを許す。
- 判定キーは帳票種別ごとに確定する（種別によって承認状態を表す項目が異なる）。

**判定と共通ボタン規約の帰属**: 押印/DRAFT判定と、薄い出力ボタンのシェル規約は、実体も呼び出しIFも本スキルローカルに置く。2つ目の利用者が同じ判定/規約を要した時点で ti-core へ昇格する。

## 差し込んだデータのハッシュ値（二重添付の判定に使う） [REQUIRED]

`deploy-and-fields.md` §描画とPDF化の方式 で同じ帳票かどうかを判定するハッシュ値は、次の規約で算出する。実行のたびに、またはスクリプトを作成し直すたびに規約が異なると、内容が同じ帳票でもハッシュ値が一致せず、同じPDFが二重に添付される。このため、ハッシュ値を算出するスクリプトを作成し直すときも規約を変えない。

- **対象**: 差込点へ差し込んだ値（整形した後の、帳票に表示される文字列）。画像の差込先は、差し替えた参照先の文字列。テンプレートの中の固定の文字と生成日時は含めない
- **差込キー**: スカラはその差込キー。繰り返しコンテナの内側の値は `{コンテナのキー}[{行番号}].{差込キー}`（行番号は帳票に表示される順で、1から数える）
- **値の正規化**: Unicodeの正規化形式NFCにそろえ、改行コードをLFに統一し、前後の空白を除く
- **空値**: 値が無い差込点も、差込キーを省かず、空文字列として含める（値が無いことと空文字列を区別しない）
- **並び順とJSONへの変換**: 差込キーと値の組 `[差込キー, 値]` を、差込キーの昇順に並べて配列にする。並べる順は、差込キーの文字列どうしをJavaScriptの`<`で比べた順とする。この配列をJSONの文字列に変換する。区切りの空白は入れず、ASCII以外の文字はエスケープしない（JavaScriptの`JSON.stringify`の既定の出力）
- **ハッシュ値**: JSONの文字列をUTF-8のバイト列にしてSHA-256でハッシュ値を算出し、16進数の小文字の文字列で表す

## 定型帳票との棲み分け [重要]

承認済み押印が必須の確定帳票には、**既存の定型帳票経路**（レイアウトが固定で承認済み押印を付与する経路）が別に存在する。本スキルの軽量帳票が扱う角印は「承認済みであることの視覚表現」であって会社実印の代替ではなく、定型帳票を置き換えない。押印が必須の確定帳票は既存の定型経路を使い、軽量帳票は定型では足りない自由項目・体裁の調整、ドラフト・非定型帳票を担う。

> 帳票機構の一次事実（描画・添付の API・パラメータ）はコードが正本。参照するときは ref（対象ブランチ）を明示して確認し、利用 org の describe/SOQL のラベル・選択肢を「標準」と断定しない（`code-investigation` の作法）。
