# migration-principles — 移行の原則と関係解決

投入・移行の骨格。4本柱・tb_ExId による関係解決・サンドボックス間の多段移行・標準フロー（導入/デモ共通）・期首残高主義。型（何を作るか）は本ファイルに焼き込まず、着手前に ti-reference の recipe を索引で引く（`boundaries-and-gates.md`）。

## 大原則（4本柱）

データ移行が難しいのは「新システムでのマスタと各トランザクションの関係性を、整合性を保ってインポートすること」が難しく、かつ「旧システムが新システムに必要なデータを持っていない」ことが多いため。次の4原則でこれを回避する。

1. **マスタが先、トランザクションが後**。トランザクションはマスタ（取引先・部門・品目・税区分・原因・セグメント 等）を参照して成り立つ。投入先にマスタが存在しなければ参照は解決できない。マスタは移行前にクレンジング（名寄せ・誤り修正）して品質を上げてから入れる。

2. **自動作成される会計計上レコードは投入せず、自動作成させる**。**売上・請求・入金予定・支払予定・支払・仕入経費** といった会計計上レコードは直接 load せず、最小限のソース文書（受注、必要に応じて発注）だけ入れ、それ以降（納品・期間収益・従量収益・請求・売上・発注・検収・期間費用・従量費用・支払・仕入経費）はパッケージの自動作成機能に任せる。直接 load は主従制約・削除済み参照で破綻する（削除済みエンティティ参照エラー）。これが整合の取れたトランザクションを作る現実的な唯一の道。**総称語「帳票」「会計ヘッダー」で呼ばず個別名で書く。「請求予定」は使わない**（「請求」と「入金予定」を混同した誤りの造語。会計計上レコードとしては「請求」と「入金予定」を別に扱う）。

3. **組織をまたぐと内部 Id は変わる。外部ID（tb_ExId）で関係を解決する**。Salesforce は登録時に内部 Id を自動採番するため、元組織の Id をそのまま使い回せない。レコードの一意キーを外部IDフィールド **`tb_PSA__tb_ExId__c`（テキスト・ユニーク・大文字小文字区別）** に持たせ、親子・参照を tb_ExId で結ぶ。内部 Id の再採番に左右されずに関係が復元できる。

4. **投入時は自動処理を明示制御する**。インポートモード・自動計上 gate・承認/ロック・フロー適用の ON/OFF を、投入のどの段階でどう効かせるかを意図して切り替える（`load-controls-and-prereqs.md`）。

## 核心：tb_ExId による関係解決

ほぼ全 PSA オブジェクトが外部IDフィールド `tb_PSA__tb_ExId__c`（ユニーク）を持つ。インポート時のレコード照合キーは Salesforce Id / 名前 / 外部ID の3種から選べるが、名前はユニークでないと誤った相手に紐づくため、**外部ID（tb_ExId）を関係解決キーにするのが安全**。

### 手順（親→子→孫）

1. 親（例 案件）をインポートする。親の tb_ExId に「元システムでの親キー」（案件キー等。サンドボックス移行なら元組織の内部 Id）を入れる。インポート後、移行先で内部 Id が自動採番される。
2. 子（例 受注）をインポートする。子の tb_ExId にも「子自身の一意キー」を入れる（後続の孫＝受注明細と結ぶキーになる）。
3. 子のCSVの「親項目」には**親の tb_ExId 値**を入れておく。
4. インポートウィザードの主従関係の指定で **tb_ExId** を選ぶ。
5. これで内部 Id によらず、tb_ExId をキーに親子が自動リンクされる。孫（明細）も同様に、明細CSVの「親（受注）」項目に受注の tb_ExId と同じ値を入れて紐づける。

### サンドボックス間移行（開発1→2→3）

開発で複数サンドボックスを作り、1で試作→2で詰める→クレンジングして3へ、という流れは移行・導入の必須パターン。要領は本番移行と同じ。

1. 移行元サンドボックスから対象データをエクスポートする。各レコードには内部 Id（例示・実値は載せない）が採番済み。
2. その内部 Id を、各レコードの tb_ExId に**割り当てて**移行先へインポートする（親も子もそれぞれ自分の Id を自分の tb_ExId へ）。
3. 子のインポート時に、親参照の関係解決に **tb_ExId** を選ぶ。
4. 段階移行のたびに「前段の内部 Id を tb_ExId に保持」しておけば、何段サンドボックスを重ねても関係が辿れる（内部 Id ではなく外部キーで連鎖するため、組織が変わっても壊れない）。

> 自動移行ツール（外部の自動移行ツール）や一括ローダを使う場合も考え方は同じ。**外部キー（tb_ExId）を一意・不変のリンクキーにし、内部 Id には依存しない**。元組織でしか有効でない内部 Id をそのまま参照に使う「恒等マッピング」は、新規組織では参照先が存在せず必ず失敗する。

## 標準フロー（導入・デモ共通）

1. **マスタ投入**（クレンジング後）。取引先は「取引先関連情報を作成=TRUE」で取引先関連情報（1:1）を自動作成。取引先責任者（1:N）は別途。品目・部門・税区分・原因・セグメント等も先に。各マスタに tb_ExId を付与。
2. **トランザクションは最小限だけ load**＝受注（必要に応じて発注）。原則**期首残高主義**（過去の取引明細は移さず、期首時点の残高＝売掛金残高等のみ）。完了済みの過去データや後続処理で生成されるデータは移さない。
3. **自動作成を発火**させ、受注以降（納品・請求・入金予定・売上・発注・検収・支払・仕入経費 等）をパッケージに生成させる。
4. **検証**＝件数・主要項目・業務シナリオで突合。必要なら期首残高（売掛・買掛）を後付け（`import-errors.md`）。
5. **リハーサル徹底・切り戻し計画**。本番前に複数回テスト移行し、手順・作業時間・問題点を洗い出す。万一に備え旧システムへの切り戻し計画を持つ。

## 自動作成シーム経由で下流を生成する（標準フロー手順3の実体）

**上流レコードの自動作成チェックボックスを ON にして保存し、パッケージに正規の下流レコードを生成させる。** 下流を項目ごとに直接 INSERT すると、画面・承認フローが埋める整合（金額・税・原価・関連付け・計上日・収益認識）を欠いた不整合データになる。

**原則**: 自動作成シームがあるオブジェクトは、必ずそのシーム経由で生成する。**直接作成はシームが存在しないオブジェクト（マスタ・案件 等）に限る**。対象ごとのシームの有無とフラグの API 名は書込前ゲート（`ti-reference references/write-index.md`）で引く。**本ファイルにフラグ名を焼き込まない**（シームは版で変わるため、実名は実行時に引く）。

**手順**:

1. 起点レコードを作る。自動作成シームでは生成できない起点は、書込前ゲートが `function_only` として返す。
2. 自動作成フラグを ON にして保存する。
3. 生成された下流を**読み戻す**。
4. 未充当の整合項目のみ**差分 UPDATE** する。
5. 突合する（源件数 ≦ 生成件数。詳細は `import-errors.md` の生成完全性ゲート）。

**非同期生成はドレイン待ち**（数十秒〜）。待てば反映されるので、未反映に見えても再投入しない。管理会計データを作るなら投入前に copy_toma を true にしておく（`load-controls-and-prereqs.md`）。

**射程は投入・移行・サンプル作成に限る。** 稼働後の実業務データは、正規の承認・画面フローを通して作る（本節は移行時にソース文書から後続を起こすための機構であって、日常業務の代替手順ではない）。

## この reference が持たないもの

- **型（何を作るか）**＝契約モデルごとの商品サービス・明細・収益/費用認識は ti-reference の recipe が正本。着手前に索引ファセット（`contract_model:*`／`cost_model:*`）で引く（`boundaries-and-gates.md`）。本ファイルは順序・関係解決・標準フロー・生成の機構だけを持つ。
- **シームの実名と可否**＝どのオブジェクトにどの自動作成フラグがあるか、作れない工程はどれかは書込前ゲート（`ti-reference references/write-index.md`）が正本。
