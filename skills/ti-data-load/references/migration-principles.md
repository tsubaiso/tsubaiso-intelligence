# migration-principles — 移行の原則と関係解決

投入・移行の骨格。4本柱・tb_ExId による関係解決・サンドボックス間の多段移行・標準フロー（導入/デモ共通）・期首残高主義。型（何を作るか）は本ファイルに焼き込まず、着手前に ti-reference の recipe を索引で引く（`boundaries-and-gates.md`）。

## 大原則（4本柱）

データ移行が難しいのは「新システムでのマスタと各トランザクションの関係性を、整合性を保ってインポートすること」が難しく、かつ「旧システムが新システムに必要なデータを持っていない」ことが多いため。次の4原則でこれを回避する。

1. **マスタが先、トランザクションが後**。トランザクションはマスタ（取引先・部門・品目・税区分・原因・セグメント 等）を参照して成り立つ。投入先にマスタが存在しなければ参照は解決できない。マスタは移行前にクレンジング（名寄せ・誤り修正）して品質を上げてから入れる。

2. **自動作成される会計計上レコードは投入せず、自動作成させる**。**売上・請求・入金予定・支払予定・支払・仕入経費** といった会計計上レコードは直接 load せず、最小限のソース文書（受注、必要に応じて発注）だけ入れ、それ以降（納品・期間収益・従量収益・請求・売上・発注・検収・期間費用・従量費用・支払・仕入経費）はパッケージの自動作成機能に任せる。直接 load は主従制約・削除済み参照で破綻する（削除済みエンティティ参照エラー）。これが整合の取れたトランザクションを作る現実的な唯一の道。**総称語「帳票」「会計ヘッダー」で呼ばず個別名で書く。「請求予定」は使わない**（「請求」と「入金予定」を混同した誤りの造語。会計計上レコードとしては「請求」と「入金予定」を別に扱う）。

3. **組織をまたぐと内部 Id は変わる。外部ID（tb_ExId）で関係を解決する**。Salesforce は登録時に内部 Id を自動採番するため、元組織の Id をそのまま使い回せない。レコードの一意キーを外部IDフィールド **`tb_PSA__tb_ExId__c`（テキスト・ユニーク・大文字小文字区別）** に持たせ、親子・参照を tb_ExId で結ぶ。内部 Id の再採番に左右されずに関係が復元できる。**ただし外部IDを持つのは自分たちが入れたレコードだけで、製品同梱の標準マスタは空**（下記 §関係解決は二段構えにする）。

4. **投入時は自動処理を明示制御する**。インポートモード・自動計上 gate・承認/ロック・フロー適用の ON/OFF を、投入のどの段階でどう効かせるかを意図して切り替える（`load-controls-and-prereqs.md`）。

## 核心：tb_ExId による関係解決

ほぼ全 PSA オブジェクトが外部IDフィールド `tb_PSA__tb_ExId__c`（ユニーク）を持つ。インポート時のレコード照合キーは Salesforce Id / 名前 / 外部ID の3種から選べるが、名前はユニークでないと誤った相手に紐づくため、**外部ID（tb_ExId）を関係解決キーにするのが安全**。

### 手順（親→子→孫）

1. 親（例 案件）をインポートする。親の tb_ExId に「元システムでの親キー」（案件キー等。サンドボックス移行なら元組織の内部 Id）を入れる。インポート後、移行先で内部 Id が自動採番される。
2. 子（例 受注）をインポートする。子の tb_ExId にも「子自身の一意キー」を入れる（後続の孫＝受注明細と結ぶキーになる）。
3. 子のCSVの「親項目」には**親の tb_ExId 値**を入れておく。
4. インポートウィザードの主従関係の指定で **tb_ExId** を選ぶ。
5. これで内部 Id によらず、tb_ExId をキーに親子が自動リンクされる。孫（明細）も同様に、明細CSVの「親（受注）」項目に受注の tb_ExId と同じ値を入れて紐づける。

### 関係解決は二段構えにする [REQUIRED]

**外部IDを持つのは自分たちが入れたレコードだけ。製品同梱の標準マスタ（税区分・単位・セグメント・原因の一部 等）は移行元・移行先の両方に同じものが入っていても外部IDが空**で、柱3のやり方だけでは突き合わせられない。外部ID一本で組むと、そこで参照が落ちる。

| 段 | 引き当て方 | 対象 |
|---|---|---|
| 1 | 外部IDで解決する | 自分たちが入れたレコード |
| 2 | 名前またはコードで宛先を引き当てる | 製品同梱の標準マスタ（外部IDが空） |

**段2で名前が一意でなければ、そこで止めて人へ返す**（近い方を勝手に採らない）。**判定はオブジェクト単位でなくレコード単位**で、参照先を実際に読み出して外部IDの有無で振り分ける。同じオブジェクトに製品同梱のレコードと自分たちが足したレコードが混在するので、オブジェクト名で決め打ちすると、後者ごと段2へ落として名前で引き当ててしまう。

### 送るレコードに自分自身の外部IDを含めない

外部IDを照合キーにした upsert では、**キーは経路側で指定済み**なので、送るレコードの中身に同じ外部ID項目を入れると弾かれる（「その項目は指定できない」というエラーになる）。子の参照を親の外部IDで書く形と並ぶため、「外部IDを付与して入れる」という説明から自然に書くとこの形になる。**含めるのは親参照の外部ID、含めないのは自分自身の外部ID**。

### 移行対象の閉包は参照グラフから機械的に取る [REQUIRED]

移行するマスタを業務的な思いつきで列挙すると漏れやすい。**同じオブジェクトの中に、移行するレコードと移行しないレコードが混在する**のが理由で、オブジェクト単位で「これは標準マスタだから対象外」と切ると、そのオブジェクトに自分たちが足したレコードごと落ちる。列挙から漏れるのはたいてい、業務の話題に出ない裏方のマスタ（単位・勘定科目・セグメント・帳票の送信元・原価計算の手続 等）で、参照する側を投入して初めてエラーで露見する。

判定は**レコード単位**で、上の二段構えと同じ軸（外部IDを持つか）で行う。

0. **先に外部IDの採番規約を決め、移行元のレコードへ付与しておく。** 判定にこの値を使うので、付与前に閉包を取ると全件が「外部IDが空」に倒れて閉包が空になる。規約は案件・組織ごとに接頭辞を決めて外部IDの先頭に置く形が扱いやすい。
1. 取り出した各レコードの参照先を辿る。
2. 参照先が**外部IDを持ち、その値が採番規約に合致する**なら、そのレコードも移行対象に入れる（＝段1で解決する側）。合致しなければ移行対象に入れず、投入先に既にある同じものを**名前・コードで引き当てる**（＝段2で解決する側）。
3. 1〜2 を収束するまで繰り返す。
4. **投入の前に検算する**＝取り出した全レコードの参照先をもう一度舐め、段1でも段2でも宛先が決まらない参照が 1 件も無いことを確かめる。決まらないものが残っていたら、投入を始めずにそこで止める（実行してエラーで気づく形にしない）。

### サンドボックス間移行（開発1→2→3）

開発で複数サンドボックスを作り、1で試作→2で詰める→クレンジングして3へ、という流れは移行・導入の必須パターン。要領は本番移行と同じ。

1. 移行元サンドボックスから対象データをエクスポートする。各レコードには内部 Id（例示・実値は載せない）が採番済み。
2. その内部 Id を、各レコードの tb_ExId に**割り当てて**移行先へインポートする（親も子もそれぞれ自分の Id を自分の tb_ExId へ）。
3. 子のインポート時に、親参照の関係解決に **tb_ExId** を選ぶ。
4. 段階移行のたびに「前段の内部 Id を tb_ExId に保持」しておけば、何段サンドボックスを重ねても関係が辿れる（内部 Id ではなく外部キーで連鎖するため、組織が変わっても壊れない）。

> 自動移行ツール（外部の自動移行ツール）や一括ローダを使う場合も考え方は同じ。**外部キー（tb_ExId）を一意・不変のリンクキーにし、内部 Id には依存しない**。元組織でしか有効でない内部 Id をそのまま参照に使う「恒等マッピング」は、新規組織では参照先が存在せず必ず失敗する。

## 標準フロー（導入・デモ共通）

0. **順番を引く** [REQUIRED]。投入順を組む前に、**レコードができる正準シーケンスを ti-reference の手順で引く**（`ti-reference SKILL.md §業務プロセスの図・順番を描くとき`）。下の 1〜5 は骨格で、どのオブジェクトがどの順に立つかまでは持っていない。**記憶や移行元データの日付順で順番を決めない。**
1. **マスタ投入**（クレンジング後）。取引先は**3段**で入れる（下記）。取引先責任者（1:N）は別途。品目・部門・税区分・原因・セグメント等も先に。各マスタに tb_ExId を付与。
   - **移行元の値をそのまま写す前に、既定値の取り残しを人に確かめる。** 対象は**所有・責任を表す参照**（担当者・部門 等）に限る。移行元の組織でレコードを作ったときに既定で入った値が、業務の実態と合わないまま残っていることがある。**これは機械では判定できない**（値としては正しい参照で、誰が正しい担当かは業務側にしか無い）ので、投入前に一覧にして確かめる。既定値は誤ったまま下流へ流れ、後工程の集計で初めて表に出る。マスタへの参照（税区分・単位 等）はここでは見ない（下の二段構えで宛先が決まる）。
2. **トランザクションは最小限だけ load**＝受注（必要に応じて発注）。原則**期首残高主義**（過去の取引明細は移さず、期首時点の残高＝売掛金残高等のみ）。完了済みの過去データや後続処理で生成されるデータは移さない。
3. **自動作成を発火**させ、受注以降（納品・請求・入金予定・売上・発注・検収・支払・仕入経費 等）をパッケージに生成させる。
4. **検証**＝件数・主要項目・業務シナリオで突合。必要なら期首残高（売掛・買掛）を後付け（`import-errors.md`）。
5. **リハーサル徹底・切り戻し計画**。本番前に複数回テスト移行し、手順・作業時間・問題点を洗い出す。万一に備え旧システムへの切り戻し計画を持つ。**同じ手順を2回流せることを手順の側で担保する**（下記 §同じ手順を2回流せるようにする）。

### 取引先は3段で入れる [REQUIRED]

| 段 | やること |
|---|---|
| 1 | 取引先を投入する。**このとき転記専用項目（取引先区分・企業グループ）はコピー対象から外す** |
| 2 | 取引先関連情報を自動作成するシームを発火させ、1:1 の子を作らせる。**作成と同時ではなく、作成後の更新で発火させる**（フラグの実名とシームの向きは書込前ゲートで引く） |
| 3 | **自動作成された取引先関連情報の側を埋める**。取引先側へは製品が転記する |

**段3で埋めるのは区分だけではない。** 書込前ゲートが返す差分更新の対象を**全件**埋める。自動起動フローが埋めない項目には、支払先として成立する条件になるものや、税区分の選択に効くものが含まれる。区分だけ埋めて次工程へ進むと、段2で止めたのと同じ形の欠落が残る。**項目名を本ファイルに列挙せず、書込前ゲートが返した一覧を使う**（版で変わるため）。

段1で外した項目のうち、**差分更新の一覧に載らないもの（与信・反社の取得元になる区分 等）はゲートの制約側に出る**ので、差分更新の一覧だけを見ると落ちる。ゲートの応答は差分更新と制約の両方を読む。

2段目までで止めると、**取引先は入っているのに全社が区分なしで、受注も発注も相手として選べない**状態で終わる。区分が空のまま次工程へ進まない。

> 段2を「作成後の更新」にするのは、**実測した組織で、作成と同時にフラグを立てても子が作られなかった**ため。書込前ゲートは「保存すると生成する」としか言っておらず作成と更新を書き分けていないうえ、フローが不発の組織向けの退避路も併記している。**発火条件は組織によって違いうる**ので、更新で立てる形（何度流しても同じ結果になる）を既定にし、生成の有無は手順3の読み戻しで必ず確かめる。

### 転記専用項目は describe で判別できない [REQUIRED]

段1で外す項目は、**いずれも describe が作成可能として返す**。直接設定を止めているのは検証ルールであって項目属性ではないため、「書ける項目を describe から機械的に集める」やり方では踏む。**項目属性を安全性の根拠にしない**＝除外する項目は書込前ゲート（`ti-reference references/write-index.md`）と実機のエラーから起こす。同じ理由で、**製品が積み上げる合計・累計項目も作成可能として返るが写さない**（移行元の累計値がそのまま入り、投入後の実績と二重になる）。

### 同じ手順を2回流せるようにする

取引先関連情報が作られたあとに同じ移行を再実行すると、取引先が一意制約に当たって失敗する。製品が一意キー項目へ取引先関連情報の内部 Id を書き込むため、外部IDでの upsert であっても衝突する。手順5（リハーサル徹底）と正面から食い違うので、**その一意キー項目を移行のコピー対象から外す**。

**どの項目かは書込前ゲートには出ない。** ゲートが返すのは転記される項目と差分更新の対象で、製品が内部 Id を書き込む一意キー項目はどちらにも載らない。**実機の一意制約エラーが指す項目名から同定する**（1回踏めば確定するので、リハーサルの1周目で拾って除外表へ入れる）。ゲートで引ける除外項目（転記専用）とは出所が違う点に注意する。

**「再実行時は取引先だけ流さない」で回避しない。** 新しく足した取引先が段2・段3を通らず、区分の無いまま残る。3段を毎回そのまま流し、段3（埋め直し）は何度実行しても同じ結果になるようにしておく。

## 自動作成シーム経由で下流を生成する（標準フロー手順3の実体）

**上流レコードの自動作成チェックボックスを ON にして保存し、パッケージに正規の下流レコードを生成させる。** 下流を項目ごとに直接 INSERT すると、画面・承認フローが埋める整合（金額・税・原価・関連付け・計上日・収益認識）を欠いた不整合データになる。

**原則**: 自動作成シームがあるオブジェクトは、必ずそのシーム経由で生成する。**直接作成はシームが存在しないオブジェクト（マスタ・案件 等）に限る**。対象ごとのシームの有無とフラグの API 名は書込前ゲート（`ti-reference references/write-index.md`）で引く。**本ファイルにフラグ名を焼き込まない**（シームは版で変わるため、実名は実行時に引く）。

**手順**:

1. 起点レコードを作る。自動作成シームでは生成できない起点は、書込前ゲートが `function_only` として返す。**返った判定と生成経路（`function_ref` / `recipe`）に従い、正規機能・専用画面で作る**（ここで直接 INSERT へ倒さない）。
2. 自動作成フラグを ON にして保存する。
3. 生成された下流を**読み戻す**。
4. 未充当の整合項目のみ**差分 UPDATE** する。
5. 突合する（源件数 ≦ 生成件数。詳細は `import-errors.md` の生成完全性ゲート）。

**非同期生成はドレイン待ち**（数十秒〜）。待てば反映されるので、未反映に見えても再投入しない。管理会計データを作るなら投入前に copy_toma を true にしておく（`load-controls-and-prereqs.md`）。

**射程は投入・移行・サンプル作成に限る。** 稼働後の実業務データは、正規の承認・画面フローを通して作る（本節は移行時にソース文書から後続を起こすための機構であって、日常業務の代替手順ではない）。

## 画面が写す項目を API 経路は肩代わりしない [REQUIRED]

シームが無く明細を API で作るとき、**画面が裏で親や関連マスタから写している項目は、API 経路では空のまま**になる。空でも保存が通り、一覧の見た目も変わらないため、**後工程の集計で初めて 0 や欠落として現れる**。区分の類（写らないと下流の計算が 0 になる）でも、金額の類（一方だけ転記される）でも起きる。

**手順**: 明細を API で作る前に、**親から写る項目と写らない項目を確定させる**。

1. **捨てて構わない環境**（sandbox・トライアル・検証用の組織）で、画面で 1 件作り、API で 1 件作る。**本番組織で試さない**。書込は `ti-core references/safety-gate.md` の承認ゲートを通し、確認後に 2 件とも消す。
2. 両者を同じクエリで並べ、**差分の出た項目を明示セットの対象**にする。
3. 以後はその一覧を投入スクリプトの必須項目として持つ。**同じ組み合わせ（対象オブジェクト × 版）で一度確定すれば足りる**ので、投入のたびに作り直さない。

**金額項目が絡むときは、税抜・税込のどちらが後工程（原価計算票・会計連携）の入力かを先に押さえる。** 入力口が税込で後工程が税抜のときは丸めの向きでずれるため、**後工程の値から逆算して入力する**。

## この reference が持たないもの

- **型（何を作るか）**＝契約モデルごとの商品サービス・明細・収益/費用認識は ti-reference の recipe が正本。着手前に索引ファセット（`contract_model:*`／`cost_model:*`）で引く（`boundaries-and-gates.md`）。本ファイルは順序・関係解決・標準フロー・生成の機構だけを持つ。
- **シームの実名と可否**＝どのオブジェクトにどの自動作成フラグがあるか、作れない工程はどれかは書込前ゲート（`ti-reference references/write-index.md`）が正本。
