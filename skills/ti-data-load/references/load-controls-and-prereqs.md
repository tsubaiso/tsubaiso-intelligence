# load-controls-and-prereqs — 投入時の制御と前提セットアップ

投入のどの段階で自動処理をどう効かせるかの制御と、投入先 org が満たしていないと沈黙で失敗する前提（会計期間の締め・組織デフォルト・管理会計連携・レート/共有・マスタ seed 閉包）をまとめる。前提が欠けると入力規則が出ないまま生成 0 件・レート 0・不可視になり、原因が分かりにくい。

## 本 reference の持ち場と、意味定義との分担

本 reference が持つのは**投入運用の段取り**＝どの順で何を整えるか、沈黙で失敗したときにどう見分けるか、失敗後にどう復旧するか。**どの設定が何を止めるか・どのマスタ欠落が何を壊すかという判定内容の正本は意味定義側**にあり、本文には**名前空間付きの API 名・項目 API 名を列挙しない**（日本語のスイッチ名・ラベルは、実機で項目を突き止める手掛かりとして残す）。

引き方は次のとおり。索引（`atlas_domain_index`）の `objects[].meaning_short` で表示名を引き当て、その `api_name` を `atlas_explain` に渡して意味・挙動（arm）を読む。

| 引きたいこと | 索引で探す対象 | explain で読む箇所 |
|---|---|---|
| 投入中の自動化抑止・自動作成の既定・ロック等のスイッチの所在 | master ドメインの「PSA の挙動を制御する組織階層カスタム設定」 | 挙動 family の member 一覧。family は 10 種以上あり、データ取込・管理会計連携のスイッチは分類外の「その他の挙動変更」family に入るため、**family を絞り込まず通読する** |
| 会計期間の締めの意味と、直接作成の可否 | financial_record ドメインの「月次締処理」 | 意味・カテゴリ別の締め・作成操作の判定（機能専用かどうか） |
| 管理会計データが作られる前提 | management_accounting ドメインの「管理会計2」 | 前提スイッチの arm（生成されないときの最初の確認点として明記されている） |
| 集計値が投入後に固定値のまま残る問題と再計算 | project ドメインの「案件」 | 集計項目の rule（再計算の要否・再計算後の値の権威性） |
| レート転記が効く条件・案件メンバー経由の共有が効く条件 | production ドメインの「配員」 | 転記の arm（前提条件つき）・共有の arm |
| マスタの必須入力規則（seed 閉包の確認） | 該当マスタ（例: master ドメインの「商品・サービス」） | 入力規則の behavior（`kind=validation`） |

**意味定義の member 一覧・スイッチ名は API 名またはラベルの片方しか持たないことがある。** 日本語のスイッチ名から実際の設定項目を確定するときは、対象 org を describe し、label / inlineHelpText で突き合わせる。意味定義と本文が食い違ったら**意味定義側を採る**。ただし引いた内容が明らかに用途と噛み合わないとき（更新すると別の作用を持つ項目を指している等）は実行せず、describe で裏を取る。未接続・403・未収録で引けないときは本文の段取りをフォールバックとして使う。同じ確認を意味定義側と本文で二重に走らせない。

## 投入時の制御

| 段階 | 制御 | 目的 |
|---|---|---|
| load 中 | データ取込モード（製品では「インポートモード」とも呼ぶ）を有効化 | 投入中の自動起動フロー・維持トリガを抑止し、テンプレ由来のロック/承認フローでの全件失敗を防ぐ |
| load 直後 | データ取込モードを無効化 | 通常動作へ戻す |
| 自動作成前 | 自動計上のスイッチを有効化 | 会計計上レコードの自動生成トリガの大元を開ける |
| 自動作成 | ソース文書を「自動作成」フラグで touch | 検収→仕入経費、出荷/期間収益→売上・請求・入金予定 を native 生成（非同期。完了待ち要） |
| 生成後 | ロールアップ再計算 | 投入中に抑止された積み上げ集計を明細から復元する。**再計算は必須**で、実行しないとテンプレ由来の固定値が残る。再計算後はロールアップ値が正であり、明細直接集計へ切り替える必要はない |

各スイッチの所在（どの設定オブジェクトのどの項目か）は上表の引き方で意味定義から当たりを付け、**項目 API 名は describe で確定する**。承認・ロック・自動計上の制御項目は、合成・移行レコードでは「未承認・未ロック・自動計上 OFF」で入れ、生成は投入後に意図して発火させる。インポートウィザードの「ワークフロールールおよびプロセスを適用」チェックは、フローを動かしたい段階でのみ ON。

## 前提1：会計期間の締めが無いと会計計上レコードが作れない

会計計上レコード（仕入経費・売上・請求 等）の作成時、各レコードは**期間ロックの入力規則**で対象月の締め状態を確認する。投入先に対象月の締めレコードが無いと「月次締処理が設定されていません」で**会計計上レコードの作成が全件失敗**する。自動作成の非同期ジョブは例外を握りつぶしてメール通知するため、生成件数 0 なのに「失敗ジョブ 0」に見え、原因が分かりにくい。

- 締めレコードはパッケージインストールでは自動作成されない。**投入前に用意しておく**。
- **直接 INSERT・インポートでは作れない**（意味定義上は機能専用＝計算・締め・転記の機能が生成する）。顧客 org は**製品の月次締作成機能**で用意する。検証・スクラッチ org は初期化用の post-install スクリプト（手動実行相当）を匿名 Apex で実行する。**正本クラス実名・メソッド名・スクラッチ専用スクリプトのファイル名・関連カード番号は本文に載せない**（実行時にコードベースを ref で確認する）。
- 用意する範囲: 会計計上年月と締めレコードを、投入対象期間を十分に覆う年月分（当年の前後 10 年＝計 21 年分が目安）、**未ロック（ロックステータス＝未ロック）**で用意する。
- 確認: 投入対象期間（取引の計上日レンジ）の締めレコードが未ロックで存在すること。ロック済の月には作れない。

## 前提2：組織デフォルト設定が無いと取込モードの切替に失敗

投入時の制御スイッチ（データ取込モード・自動計上）は、組織に 1 件だけ置く**階層カスタム設定の組織デフォルトレコード**を更新して効かせる。新規 org・パッケージ払い出し直後の org はこのレコードが未作成のため、設定レコードを引く処理が対象 0 件で失敗する。

- 投入前に組織デフォルトを 1 件 seed する（階層カスタム設定の組織デフォルトは `SetupOwnerId` に組織 Id を入れたレコード）。
- 最低限の項目（債権・債務の入出金予定の理由の既定など）だけ設定すればよい。どの項目が何を決めるかは意味定義の挙動 family で当たりを付け、項目は describe で確定する。
- **冪等にする**（既存なら作らない）。投入スクリプトの前段に「無ければ作る」ステップとして組み込むと、新規・払い出し org でもそのまま回る。

## 前提3：マスタ seed の必須参照閉包

マスタ（品目・取引先・部門 等）が、別の小さなマスタへの**必須参照**を持つことがある。参照先マスタを seed セットに入れ忘れると、参照がブランク化し、対象側の必須入力規則が発火してレコードが load されない。代表例＝**在庫管理対象の品目は基準単位が必須**（さらに売上プロセスを使うなら販売単位、調達プロセスを使うなら仕入単位が必須）で、単位マスタを seed していないと品目の単位 lookup が解決できずブランク化し、単位必須の入力規則が発火 → 当該品目が未 load → その品目を参照する取引明細が連鎖ブロックされ、下流の会計計上レコード（売上等）まで生成されない。どのマスタにどの必須条件が掛かるかは意味定義の当該マスタの入力規則（`kind=validation`）から引く。

- マスタの seed セットは「マスタが参照する必須項目の参照先マスタ」まで閉包を取る（原則1 の徹底）。describe で各マスタの必須・作成可能な参照を数え上げ、seed セットに含まれているか確認する。
- 取引に在庫管理対象品目を使わない設計なら、品目カタログは忠実に seed しつつ、取引プールからは在庫管理対象を除外する手もある。

## 前提4：管理会計データは前提スイッチが有効でないと作られない

サンプル作成・データ移行でも基本的に管理会計データ（管理会計2）を作る。管理会計2 は各取引・会計明細（売上明細・仕入経費明細・受注明細・配員 等）の保存時に、明細種別ごとの自動起動フローが生成する。これら全フローの入口条件が、カスタム設定の**「管理会計へのデータ登録」（既定 true）**という共通の前提スイッチで、無効だと明細はできても管理会計2 が一切作られない。このスイッチが「管理会計2 が一切生成されないときの最初の確認点」であることは、意味定義の「管理会計2」の前提スイッチ arm に収録されている。

- 意図的に外す例外運用でない限り、**投入前に有効**であることを確かめる。
- 投入中はデータ取込モードで自動起動フローが抑止されるため、管理会計2 は**取込モード解除後の生成段階**で作られる（または下記の再作成で作る）。
- 症状判定は管理会計2 の総数でなく**明細種別リンクで**行う（予実・受発注側だけ存在し、売上/仕入の実績が欠落していることがある）。

**管理会計2 が抜けた場合の復旧（順序が重要・先に前提スイッチを有効化）**:

1. **案件単位**＝案件／制作指図のラベル「管理会計を再作成」のチェックボックスを立てる（項目は対象オブジェクトを describe してラベルで確定する）。記録更新フローが約 1 分後の scheduled path で、その案件の未保護レコードを削除→全明細を再同期にして再生成する。即時には動かない（約 1 分＋非同期ドレイン待ち）点に注意。
2. **明細単位**（案件単位で取りこぼす／失敗する場合）＝各明細のラベル「管理会計を再作成」のチェックボックスを立てる。**項目は対象明細を describe してラベルで確定する**。無効化・論理削除のフラグと取り違えると、再作成のつもりでレコードを無効化してしまうため、立てる前に項目のラベルと型を確認する。
3. **大量明細の一括再作成は型別に直列**で（並列処理のロック競合回避）、各型ごとに数十秒のドレイン待ちを見込む。

## 前提5：社員・担当者・レート・共有（配員/工数・担当者を伴う投入）

配員（工数）や担当者を伴うデータを投入する場合、次を満たす。満たさないと「レートが 0」「担当者 lookup が解決しない」「投入レコードが該当ユーザから見えない」という形で表面化し、入力規則が出ないため原因が分かりにくい（沈黙の前提）。

- **人件費レートマスタを社員マスタに紐付ける（適用期間つき）**。配員は作成時に社員マスタのレートマスタから人件費レートを転記する。転記が成立する前提条件（適用期間の合致）は意味定義の「配員」の転記 arm に明記されている。レートマスタは非必須 lookup（入力規則なし）ゆえ、前提3 の閉包対象に含める（未設定でも load は通るが労務原価が 0 になる）。
- **社員マスタに有効なユーザを紐付ける**。社員部門マスタの公開グループメンバー生成はユーザ導出（有効 User）が前提。ユーザなし社員マスタ（協力会社 等）は共有・担当者可視性の対象にならない点を運用で織り込む。
- **社員部門マスタで公開グループメンバーを生成させる**。これがないと部門公開グループにユーザが登録されず、保存時の共有設定が対象ユーザに共有できない＝担当者 lookup 不可・レコード不可視。公開グループの自動生成は組織階層カスタム設定の自動化系スイッチに従う。
- **案件メンバー経由の共有条件は別系統**。配員等は保存時に、参照先案件の案件メンバー（有効ユーザが紐づくもの）へレコード共有される。成立条件（案件が設定されていること・案件メンバーに有効ユーザが紐づくこと・共有機能のスイッチが有効なこと・対象レコードが共有対象フラグを持つこと）は意味定義の「配員」の共有 arm から引く。
- **直接 INSERT する場合の明示**: レート転記・共有は正規経路（配員作成トリガ・グループ生成・共有トリガ）でしか埋まらない。直接 INSERT では (a) レートは配員に手設定、(b) 可視性は管理者権限での閲覧に留まる（一般ユーザ視点は再現されない）ことを前提に読み、実運用との乖離を承知した上で使う。

## 前提6：一括移行ツールのターゲット指定の回避策

外部の自動移行ツールには、ターゲットオブジェクト指定時に対象 CSV を空扱いにしてクラッシュする**特定バージョンで既知の不具合**がある。**回避**＝ターゲット指定オプションを使わず、投入したい CSV だけを入れた一時ディレクトリを入力ディレクトリに渡す（dir 内に存在する CSV のみが load 対象になる）。ツール本体を改変しないのでパートナー配布でも安全。バージョン番号のピン留めや具体パスは本文に載せず、実行時に確認する。
