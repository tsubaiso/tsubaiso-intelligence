# demo-chain-generation — デモ連鎖生成の機構

デモ・サンプル・テスト用のトランザクションを、整合を保って作るための機構。**上流レコードの自動作成チェックボックスを ON にして保存し、正規の下流レコードを生成させる**。下流を直接 INSERT しない。**どのシナリオを何件・どの順で作るかのワークフローは持たない**（それは ti-poc がモードプロファイルで本ファイルの機構を呼ぶ）。

## 発火点（自動適用・指示不要）

PSA/IMA org へデモ/サンプル/テスト用のトランザクションを作成する瞬間、ユーザー指示の有無に関わらず本節を適用する。**書込直前に ti-reference の write-index（`ti-reference references/write-index.md`）を引き**、対象が `function_only`（自動生成シームで作れない起点）／auto_create シーム（源として/作成先として）に当たるかを判定する。判定に従い、直接 INSERT に進まず本節のチェックボックス連鎖に切り替える（判定→本節適用は自動、実投入＝org 書込は §7.C 承認）。ゲート機構は write-index が正本で再実装しない。

## 直接 INSERT しない理由

デモ・サンプル・テストデータの下流レコード（受注→制作指図／納品／期間収益／従量収益、制作指図→原価計算票、各明細→管理会計2 等）を項目ごとに直接 INSERT すると、画面・承認フローが埋める整合（金額・税・原価・関連付け・計上日・収益認識）を欠き、不整合データになる。パッケージは「上流レコードの自動作成チェックボックスを ON にして保存すると、データを引き継いだ**正規の**下流レコードが生成される」設計を持つ。承認は本来このチェックを自動で ON にするだけなので、デモ用途では承認を待たず手動でチェックを ON にして保存すれば正規の次工程データを作れる。これを既定手順とする。

**原則**: 自動作成シームがあるオブジェクトは、必ずそのチェックボックス経由で生成する。**直接作成は「自動作成シームが存在しないオブジェクト（マスタ・案件 等）だけ」に限る**。対象ごとのシーム有無は write-index で引く。

## 主要チェックボックス（受注起点の例）

| 上流レコード | ON にするフラグ | 生成される正規の下流 |
|---|---|---|
| 受注 `tb_SalesOrder__c` | 各自動作成フラグ | 発注／制作指図／納品／期間収益／従量収益（明細起点・保存時） |
| 受注 `tb_SalesOrder__c` | `tb_AutoCreatePdO__c` | 制作指図（原価側プロセスの起点） |
| 受注 `tb_SalesOrder__c` | `tb_AutoCreateOD__c` / `tb_AutoCreateTS__c` / `tb_AutoCreateUS__c` | 納品／期間収益／従量売上 |
| 制作指図 `tb_ProductionOrder__c` | 保存で自動（フラグ不要） | 原価計算票＋管理会計2 |
| 部門社員ロール `tb_DeptEmployeeRole__c` | `tb_ToCreateWorkTime__c` | 配員 |
| 配員 `tb_WorkTime__c` | `tb_SyncMA__c` | 管理会計2（配員実績） |
| 案件 `tb_Project__c` | `tb_RecreateMA2Record__c` | 紐付く全明細の管理会計2を再作成（約1分後・非同期） |

> フラグの API 名は投入機構に不可欠なデータモデル語彙。実名・最新のシームは write-index（実体＝Atlas MCP `atlas_write_seam`）と管理パッケージのコードを ref で確認する（code-investigation）。

## チェーン起点の例外（function_only・専用画面）

見積 `tb_Quote__c`・受注 `tb_SalesOrder__c` は**どの自動作成シームでも生成されない** function_only（源＝専用画面・案件からの作成・システムモード Flow）。起点のこの 1〜2 レコードだけは**専用画面（UI）またはシステムモード Flow**で作る（直接 INSERT もチェックボックスも不可）。起点さえ作れば、以降はチェックボックス連鎖で正規生成できる。

## 連鎖の型

1. 起点（見積／受注）を専用画面 or システムモード Flow で作る。
2. 自動作成フラグを手動 ON にして保存する。
3. 生成された下流を**読み戻す**。
4. 未充当の整合項目のみ**差分 UPDATE** する。
5. 突合する（源件数 ≦ 生成件数。詳細は `import-errors.md` の生成完全性ゲート）。

前提として管理会計データを作るなら投入前に copy_toma を true にしておく（`load-controls-and-prereqs.md`）。**非同期生成はドレイン待ち**（数十秒〜。待てば反映されるので、未反映に見えても焦って再投入しない）。

## UI 専用工程を system-mode で越える暫定策（恒久改修が入るまで）

デモ・サンプル・テストデータの構築では、直接 INSERT もチェックボックス連鎖も効かない工程に突き当たることがある（起点レコードが function_only、集計・転記が UI リストボタンでしか動かない 等）。恒久改修（トリガーフロー化 等）が入るまでの暫定策として、整合を保ったまま越える手順が 2 系統ある。**record-triggered フロー・入力規則は発火するが、画面フロー（ボタンアクション）は発火しない**という前提を共有し、逸脱はステアリングに明記する（特定案件・恒久改修カード番号は本文に載せない）。

- **(1) レコード生成系（function_only の起点）**: 既存の正規レコードを雛形に、作成可能項目だけを動的 clone してシステムモードで INSERT する。入力規則・record-triggered フローは発火し整合が維持される（画面フロー＝ボタンアクションのみ非発火）。clone 時は添付コピー等の危険フラグを false 化する（無フィルタの添付照会が実装制限エラーで失敗するのを防ぐ）。
- **(2) 集計・転記系（UI バッチ・リストボタン）**: 出力先が**更新可能フィールド**なら、バッチと同じ値を直接セットして再現する。数式派生値（進捗度・原価計 等）は自動で追随する。どのフィールドが更新可能かは describe で確認してから使う。一方、明細レコードそのものの自動作成を更新可能フィールドの直接セットで代替できるかは個別に見極める。

いずれも「**正規の下敷きデータ（実データ）＋ UI ゲート工程だけを暫定再現**」が原則。

## 本番非適用

手動フラグでの連鎖生成はデモ・サンプル・テストデータの効率化手段。本番の実業務データは正規の承認・画面フローを通す。

## 型は recipe を引く（型を焼き込まない）

契約モデルごとの「商品サービスの型・明細の型・収益認識・費用認識」の具体は、ti-reference の recipe が正本。本スキルはそれを索引ファセット（`contract_model:*`／`cost_model:*`）で引いて適用するだけで、型そのものは持たない（業種が増えても本スキルは変わらない）。**recipe の登録コード名は本文に焼き込まず、引くのは索引ファセットのみ**。型の判定手順と取り違えの検知サインは `boundaries-and-gates.md`。本スキルの責務＝連鎖の機械と投入の制御。recipe の責務＝業務モデルの型。この主従（スキル＝実行、意味定義＝航法）を崩さない。
