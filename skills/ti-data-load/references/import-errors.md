# import-errors — よくあるエラー対処と検証

インポート・自動生成でよく出るエラーと、その原因→対処。末尾に検証と生成完全性ゲート、一次情報URL。エラー対処で参照する入力規則の実トリガ名は本文に焼き込まず、業務語で書いて実名はコードベースを ref で確認する（code-investigation）。

## よくあるエラーと対処

| エラー | 原因 | 対処 |
|---|---|---|
| 削除済みエンティティ参照エラー（`ENTITY_IS_DELETED`） | 会計計上レコードを直接 load、または削除済み取引文書への参照が残っている | 会計計上レコードは load せず自動作成へ（原則2）。ソース文書は live 参照のみにし、不要な継承参照はブランク化 |
| 参照解決失敗（`INVALID_CROSS_REFERENCE_KEY`） | マスタが投入先に未先在、または内部 Id を直参照（組織で無効） | マスタを先に投入（原則1）。参照は tb_ExId で解決（原則3） |
| 選択リスト値エラー（`INVALID_OR_NULL_FOR_RESTRICTED_PICKLIST`） | 選択リストに表示ラベルを入れた（API 参照名が必要） | オブジェクトマネージャで値の API 参照名を確認して入れる（翻訳メニューで表示ラベル↔API 参照名の対応を確認） |
| 重複値エラー（`DUPLICATE_VALUE`） | ユニーク項目（部門コード・tb_ExId 等）に重複値 | オブジェクト内で一意の値にする。tb_ExId は特に一意・大文字小文字区別 |
| 入力規則例外「月次締処理が設定されていません」 | 投入先に会計計上年月・月次締処理が未作成で、会計計上レコードが期間ロックの入力規則で全件作成失敗 | 投入前に月次締を作成（`load-controls-and-prereqs.md` 前提1）。21年分を未ロック生成 |
| 入力規則例外（在庫管理対象品目の単位必須） | 在庫管理対象品目の参照先である単位マスタを seed していないため単位 lookup がブランク化し、単位必須の入力規則が発火して品目が未 load → 取引明細が連鎖ブロック | 参照先マスタ（単位マスタ等）まで seed の閉包を取る（前提3）。取引に在庫管理対象品目を使わないなら取引プールから除外する手もある |
| インポートモード切替が失敗（設定レコード 0 件／添字エラー） | 新規・払い出し org に組織デフォルト設定が未作成 | 投入前に org デフォルト（`SetupOwnerId`=組織 Id）を 1 件 seed（前提2）。冪等に「無ければ作る」 |
| 管理会計（MA2）が作られない／実績の売上・仕入が管理会計に出ない | カスタム設定「管理会計へのデータ登録」（copy_toma）が false で、MA2 生成フロー群が発火していない | フラグを true にし、案件単位（約1分後発火）または明細単位で再作成（前提4）。順序は必ず「フラグ true → 再作成」 |
| 配員の人件費が 0／担当者 lookup が空／投入レコードが該当ユーザから見えない | 社員マスタのレートマスタ・ユーザ紐付け、または社員部門マスタの公開グループメンバーが未設定（入力規則が出ないため気づきにくい） | 前提5 を満たす（社員マスタにレートマスタ＋有効ユーザ／社員部門マスタで公開グループメンバー生成）→ 再投入 |

## 検証

件数（投入件数＝生成件数の整合）／主要項目（金額・日付・参照先）／業務シナリオ（受注→売上→請求→入金、調達→検収→仕入経費）で突合する。

### 投入後の答え合わせ（3層・完了条件）[REQUIRED]

**答え合わせは投入の後工程ではなく完了条件**で、指示を待たずに走らせる。**明細の合計と正解値の突合だけで終わらせない**——合計が一致していても、集計の経路が切れている・作り方が正規経路でない、という誤りは残る。抽象度の高い順に降り、層ごとに違う種類の誤りを捕まえる。

| 層 | 見るもの | この層でしか出ない誤り |
|---|---|---|
| **L1 管理会計** | 計画・予定・実績の各列が、集計区分・集計科目ごとに矛盾なく並ぶか。**月別でも見る**（合計だけで判定しない） | 集計科目の分岐から外れて未集計へ落ちている／ある発生源が丸ごと欠けている／前提スイッチが切れていて1件も作られていない／**計上日が空で、どの期間にも立っていない** |
| **L2 伝票の最終形** | 画面に出る集計値・予算・残高が発生源と一致するか | ロールアップの取りこぼし／予算の鎖が切れている／解消されない残高／集計値どうしの食い違い |
| **L3 構造・経路** | 各レコードが正規の作成経路を通り、親子の紐づきが本来の形か | 上流を飛ばした直接作成／用途の違う親への相乗り／作成に失敗した試行の親だけが残る残骸 |

**L1 を先に見るのは、誤りが最も大きく出るから**。管理会計は全発生源を1つの面に集めるので、経路ごと欠けているものがここで最初に見える。L2 は「どの伝票で欠けたか」、L3 は「なぜ欠けたか（作り方）」に降りる。**L3 は金額が合っていても不合格になりうる**——構造の誤りは金額に現れず、次に触ったとき（承認・締め・追加投入）に初めて表面化する。

**金額の検査と時間軸の検査は別で、L1 は月別で1回見る [REQUIRED]。** 合計の一致が保証するのは「どこかに全額ある」ことだけで、**いつ立っているかは保証しない**。計上日が空の会計計上レコードも合計には正しく入るため、金額の突合は素通りし、月次の面でだけ崩れて出る。L1 では (1) 計上日が空の会計計上レコードが無いこと（種別ごとに件数を出し、空があれば源泉レコードのどの日付が空かまで辿る）、(2) 意図した期間に意図した金額が立っていること（合計でなく月別）を見る。**顧客が最初に開くのは月次の面**なので、金額が合っていてもここが崩れていれば信用されない。埋める側の規約は `migration-principles.md §業務日付は実績側と予定側を対で埋める`。

判定の中身は承認前チェックの**観点(h) 集計整合**と同じものを使う（`ti-update references/approval-support.md`）。チェック項目を本書へ写さず、同じ判定を二重に持たない。

**⚠️ が出たら、手当てでなく手順へ帰属させる [REQUIRED]。** ⚠️ を1件ずつ直して終わると、次の投入でも同じ誤りが出る。原因を「レコード側の値」「投入順序」「正規経路を通っていない」「製品側の制約」のどれかに帰属させ、**投入手順の側を直してから再実行**し、同じ⚠️ が出ないことを確かめる。**「積み上がらない」を製品側の制約に帰属させて集計項目を直接更新しない**——正規経路を通っていないことの症状かどうかを先に疑う（`ti-update references/boundaries-and-gates.md §集計側の項目を直接更新する手当ての抑止`）。

**移行で見るのは「入ったか」ではなく「読めるようになったか」。** レコードが揃っていても集計経路に乗らなければ業務では使えない。移行の完了条件は L1 の一致に置く。

**生成完全性ゲート**＝「**ソース文書（受注・発注等）の件数 ≦ 生成された会計計上レコード（売上・請求・入金予定・支払予定・支払・仕入経費）の件数**」を最終ゲートにする（総称語でなく個別名で数える）。壊れたデータを「完了」と報告しない。ゲートが満たせない・判定不能なら捏造せず人へ引き継ぐ。
