# boundaries-and-gates — 隣接境界・着手前ゲート・書込前ゲート委譲

本スキルと隣接スキルの分かれ目、着手前に型を引く索引ゲート、書込直前に構造ゲートへ委譲する規律。境界の正本は TI クライアントスキル体系設計と ti-update 設計。

## 隣接境界（誤発火の決め手）

| 相手 | 分かれ目 | 決め手 |
|---|---|---|
| **ti-update** | 一括投入の機構 vs 日常の少量書込 | **稼働前/後の timing では分けない**。初期一括ロード・org間移行・期首残高・大量投入・**稼働後のCSV/ファイル一括登録/更新**＝ti-data-load／稼働後の**日常の少量（1件〜数件・対話的）**の作成・更新（トランザクション＋マスタメンテ）＝ti-update。稼働後でも一括なら本スキル、稼働前でも「テスト中に1件だけ対話的に直す」なら ti-update 寄り。境界の対の記述は ti-update `boundaries-and-gates.md` と揃える |
| **ti-poc** | 機構 vs ワークフロー | デモデータ連鎖生成の**機構**（自動作成連鎖・投入制御・前提セットアップ）は ti-data-load 保持。どのシナリオを何件・どの順で・どんな体験で作るかの**ワークフロー**は ti-poc。ti-poc がモードプロファイル（量・シナリオ）付きで本スキルの references を参照する（ti-poc → ti-data-load の一方向。本スキルからハードパスは張らない） |
| **ti-reference** | 投入の機構 vs 型・参照・構造ゲート | 契約モデルの型（recipe）・SOQL 参照/集計・書込前の構造ゲート（write-index）は ti-reference。本スキルは投入に専念し、型は索引で引き、ゲートは委譲して呼ぶ |
| **ti-metadata** | レコード/設定 seed vs メタデータ定義配備 | 月次締レコード・組織デフォルト設定レコード・copy_toma フラグ値は**レコード/カスタム設定の seed**（データ投入の前提）で ti-data-load が担う。カスタム項目・レイアウト・Flow・権限セット等の**メタデータ定義の差分デプロイ**は ti-metadata。「設定値を1件入れる（seed）」と「定義を配備する（deploy）」を混同しない |

## 着手前ゲート（型の索引呼び出し）[REQUIRED]

**発火点（自動適用・指示不要）**: デモ/PoC/移行/テスト用に「どんな商品サービス・どんな明細・どんな案件を作るか」を決める瞬間、ユーザー指示の有無に関わらず本節を先に通す。オブジェクトを 1 件でも作り始める前に実行する（連鎖生成は「作る対象と型」が確定してから）。

**なぜ [REQUIRED] か**: 連鎖の機械（自動作成フラグ）が正しくても、業種・契約モデルで変わる商品サービス／明細／収益認識／費用認識の**型**を取り違えると、整合はしているが業務的に誤ったデータになる。型の正しさは連鎖の機械では担保されない。

**手順**:

1. **業種と契約モデルを判定する**。少なくとも収益の型（準委任・人月課金／進行基準／検収基準／期間／従量）と費用の型（自社社員の工数か、協力会社への外注か、両方か）を確定する。不明・混在なら決め打ちせず `ti-core references/spec-roundtrip.md` でユーザーに確認する。
2. **契約モデル索引で該当 recipe を引く**（ti-reference）。索引ファセット（`contract_model:*`／`cost_model:*`）で recipe を返す。売り側・買い側（費用側）を各々引く。**recipe の登録コード名は本スキルに焼き込まず、引くのは索引ファセットのみ**（型の本体＝recipe の意味定義が正本）。
3. 引いた recipe の型（商品サービスの型・明細の型・収益認識・費用認識）に従って構築計画を作る。
4. その後にオブジェクト作成へ進む（マスタ→起点→チェックボックス連鎖・`demo-chain-generation.md`）。

**型取り違えの検知サイン**（1 つでも当たれば型の再判定・recipe 再取得）:

- 人月課金（準委任）なのに商品サービスが 1 種類だけ・単位が「人」でない・控除/超過の受け皿がない。
- 協力会社（BP）を社員マスタに登録して工数で回そうとしている（原価が直接労務費に落ち、本来の外注費と乖離する）。
- 進行基準案件で、受注明細本体の商品サービスの収益認識を「進行基準」にしている（本体は検収基準、進行基準は専用の商品サービスで期中相殺が正）。

## 書込前ゲート（構造ゲート）の ti-reference 委譲 [確定]

create / insert / import の**書込直前**に、ti-reference の write-index（`ti-reference references/write-index.md`）を参照ファイル経由で呼ぶ。ゲートは `function_only` 検出・参照先の有効条件（C5 参照フィルタ）・自動生成（auto_create）シームの両方向検出を担う。返る判定に従う:

- **❌ 直接 INSERT 禁止**（別シームの自動生成先）＝`demo-chain-generation.md` の連鎖に切り替える。
- **⚠️ シーム経由で書く**（フラグ→保存→読み戻し→差分 UPDATE→突合）。
- **✅ 通常の作成・更新でよい**（入力規則の充足は書込スキル側の射程）。

C5 の有効条件（参照先マスタの `active_condition`）は候補取得 SOQL に WHERE として付与し、無効・終了・User 未紐付けで非有効なマスタを参照しない（画面の lookupFilter は API・直接書込・インポートに効かないため、有効条件フィルタは投入側で必ず適用する）。

**ゲート機構を再実装しない [REQUIRED]**: function_only／C5／auto_create の実装カバレッジは write-index.md／ti-reference が所有・注記する。本スキルは個別 arm の実装状態を独自に断定せず、write-index の判定に従う。ゲートが「判定不能／未カバー」を返したら捏造せず人へ引き継ぐ。写像元と配布 write-index.md で記述が食い違う場合は、配布リポ main の write-index.md／`atlas_write_seam` 応答を正本に確認する。

## 発火点の独立性

「着手前ゲート（型の判定＝何を作るか）」と「書込前ゲート（構造ゲート＝どう書くか）」と「連鎖生成の機械（どう作るか）」は別の発火点で、片方の実施が他方を代替しない。連鎖生成節を実施したことは着手前ゲート・書込前ゲートを代替しない（機械の正しさ ≠ 型の正しさ ≠ 構造の可否）。
