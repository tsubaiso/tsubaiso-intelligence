# mode-and-handoff — poc モード・onboarding 引き継ぎ・ロール別

本スキル（契約前寄り）と ti-onboarding（契約後寄り）は同じ層2能力を違う局面モードで束ねる**連続体**である。本 reference は poc モードの挙動・onboarding への引き継ぎ・ロール別出し分け・安全ゲートの用語区別を定める。

## poc モードの挙動軸

契約前の局面に合わせて、層2能力を呼ぶ際の挙動を設定する。

| 設定軸 | poc モードの値（onboarding モードとの対比） |
|---|---|
| データ規模 | サンプル／少量（onboarding＝全量移行・期中運用） |
| 対象環境 | トライアル環境・破棄前提（onboarding＝Sandbox → 本番） |
| 書込ポリシー | トライアル環境内で自由に試せる（やり直し自由）。ただし作法（自動生成シーム経由・dry-run→突合）は本番と同一 |
| 語り口 | 自己完結ガイド・意思決定者向けの要点（onboarding＝実務者・管理者向けの手順の詳しさ） |
| ゴール | 価値実証・意思決定の後押し（onboarding＝本稼働への着地） |
| 失敗の扱い | やり直し自由（学習体験の一部）（onboarding＝是正してリリース判断） |

モードプロファイルの正式なパラメータ化は横断基盤側の次版で扱う。それまでは各体験の発火点でこの挙動を注記として適用する。

## 安全ゲート ≠ ライセンス制御（用語の区別）

混同しやすいため明記する。トライアルの「環境内で自由に試せる（破棄前提）」は書込ポリシーの緩さであって、安全ゲートを外すことではない。

| 用語 | 何のための仕組みか |
|---|---|
| **安全ゲート** | org 書込時の事故防止（dry-run→承認→突合・書込前インデックスで自動生成シームを引く二重計上ガード・PII マスキング）。契約とは無関係。横断基盤の安全機能 |
| **ライセンス制御** | 契約解除で機能を停止させる仕組み（意味定義を返さないことで機能停止）。提供形態の別レイヤーで、本スキルの射程外 |

poc モードでも安全ゲートの作法（シーム経由・突合）は本番と同一に保つ（連続性と安全教育を兼ねる）。「契約解除でスキルを止める」はライセンス制御の役割で、安全ゲート（事故防止）とは別系統である。

## poc ⇄ onboarding の引き継ぎ（モード遷移）

- PoC で作った業務モデル・マスタ設計の下書き・マッピング定義は、契約後の ti-onboarding へそのまま引き継ぐ（能力は同じ層2なので作り直さない）。引き継ぎの入口（契約成立検知でのモード遷移）は本スキルが持ち、受け口は ti-onboarding が持つ（双方向の対）。
- **契約成立が判明した時点で局面モードが poc → onboarding へ遷移**する（相互排他の切替でなく連続体上のモード遷移）。
- **未判定既定**: 契約状態・環境が読めないときは、フェーズを確定せず、参照・可視化のみで応答し、書込・環境前提を要する段に入る前に契約状態と環境を能動的に確認する。poc モード（サンプル・破棄前提・少量）を本番顧客に安易に適用しない（本番 org への誤書込を避ける）。
- トライアル環境であっても「契約後の設計・移行の予行」なら onboarding モードで動く余地を残す（環境だけでモードを断定しない）。

## ロール別の見せ方

ロールは機能分類に直交する横断軸で、強制境界は org 権限（横断基盤のロール出し分けがディスパッチ・権限セットが強制）。

| ロール | 見せ方（呼ぶ層2・見せる要点） |
|---|---|
| プリセールス・営業（実演の主オペレータ） | 4体験の実演進行・デモデータ準備・軸切替の台本運用（ti-reference・ti-data-load を poc モードで呼ぶ）。買い手の業務語に合わせて可視化・集計軸を差し替える |
| 評価者・意思決定者（買い手） | 「導入が簡単・速い」の実感・ROI の体感（手作業時間との対比）。内部構造・API 名は出さず業務語＋レコードリンクで受け取る |

ペルソナの細分（プリセールス／営業／評価者／意思決定者）と権限マッピングは、ロール軸の設計トラックで詰める。

## 段階導入と二層モデル

- **段階導入**: 第1段＝体験1（理解・可視化）と体験2（サンプル多軸集計）＝自社データ不要・準備ゼロで成立する中核を、ti-reference が揃う範囲で効かせる（デモデータは ti-data-load ワークフローで準備）。第2段＝体験3（自社マスタ取込・ti-data-load）・体験4（自社文書→取引・ti-update）を結線。第3段＝モードプロファイルの正式化で poc⇄onboarding のモード遷移を正式表現。層2の実装状況に段階が律速される。
- **二層モデル**: 道具と型（4体験ナラティブ・poc モードの挙動軸・驚きの源泉の設計原則・デモデータの山と谷の型・多軸集計の軸セットの型・実演台本の型・ロール別出し分けの枠組み）は**標準**、あてはめ（買い手の業種・業務プロセスの中身・実マスタ・実文書・見せる軸の具体・台本の細部）は**顧客ごとに AI が都度生成**。取り違えない（体験の枠組み＝標準／実演内容＝顧客固有）。
- **評価軸**: 進行の十分性は「4体験を順に回せたか」だけでなく「**意思決定を後押しできたか（買い手が簡単さ・速さを実感し次段へ進んだか）**」で測る。かつ驚きの源泉（AI 固有性）を外していないか（人力準備で代替可能な見せ方に堕していないか）を評価軸に含める。
