# demo-data-and-scenario — デモデータ作成・多軸集計・実演台本

体験2「見たい軸を変えた集計がその場で速く出る」を成立させるには、多軸で切り替えても差が出る最小限のサンプルデータと、軸を次々変えて速さを体感させる台本が要る。デモデータ作成の**機構は ti-data-load**、**どのシナリオを何件どの順で用意するかのワークフローは本スキル（poc モード設定で ti-data-load を呼ぶ）**。

## デモデータ作成ワークフロー（ti-data-load をワークフロー設定で呼ぶ）

- **業種プロファイル（差し替え可能な型）**: 典型顧客像に近い業種を1社設定する（例＝受託制作・運用サービス型）。受託制作／運用保守／スポットのように複数サービス種別を混ぜると、案件別粗利・サービス種別×取引先・継続/都度が軸として意味を持つ。業種はプロファイルとして差し替え可能で、型は業種非依存。
- **数字に山と谷を作る型**: 月次売上に季節変動を持たせる／案件ごとに粗利率を散らし赤字案件を数件含める／一部の請求を未入金・滞留（30日・60日・90日超）にする／取引先×サービスに偏り（主要顧客・スポット中心顧客）を作る。これで各集計軸に濃淡が出て、軸を変えると形が変わる。
- **最小規模の目安**: 多すぎると準備・実演が重く、少なすぎると軸を変えても差が出ない。取引先・品目/サービス・部門・担当者・案件・受注・売上/請求・入金を、月次推移が見える期間（直近1年程度）に分散させる。具体の件数はデモの重さと差の出方のバランスで調整する。
- **大量 I/O はスクリプト経路**: デモデータ準備は逐次呼び出しでなく雛形から生成したローカル実行スクリプトで行う（横断基盤の操作経路選択）。スクリプトは意味定義で正しい項目・関係・自動生成シームを用い、dry-run→突合を伴う（機構は ti-data-load）。

### 予算側を必ず埋める [REQUIRED]

「数字に山と谷を作る型」は**実績側**の型で、予算側に触れていない。予実対比・予算消化は実演で必ず開く軸なので、実績と対で予算も作る。**予算が空のままだと、利益の予算が大きな負の値で並ぶ**——原価の予算だけが積まれて、引かれる側の収益の予算がゼロになるため。

- **結果側の項目に直接書かない。** 利益の予算・期待の金額のように他の項目から計算される値は直接更新できず、書こうとすると更新できない項目として落ちる。**入れるのは元になる項目**（目標の金額と期待の乗数など）で、結果側はそこから決まる。
- **原価側の予算は、積む先ごとに入口が違う。** 人の予算は要員の予定時間、間接費の予算は配賦の基準量または登録した予算額、購買の予算は上流の依頼側、というように分かれる。**総額を1か所へ手入力しても、内訳を持つ軸では積み上がらない。**
- **どれが入口でどれが結果側かは意味定義から引く**（本ファイルに項目名を列挙しない）。埋めた結果は下の答え合わせのL2で、予算が空でない・利益の予算が負でないことを確かめる。

### 投入後の答え合わせ（見せる前の関門）[REQUIRED]

**デモデータは「入った」ではなく「見せる画面に⚠️ が出ない」を完了条件にする。** 実演で開く画面（案件・受注・制作指図・管理会計の集計）は、合計が正解値と一致していても、予算が空・残高が解消しない・集計値どうしが食い違う、といった状態のまま出せてしまう。**買い手はその画面を業務の目で見るので、こちらが見ていない不整合を先に見つける。**

段取りは次の3つ。

1. **先に正解表を書く**（何を何件投入すると、どの数字がどうなるはずか）。設例の正解表がデモの計画にあたる。
2. **投入したら答え合わせを走らせる**——L1 管理会計 → L2 伝票の最終形 → L3 構造・経路（機構と手順は ti-data-load `references/import-errors.md §投入後の答え合わせ（3層・完了条件）`）。
3. **⚠️ は投入手順へ帰属させて直す**。その場の手当てで数字だけ合わせない。手当てで作ったデータは、実演中に別の軸へ切り替えた瞬間に破綻する。

**実演で開かない画面まで完璧にしない。** 見せる軸・見せる伝票を先に決め、その近傍を確実に整えるほうが、全体を薄く均すより効く。

## 多軸集計の軸セットの型

「経営が日々見たい数字」に絞った少数軸。各軸は read-only・表計算出力・レコードのリンク化（明細にドリルできるよう Id 保持）を前提とする。多機能の網羅でなく、意思決定に直結する少数軸で驚きを作る。集計の実体は ti-reference の定番集計で組み、具体の項目・レシピは実装時に接地する。

| 軸 | 何が分かるか | 実演での効き |
|---|---|---|
| 月次売上推移 | 売上の伸び・季節変動 | 最初に出す基準の数字 |
| 案件別粗利（粗利率つき・赤字強調） | どの案件が稼ぎ・どれが赤字か | 「赤字案件が一目で分かる」驚き |
| 部門別 売上/粗利 | どの部門が貢献しているか | 同じ素地から別軸が即出る |
| 取引先 × サービス クロス | 主要顧客・サービスの濃淡 | 多軸クロスの自在さ |
| 売掛残高・滞留（年齢表） | 未回収・滞留の状況 | 資金面の意思決定に直結 |

追加軸（担当者別・サービス種別推移等）は同じデータから派生で出せることを口頭で添える。

## 実演台本の型

体験2を「軸を次々変えても待たずに出る」流れで見せる。各ステップは数秒で結果が出ることを前提に、テンポよく切り替える。

| Step | 進行（買い手↔AI） | 見せる驚き |
|---|---|---|
| 0 | 「サンプルデータで、見たい数字を何でも出してみます」 | これから自在に出る予告 |
| 1 | 「まず売上の推移を」→ 月次売上推移 | 待たずに出る・季節変動が見える |
| 2 | 「部門別ではどう？」→ 部門別 売上/粗利 | 同じ素地から別軸が即出る |
| 3 | 「案件ごとの粗利は？赤字はある？」→ 案件別粗利（赤字強調） | 赤字案件が一目で分かる |
| 4 | 「主要顧客とサービスの組み合わせは？」→ 取引先×サービス クロス | 多軸クロスもその場で |
| 5 | 「売掛の滞留が気になる」→ 売掛残高・滞留 年齢表 | 資金判断に直結する数字も即 |
| 6 | 締め「今出した数枚、普段なら手集計で何時間ですか？」 | 速さ＝ROI の体感へ接続 |

### 台本の原則

- 各ステップで「軸を変える指示 → 数秒で別の集計」を体感させ、**待ち時間ゼロ**を前面に出す。
- 数字の「出どころ」は体験1のデータのつながり図を指して「この数字はここから来ています」と裏づけ、信頼を担保する。
- 最後に手作業時間との対比で生産性向上（ROI）に接続し、意思決定を後押しする。
- 業務語のみ（API 名・SOQL は出さない）。金額・率は読みやすい書式に整える。

## 二層モデル（取り違え注意）

台本・軸セット・デモデータの山と谷の型は**標準**（顧客非依存）。買い手の業種・見せる軸の具体・台本の細部・実データの中身は**顧客ごとに AI が都度生成**（顧客固有）。投入・レシピ実装の段階で、業務語で定義した軸・列が製品の実オブジェクト/項目で成立するかを裏取りし、成立しない軸があれば調整する。
