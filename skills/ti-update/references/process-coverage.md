# process-coverage — プロセス網羅と段階拡張

ti-update の射程は**稼働後のデータ更新全般**（トランザクション＋マスタ日常メンテ）。入力支援・承認支援の型は対象非依存だが、対象ごとにVR・承認フロー・自動副作用が異なるため、対象を**実機の確認軸で確定してから**展開する。

## 実証済み（型の確立ドメイン）

- **受注ドメイン**: 両輪（入力支援＋承認支援）の型を確立・実証した（API必須＝主従親のみ・実境界はVR・型別切替・突合完全一致・承認真実源）。**実証済みは受注のみ**（PoC完了）。
- **同じ販売チェーンでも未実証**: 見積・売上→請求→入金は、受注で確立した型を流用する**未実証**対象であり、着手時に実機の確認軸で確定してから展開する（チェーン全体が実証済みではない＝穴を隠さない）。
- この型（読み込み→マスタ突合→整形→突合検証／正規経路＝項目更新→自動起動委譲／承認前チェックの2層構造）を、以下の対象へ同型展開する。

## 段階拡張の対象（未実証・着手時に実機確定）

| 対象 | 種別 | 状態 |
|---|---|---|
| 見積・売上・請求・入金 | 販売トランザクション（受注以外） | 未着手（着手時にトランザクション確認軸4点） |
| 調達依頼・発注・検収 | 購買トランザクション | 未着手（着手時にトランザクション確認軸4点） |
| 入出庫・在庫移動 | 在庫トランザクション | 未着手（着手時にトランザクション確認軸4点） |
| 経費精算 | 経費トランザクション | 未着手（着手時に確認軸4点＋画像OCR越境フロー。`input-support.md §領収書など画像からの経費精算`） |
| 会計仕訳・支払 | 会計トランザクション | 未着手（着手時にトランザクション確認軸4点。越境フローは適用外） |
| 取引先・商品・税区分・部門・銀行口座 等 | マスタ日常メンテ | 未着手（着手時にマスタ確認軸4点） |

**トランザクションの着手時確認軸4点**: (1) API必須＝主従親のみか、(2) 有効VRの本数と条件、(3) 承認申請フロー（画面フロー）の有無と開始条件、(4) 承認後の自動副作用フロー名。

**経費精算の着手時追加確認点**: 上記4点に加え、(5) 画像入力時のOCR抽出機能の有無と呼び出し可否（抽出と書込で担い手が分かれる越境フローに注意）、(6) 原本添付の参照渡し経路の実在。経費は「画像入力＋原本添付」が本線のため、`input-support.md §領収書など画像からの経費精算（越境フロー） / §添付の受け渡し（規律）` を必ず併読する。

**マスタの着手時確認軸**: (1) API必須、(2) 有効VR、(3) 一意制約・参照整合（他マスタへのlookup条件）、(4) 承認プロセスの有無（多くは無し＝承認支援は薄い）。

**発火時の告知**: 未実証の対象で発火したら、実体がまだ無い旨を告知し、着手時確認軸で実機確定してから展開する（型は流用・穴を隠さない）。気づいた不足は ti-core `references/feedback.md` へ。

## 依存グラフと作成計画の逆算生成

- **依存グラフ**: マスタ/オブジェクトをノード、前提依存とトランザクション順序をエッジに持つ。用途＝(1) トランザクション作成前の不足マスタ検知、(2) 新規顧客セットアップ順序の自動生成。
- **計画生成（逆算）**: 「発行したい請求書サンプル」から逆算した**作成計画を実行せずに生成・提示**する。手順＝(1) 請求書解析（取引先・明細・自社情報・振込先）、(2) 明細→商品サービス突合（合算禁止・明細数/合計一致）、(3) 依存グラフで不足マスタ検知（登録ステップ化）、(4) 各ステップに必須値・引き金項目・発火する自動起動フロー名・自動生成される後続を明示、(5) 検証条件（合計一致・明細数一致）。

計画に載せる引き金項目・自動起動フロー名は `input-support.md` の write_action から読む。実行（書込）は入力支援で、org書込直前に ti-core `references/safety-gate.md` を通す。
