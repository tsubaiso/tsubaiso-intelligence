# approval-execution — 承認操作の代行（人の許可を得て、操作だけを行う）

承認支援の点検で判断材料を出したあと、**本人が決めた結果を、本人の権限で反映する**のが本 reference の射程。AI が行うのは操作だけで、**承認するかどうかの判断は行わない**。射程に入るのは承認・却下（差戻しを含む）・承認申請・承認者の再割当で、操作ごとに前提が違う（下記）。

## 何が技術で守られ、何が守られないか

守られるのは**資格の境界**だけ。承認・却下は、割り当てられた承認者（本人・所属キューのメンバー・委任元）の権限で成立し、それ以外の利用者が指示しても成立しない。

**ただし例外がある。** すべてのデータを変更できる権限を持つ管理者は、承認者に割り当てられていなくても承認が通り得る。**この例外は技術では塞いでいないので、誰にその権限を与えているかを運用で把握しておく。**

**守られないのは「人が判断したこと」**。AI は承認者本人の権限で動くため、資格の照合は AI 起点の操作でも通る。**「AI が勝手に承認していない」ことを担保しているのは本 reference の手順そのもので、ほかに歯止めは無い。** 手順を省けば統制が消える。

**記録から分かるのは経路までで、判断した主体は分からない。** 承認指示のレコードが有るか無いかで、承認指示を経た操作か画面から直接承認したかは**事後に区別できる**（画面での承認では承認指示は作られない）。区別できないのは、**その決定を人が下したかどうか**である。承認指示があっても、それを本人の許可のもとで作ったのか AI が独断で作ったのかは記録に残らない。

## 絶対条件（省略不可）

1. **対象1件ごとに、承認者本人の明示的な許可を取る。** 「以後まとめて承認して」「同じ種類はすべて承認して」といった、**対象を特定しない包括的な許可は受け付けない**。
   **複数件を一度に示すのは構わない。** 一覧で対象・決定・理由を並べ、承認者が1回の返答で件ごとに決定を返す形は、この条件を満たす（承認待ちが10件あるとき、10往復にする必要はない）。**受け付けないのは、対象を見ないまま以後を任せる形**である。決定が示されなかった対象は操作しない。
2. 許可を求める前に、**承認前チェック（`approval-support.md`）の結果を必ず示す**。点検していない対象について許可を求めない。
3. 示すのは **対象・決定（承認か却下か）・理由** の3点。業務の言葉で書き、対象を取り違えられない形にする。
4. **決定を提案しない。** 「承認して差し支えないと思われます」のような推奨を添えない。要確認の有無と理由を示すところまでが AI の仕事。
5. 許可の言葉があいまいなとき（「いいんじゃない」「たぶん大丈夫」等）は操作せず、承認か却下かを確かめ直す。

## 手順

1. 承認待ちを特定する（捕捉のしかたは `approval-support.md` の承認真実源）。
2. 承認前チェックを回し、結果を出力規律に沿って示す。
3. 承認者本人へ、対象・決定・理由を示して許可を求める。
4. 許可を得たら、承認指示を1件つくる。決定（承認／却下）と理由をコメントとして渡す。**却下のときは理由を必ず入れる**（承認履歴に転記され、あとから経緯を追う唯一の手がかりになる）。
5. 処理結果を確認し、業務の言葉で報告する。対象レコードはリンクにする。
6. 結果が不成立だったときは、原因を業務の言葉に翻訳して伝える（下表）。**自動で再試行しない。** やり直すなら手順3から取り直す。

## 操作ごとの射程とバージョンの前提

| 操作 | 扱い |
|---|---|
| 承認 | 代行する（本 reference の手順） |
| 却下 | 代行する（同上） |
| 差戻し | **却下として扱う。** PSA/IMA に「差戻し」という固有の操作は無く、却下がこれにあたる。利用者が「差し戻して」と言ったときは、却下として何が起きるか（申請者へ戻り、承認履歴に理由が残る）を示してから許可を求める |
| 承認申請（申請を出す） | **対応するバージョンを導入している組織で代行する。** 承認・却下と同じ作法に載せる（点検結果の提示 → 本人の明示的な許可 → 操作だけを実行）。**ただし許可を取る相手は承認者ではなく申請者本人**で、申請者の権限で成立する。**起動口は導入済みのバージョンによって異なるため、呼ぶ前に到達可否を自己診断する**（下記） |
| 承認者の再割当 | **対応するバージョンを導入している組織で代行する**（同じ作法・同じ自己診断）。許可を取る相手は、いま承認待ちを持っている本人 |
| リコール（承認申請の取り消し） | **行わない。** 承認プロセスの既定が申請者からの取り下げを開放していない。**この設定は顧客が変更してよいもの**だが、開放されている組織でも本 reference では扱わない |

**申請と再割当は、呼ぶ前に到達できるかを確かめる [REQUIRED]。** 利用者に「どのバージョンですか」と尋ねても答えを持っていないことが多いので、ti-core `references/capability-preflight.md` の自己診断で判定する。**届かないと分かったら、その場で画面での操作を案内する**（黙って失敗させない・推測で別の経路を試さない）。

## 行わないこと

| 操作 | 扱い |
|---|---|
| 承認状態の項目を直接書き換える | 禁止（承認の偽装にあたる） |
| 承認するかどうかの判断・推奨 | 行わない |
| 自分が作った承認指示の修正・削除 | できない（記録を残したままにする設計） |

## 詰まりどころ

| 返ってきた結果 | 意味 | 次にすること |
|---|---|---|
| 承認者でない | 操作している本人が、その対象の承認者ではない（本人・所属キュー・委任元のいずれにも当たらない） | 誰の承認待ちかを確かめ、本人から操作してもらう。ほかの人の代わりに承認しない |
| 対象が承認待ちでない | すでに処理済みか、承認プロセスが先へ進んでいる | 現在の状態を確認して報告する。同じ対象へ二重に指示しても二重承認は起きない |

## 記録

承認指示は**あとから書き換えられない**（作成と参照のみで、編集・削除の権限を持たない）。誰がいつどの対象へどの決定を出したかが残り、承認履歴にはコメントが転記される。

**この記録が残すのは、経路（承認指示を経たこと）と決定の内容（対象・決定・理由）までで、絶対条件1〜5を守ったこと自体は残らない**（上記 §何が技術で守られ、何が守られないか）。残るものを最大限に意味のある形にするために、**理由の欄を空にしない**。理由が入っていれば、あとから経緯を追う人が「何を見て決めたか」を再構成できる。

## この reference を読む発火点

- 点検結果の提示と許可の往復は ti-core `references/spec-roundtrip.md`。
- 承認前チェックの中身は `approval-support.md`。検知は読み取り、操作は本 reference。
- **操作の器が組織に無くて始められないときは ti-core `references/capability-preflight.md`**。申請・再割当の到達可否と同じ自己診断で、承認指示のオブジェクトや承認者向けの権限セットが行き渡っていない組織の最初の詰まりどころを拾う。**「バージョンが古い」と「器が配られていない」は別の詰まり方**なので、どちらも自己診断で切り分けてから画面での操作を案内する。
