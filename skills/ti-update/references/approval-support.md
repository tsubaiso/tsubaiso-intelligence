# approval-support — 承認支援（人間の承認を助ける読み取りチェック）

> **ベータとして先行提供している機能です。** 記述が変わることがあります。扱いは ti-core の `references/beta-status.md` を参照してください。**ベータなのは本 reference が扱う承認前チェックだけで、入力支援と承認操作の代行は正式提供です。**

承認支援は、承認者・申請者が判断する前に、AIが矛盾・チェックポイントを検査して点検助言を届ける働き。**承認支援そのものは読み取りのみ**で、レコードを書かない（業務レコードへの書込は入力支援だけ）。**判断のあとの承認・却下の操作は `approval-execution.md` が担い、承認者本人の明示的な許可を得てから行う。** 承認申請の操作そのものは `approval-execution.md` が担う（対応するバージョンを導入している組織でのみ・申請者本人の明示的な許可を得てから）。

**非対称**: 承認支援は承認プロセスを持つ対象＝主にトランザクションに効く。マスタは承認プロセスがある場合のみ（多くのマスタは承認プロセスを持たないため、マスタは入力支援の突合検証が主で承認支援は薄い）。

## 承認真実源（承認待ちの捕捉）

通知メールはトリガにしない（取得が壊れやすい）。**標準の承認ワークアイテムをSOQLで直接拾う**ことを一次真実源にする。「誰の承認待ちか」と「対象レコード・種別」が確実に取れ、オブジェクト種別で対象プロセスに絞れる。承認ステータス（申請中）は補助。Slack/メール通知は「人が気づく」用。

**申請者の二層性**: 業務上の申請者はレコード側（申請担当者）、システムの申請者はログインユーザ。**職務分掌チェック（申請者≠承認者）はレコード側の申請者を見る**。

**承認履歴を辿る（兼務は履歴にしか現れない）**: 承認待ちの捕捉に加え、**対象レコードの承認履歴を時系列で取り、各ステップの種別（申請・承認・却下）と実行者を並べる**。レコード側の担当者と次の承認者だけを比べても兼務は出ない。同一人物が申請と承認を連続して実行していても、1段目を自分で通して2段目が別の人に回っていれば、レコード上は「担当者＝Aさん・次の承認者＝Bさん」と正常に見える。

- **職務分掌の判定材料は3点セット**にする——(a) レコード側の業務担当者、(b) 申請ステップの実行者、(c) 各承認ステップの実行者。(a)(b)(c) に重複があれば兼務として提示する。
- **申請と承認の実行間隔が極端に短い**場合（数秒差など）は、実質的な二重チェックが働いていない可能性として添える（断定でなく支援）。
- **却下ステップの後に申請ステップが無いまま経過している**場合は滞留として拾い、日付観点(d)の滞留・放置の点検へつなぐ。
- **兼務が業務上やむを得ない場合、申請コメント等に理由が記載されていることがある**。理由の有無も併せて提示し、兼務の指摘だけで終わらせない（小規模組織では代替統制が働いていることがある）。

定期スケジュール（営業時間中に一定間隔）で「抽出→チェック→レポート」を冪等に実行し、二重報告しない。**既報判定の記録先は監査証跡（対象レコードのフィードへの要約投稿履歴＝下記§レポートと監査証跡で固定する経路）**とし、そこに report 済みの痕跡が残っているレコードは再報告しない（別途の状態ストアを持たず、監査証跡を単一の真実源にする）。

## 承認前/申請前チェックの2層構造（ti-update内包）

承認前チェックは**別スキルにせず ti-update に内包**する。点検フレームは**標準フレーム × 会社ポリシー層**の重ね合わせ。

### 標準フレーム（全社共通・薄い）

会社によらず常に成り立つ点検の方法と、常に異常な普遍ルールだけを持つ。

| 観点 | 標準が検出する普遍ルール |
|---|---|
| (a) 利益率・数値矛盾 | 粗利マイナス／粗利率100%（原価未投入の疑い）／数量×単価≠金額／**原価予算に対する実績の乖離**（予算額・実績額・乖離額・乖離率の提示。予算未設定なら「予実判定不可」を明示）／**実績あり・単価/金額なしの欠落**（実績数量>0なのに単価が空、または金額が空・0）／**実績値そのものの網羅性**（別に記録された実働・実測との突合で、付け漏れ・二重付けを検出） |
| (b) 類似取引との相違 | 同一商品・得意先・契約形態の過去取引を引いて単価・粗利率・単位・期間を並べる（比較の**手順のみ**標準・警告要否は会社ポリシー） |
| (c) 注文書の抜け漏れ | 得意先・担当・部門・入金条件・計上期間・税区分など、業務上ほぼ普遍の必須項目の欠落／**入力規則では必須化されていないが後工程の集計が成立しなくなる紐付けの欠落**（原価の付け先＝制作指図・案件など） |
| (d) 金額・日付 | 見積↔受注の金額突合／開始日＜終了日／計上期間が契約期間内／税区分未設定（売上が立たない）／自動作成ONのとき承認後に何が生成されるかの予告／**承認待ちの滞留と、却下されたまま再申請されていない放置**（業務完了を表す日付から承認申請・承認までの経過。**対象自身の承認履歴から読めるので承認前フェーズで発火し、締め前でも再走する**——母集団監視のバックデート・期末集中とは別扱い。許容経過日数・再申請待ち日数は会社ポリシーだが、未設定でも経過そのものは提示する） |
| (e) 期間契約の契約条件 | 期間契約タイプの明細を含む取引で、契約開始日・契約終了日・自動更新の有無・解約通知期限のいずれかが未入力（検収基準のみの取引では不要）／**継続契約の見積・受注・発注（受注・発注は契約手続が更新・変更のもの）では、前回契約との差額分析**（金額・契約期間・単価・数量の差額と増減率。**同額でも「差額なし」として示す**。**標準は比較値の提示に徹し良否を断定しない**——要確認とするかの閾値・遡る期数・引き当て軸は会社ポリシー） |
| (f) 内部統制・不正防止 | 職務分掌（申請者≠承認者・発注者≠検収者≠支払承認者）／調達3wayマッチ（発注↔検収↔請求）／二重支払・二重請求／承認限度額の分割（structuring）／数値分布の異常（Benford）／機微マスタ（口座・取引先・単価）の変更。バックデート（計上日と実操作日の乖離）は日付観点として(d)で判定し、母集団監視として締め前でも再走する。**普遍的に異常なパターンのみ標準**。閾値・分掌マトリクス・機微範囲は会社ポリシー |
| (g) 承認の網羅性 | 対象と**同じ業務キーを共有する兄弟レコード**のうち、未承認・未申請、および却下されたまま再申請されていないものの件数と金額。**論理削除された兄弟は母集団から除く**。「この1件だけ承認すると、同じ業務単位の残りが未承認のまま締めに入る」ことを予告する。業務キーが解決できない対象では「網羅性は判定不可」を返し、黙って問題なしにしない |
| (h) 集計整合 | 承認しようとしている対象の**集計値・予算・残高が発生源から説明できるか**。案件・受注・制作指図のような集約単位は、売り側（見積→受注→納品→売上→請求→入金）と買い側（調達依頼→発注→検収→仕入経費→支払）の**工程ごとの金額を対で持つ**ので、上流と下流の差がそのまま「どこまで進んだか・どこで止まっているか」になる。段の飛び（上流に金額があるのに下流が0）と逆転（下流が上流を超える）／集計項目と発生源の合計の差／同じ対象を別経路で集計した2つの値の食い違い／予算の内訳の空欄と、予算が空のまま予実の差だけが負に出ている状態／解消する後工程が完了しているのに残る残高／**対象が正規の作成経路を通って作られているか**（上流を飛ばした直接作成・用途の違う親への相乗り・配下が1件も無い親）／**その金額がどの期間に立っているか**（会計の計上日が空でどの期間にも入っていない・意図した期間と違う期間に立っている・予定側と実績側で期間がずれている）。**構造の誤りも時間軸の誤りも金額に現れない**ため、合計の突合では出ない。集計の発生源が解決できない対象では「集計整合は判定不可」を返す |
| (i) 帳票記載内容 | 外部へ出る帳票を持つ対象で、**帳票に印字される項目**の欠落と慣行からの逸脱。宛名・敬称・件名・前文・本文・備考・振込先・送付予定日など、**入力規則で必須化されていなくても顧客の手に渡る項目**が対象。判定は3層＝(1) 帳票へ印字される項目の空欄を、必須項目でなくても列挙する（入力規則を通ることと帳票として正しいことは別）／(2) **同じ取引先・同じ商品/役務の直近の同種帳票で埋まっていた項目が今回は空**なら慣行からの逸脱として提示する（「通常は入るはずの備考が空」を機械で拾える形にする）／(3) 転記由来の項目（宛名・振込先・敬称）は §転記由来項目の遡及2段判定 でマスタまで遡る。**申請前・承認前の両フェーズで最重点**とし、提示は帳票の見え方の順（宛名→件名→金額→支払条件→備考）に並べる。帳票を持たない対象では「対象外」を返す |

**(a) に足した3つは、既存の恒等サニティでは代替できない。** 恒等サニティ（数量×単価＝金額）は**欠落を検出できない**——単価が空のとき0×0=0が恒等式として成立してしまうため、「実績あり・単価なし」は別の判定として持つ。同様に、恒等サニティは金額の内部整合しか見ないので、**実績値そのものが正しいか**（付け漏れ・二重付け）は別に記録された実働との突合でしか出ない。原価予実の乖離も、売上側の利益率異常と同格の観点として原価を持つ対象では常に見る。

**(g) の業務キー（何を兄弟とみなすか）はオブジェクト固有**で、標準フレーム側では決められない。束ね方の型は「親伝票」（分納・分割検収）・「親×計上期間」・「取引先×締め期間」・「人×対象期間」・「案件」などで、**対象オブジェクトごとの束ね単位は意味定義側のスイートが示す**（§標準フレームの実行手順 step1）。1社員1月＝1レコードのように**自身が分割されない対象では、兄弟は「同じ期間の他の対象」になる**（向きが逆になる）。

**(h) の集計経路（何と何を突き合わせるか）もオブジェクト固有**で、(g) と同じく標準フレーム側では決められない。集計項目とその発生源・**工程ごとに対で持つ上流の金額と下流の実績**・残高と解消する後工程・正規経路の上流を、**対象オブジェクトごとにスイートの集計経路の行が示す**（§標準フレームの実行手順 step1）。収益認識・費用認識の種別ごとに経路が分かれる対象では、経路別に上流と実績が対で持たれているため、合計だけを見ると止まっている経路が他の経路に埋もれる。**(h) が見るのは「数字が合っているか」ではなく「その数字が説明できる形で作られているか」**——金額が正解値と一致していても、集計の経路が切れていれば予実は判定できず、作成経路が正規でなければ次に触ったときに壊れる。**差を消すために集計側の項目を直接更新する助言はしない**（`boundaries-and-gates.md §集計側の項目を直接更新する手当ての抑止`）。

**時間軸は「その金額がどの期間に属するか」を決める会計の計上日で見る [REQUIRED]。** 計上日は対象自身に入力されるものではなく、**源泉レコードの業務日付から決まる**ため、空欄は対象の側でなく源泉側の日付の欠落として現れる。どの日付が源泉になるかは対象オブジェクトごとに違い、**業務日付の出どころをたどる索引が意味定義側にある**（`atlas_domain_index` で対象のドメインから選び `atlas_recipe` で本体を取得する）。実績の日付だけが入っていて予定の日付が空だと、**予定側だけが期間の集計から落ちる**——合計は変わらないので金額の突合では出ず、期間で見て初めて分かる。**計上日を後から直せば済むとしない**——外貨建てでは換算に使う日が計上日に追随するため、直すと金額そのものが動きうる。

**(i) の対象項目（どれが帳票に出るか・どれを空にしてよいか）もオブジェクト固有**で、標準フレーム側では決められない。帳票へ印字される項目と、空欄を許さない項目は、**対象オブジェクトごとにスイートの帳票項目の行が示す**（§標準フレームの実行手順 step1）。**(i) が見るのは「データとして正しいか」ではなく「顧客の手に渡る紙面として正しいか」**——金額と日付がすべて整合していても、宛名が旧社名のまま・但し書きが落ちていれば、誤りはそのまま外部へ出る。**この観点だけは、承認後に是正しても取り返せない**（他の観点は締め前・修正伝票で救えるが、送付済みの帳票は相手の手元に残る）。慣行からの逸脱は**良否を断定せず比較値として示す**（前回入っていた項目が今回空であること自体は、正当な変更のこともある）。

**「空・0が欠落」と決める前に、対象の型を見る [REQUIRED]。** 同じ項目の空・0が、型によって正常にも異常にもなる。実績で確定する契約形態（実働・実使用量で数量が決まるもの）では**上流の伝票の時点で数量0・金額0が正常**で、確定は下流の実績側で起きる。複数の伝票を束ねて作られた対象では**単一の上流への参照が空であることが正常**で、突合は束ね元の合計に対して行う。原価を持たない商品区分では**原価0・粗利率100%が正常**で、原価未投入の疑いには当たらない。判定の順序は (1) 対象・明細の型（収益/費用の認識種別・契約形態・束ねて作られたものか・商品区分）を先に引く → (2) その型で空・0が正常かを決める → (3) 正常でない型のときだけ欠落として出す。**型が引けなかったときは欠落と断定せず「判定不可（型が引けない）」を返す。** 型を見ずに欠落と断定すると、正常な取引に警告が出て、**承認者が警告そのものを信用しなくなる**（アラート疲れは件数ではなく偽陽性でも起きる）。型の供給源は意味定義で、どの型がどの正常形を持つかは会社ポリシー層にも重ねられる（原価を持たない商品区分・数量が発注時点で確定しない取引区分は会社ごとに違う）。

**型には対象の工程段階も含む [REQUIRED]。** 同じ対象・同じ項目でも、**上流の伝票（見積・受注・発注）では実績側の金額がまだ立たないので 0 が正常**で、そこで見るのは予定側（見積原価・見積利益率・上限枠）である。実績側で判定するのは、下流（売上・納品・検収・仕入経費）が立つ工程から。**工程ごとの対応はスイートの集計経路の行が「上流の金額と下流の実績を対で持つ」形で示すので、そこを読まずに実績側の 0 を欠落と断定しない**（読まないと、原価を持つ商品の受注でも全件が「原価未投入の疑い」になる）。**会社ポリシー層で区分を持たせるときは、機械で判定できる手掛かり（商品コードの接頭辞・明細の種別など）を書かせる**——業務名だけで書かれた区分は、明細を 1 件ずつ人が読まないと判定できない。

過去取引の引き当て・利益率の算定・母集団の統計検定など**集計の実体は ti-reference のレシピ／共有チェックの意味定義へ委譲**する（`boundaries-and-gates.md`）。ti-update は「何を点検するか（判定の是非）」を持ち、集計手順は持たない。

### 転記由来項目の遡及2段判定（マスタ不備の根本原因検出）

(c) の必須項目のうち**マスタから転記される項目**が空のとき、(a) で「実績あり・単価/金額なし」を検出したとき、および **(i) で帳票に出る転記由来の項目（宛名・敬称・振込先など）が空だったとき**は、レコード単体で「未入力」と報告して終わらせず、**転記元マスタまで1段遡って根本原因を切り分ける**:

- **マスタも空** → マスタ未整備が根本原因。レコード側だけ直しても次回の取引でまた空になる旨を明示し、まずマスタ登録を促す。
- **マスタは設定済** → 転記漏れ（作成経路がクライアント側のマスタ自動取得を通っていない等）。再取得・再転記で解消する旨を示す。

**切り分けの決め手は「同一期間・同一対象の他レコードに値が入っているか」**。他レコードに入っていればマスタは整備されており、当該レコード限りの転記漏れである。

**集約単位の対象では、対象自身でなく配下の子孫を走査する [REQUIRED]**。制作指図・案件・受注のように子孫の合計で金額が決まる対象では、**欠落は子孫にあって親には現れない**——親の合計は小さく出るだけで空欄にならないため、親のレコードだけを見る点検では原理的に検出できない。

判定に使う「どの項目がどのマスタから転記されるか」は意味定義の転記元（provenance）を辿る（`atlas_explain` で対象オブジェクトを引くと、転記される項目とその転記元マスタが意味記述に示される。対応する意味定義が未整備なら、対象マスタを直接読んで空か否かを確認するフォールバックで回す）。マスタ未整備が根本原因のときは、そのまま入力支援の**マスタ不備のその場修正ループ**（`input-support.md`）へ接続できる（検知は承認支援＝読み取り、書込は入力支援）。

### 標準Flow非依存（重要）

過大請求・過大支払・未請求チェック等の標準の通知系Flowは**顧客環境で無効化されうる**（Atlas上も一部が Obsolete）。承認前チェックはこれらのFlowの有効/無効に依存せず、**条件をレコード・明細から自前導出する**。標準Flowを前提にも参照にもしない（再実装もしない）。標準機能が動くための設定漏れ（税区分・入金条件・自動作成フラグ等）は (f) の設定漏れガードとして別に点検する。

### 標準 / 会社ポリシーの境界

標準＝普遍的に異常なパターン＋「標準機能が動かない／後工程が壊れる設定漏れ」＋検知の手順。閾値・限度額・分掌マトリクス・機微マスタの範囲・許容乖離率・「類似取引」の定義軸は**会社ポリシー層**（顧客保守。無ければ標準のみでフォールバック）。会社ごとの違いは標準に入れず会社ポリシーへ逃がす。

**数値の提示そのものは会社ポリシーに依存させない [REQUIRED]**。しきい値・許容差分・除外区分が未設定でも、予算額・実績額・乖離額・乖離率、実働との差分、単価/金額が欠落しているレコード、未承認の兄弟の件数と金額、集計値と発生源の合計の差、**帳票に印字される項目のうち直近の同種帳票で埋まっていて今回は空のもの**は**常に提示する**。判定が黙って消えると、承認者は「見なくてよい」と「見る手段が無い」を区別できない。

### 会社ポリシー層（2層＝org のルールストアと作業フォルダのファイル）

業種・会社で変わるパラメータと方針を持つ。**会社ポリシー層は2層で、置き場が違う [REQUIRED]。**

| 層 | 置き場 | 何を持つか | 編集主体 |
|---|---|---|---|
| **会社共通（一次）** | **org 内のルールストア**（カスタムメタデータ型のレコード） | 全員が同じものを見る必要がある判定＝しきい値・限度額・分掌マトリクス・機微マスタの範囲・除外区分・帳票ごとに空欄を許さない項目 | 人が設定画面またはメタデータ配備で編集する。**AI は追記できない**（カスタムメタデータのレコードは通常の作成・更新の経路を持たない） |
| **個人の観点（二次）** | 利用者の作業フォルダのファイル | 承認者ごとの見どころ・会話で貯めた気づき・まだ会社の基準になっていない暫定値 | AI が会話の中で書き足せる |

**会社共通の判定を作業フォルダのファイルだけに置かない [REQUIRED]。** ファイルは置いた本人にしか見えないので、**他の承認者が同じ基準で点検されているかを誰も確認できない**。会社の統制として効かせるものは org の中に置く。逆に、AI が会話で貯めた知識はルールストアへ直接書けないので、**両方が要る**（片方だけでは回らない）。

**読む順序と上書き規則 [REQUIRED]**: org のルールストアを先に読み、次にファイルを読む。**ファイル層は追加だけを行い、ルールストアの判定を緩める向きの上書きをしない**（個人のファイルで会社の統制を外せる形にしない）。厳しくする向きの上書きと、ルールストアに無い観点の追加は認める。食い違ったときは、どちらを採ったかを点検結果に1行で示す。

**ルールストアの型と引き方は意味定義側が示す [REQUIRED]**。どのレコードをどの条件で引くか（対象の指定・有効化の扱い・会社の識別・重大度の段階）は**本 reference に焼き込まない**——配信側が正本で、版差で陳腐化する（`§不変条件` と同じ理由）。共有チェックをレシピの索引から引くのと同じ形で、**会社ポリシーのルールストアも意味定義から型と引き方を取得してから読む**。取得できなかったときは、推測で組んだ条件で引かずに「会社共通層は引けなかった」として層別の1行を出す（当てずっぽうの条件で0件が返ると、未配備と区別がつかない）。

**ルールストアが配備されていない組織では、ファイル層だけで動く。** そのとき「会社共通のポリシーは org 内に無く、個人のファイルだけで判定した」と点検結果に出す——「会社ポリシー未設定」だけでは、共通が無いのか個人のが無いのかを利用者が区別できない。

会社共通ぶんの項目（論理ルールの識別子・対象・判定・しきい値・重大度・承認者ロール・有効化・会社の識別）はルールストアの型が持つので、**同梱の雛形は個人層のぶんだけ**（`templates/承認前チェック_会社ポリシー_雛形.md` を複製して作業フォルダへ置く）。**どちらの層も無ければ標準フレームのみで動く**（フォールバック）。内容例＝利益率の妥当レンジ（業種・商品区分別）／注文書の必須項目（契約形態別）／「類似取引」の定義軸と許容乖離率／承認金額レンジ・与信限度／**原価予実の許容乖離率と警告しきい値**／**実働との突合で許容する差分と、原価の付け先を要さない工数区分**／**単価0を正当とする取引区分（無償提供・サンプル等）**／**兄弟が揃わないまま承認してよい例外（先行承認・分割承認を前提とする運用）と取り残しとみなすまでの猶予**／**集計整合で許容する差・突合から除外する発生源・総額と内訳合計の不一致を許す運用**／**帳票ごとに空欄を許さない項目と空でよい項目・慣行の比較対象**／**原価を持たない商品区分（原価0・粗利率100%が正常なもの）と、実績で確定する取引区分（上流の数量0・金額0が正常なもの）**／**承認までの許容経過日数と、却下後に再申請を待つ日数**／**更新・変更契約の差額分析で遡る期数（既定5期）・前回の引き当て軸・要警告の乖離率**／学習済み注意事項・例外／期間契約の細部（解約通知日数・自動更新既定）。**会社ごとの細かな違いは標準に入れず会社ポリシーへ逃がす**。

**個人層の記入済みファイルは配布物の外に置く [REQUIRED]**。同梱の `templates/` は雛形の置き場で、**配布物は改訂のたびに配信元の内容へ入れ替わる**。記入済みのものをスキルのフォルダへ置くと、更新で消えるか、上書きされたことに気づけない。置き場は**利用者の作業フォルダ**（AI が読み書きしているフォルダ。組織で共有するなら、共有フォルダを全員から同じ名前で見えるようにする）とし、ファイル名は雛形から `_雛形` を外した `承認前チェック_会社ポリシー.md` にする。

**個人層の探し方は「作業フォルダから同名のファイルを探す」1本にする**（会社共通層は org のルールストアを引く）。どちらも見つからなければ標準フレームのみで動く（§標準フレームの実行手順 step2 のフォールバックは、この「探して見つからなかった」場合を指す）。**見つからなかったことを黙って通さず、点検結果に1行を出す。層ごとに書き分ける**（「会社共通のルールストアが org に無い」と「個人のファイルが見つからない」は原因も直し方も別）——置いたつもりで場所が違ったとき、利用者が気づける手掛かりはこれだけになる。同名のものが複数見つかったときは、どれを使うかを利用者に確かめてから読む（新しい方を勝手に採らない）。

### フェーズの切り分け（ロックがかかる前の4フェーズ）

対象は承認だけでなく**ロック（＝以後編集不可）がかかる前**すべて。ロックは**承認ロック**（オブジェクト別に有効/無効を切り替える）・**締めロック**（組織一括）・**無効ロック**（論理削除）の3種で、いずれも確定前が最後の点検機会。対象オブジェクトにどのロックが存在するかは意味定義から引く（`atlas_explain` で対象オブジェクトを引き、更新の判定に示されるロック状態の項目を読む）。ロック中でも更新を許す項目の指定（更新可ホワイトリスト）とロックの有効/無効は組織のカスタム設定で切り替わり、これも同じ判定に示される。フェーズごとに観点の重みを変える。

- **申請前（申請者向け・入力完全性）**: 承認申請を出す前に、承認申請の開始条件（部門設定等）と入力完全性を点検する。レコード単位。
- **承認前（承認者向け・業務妥当性）**: 承認待ちレコードを捕捉し、標準フレーム×会社ポリシー×承認者プロファイル（可変・AIに指示/記憶する承認者ごとの観点）＋職務分掌(f)を重ね合わせて1レポートに統合する。レコード単位。
- **締め前（月次締・意味定義のドメイン名は `financial_record`）**: 締める前に、未確定・未転記・未承認明細・未締め依存を検出する。加えて**母集団単位の不正・異常チェック**（二重支払・structuring・Benford・バックデート）はここで発火する。単一レコードでなく期間内の取引母集団が対象。**承認待ちの滞留・却下後の放置（観点(d)）は承認前で発火したものをここでも再走する**（承認前は単票、締め前は期間内の取り残しの洗い出しとして働く）。
- **無効前（論理削除の前）**: 無効化して安全かの影響チェック。入力完全性でなく、無効化が下流伝票・残高・消込へ及ぼす波及を点検する。

**レコード単位と母集団単位の区別**: 職務分掌・機微マスタ変更などレコード単位のチェックは申請前/承認前で発火。二重支払・structuring・Benford・バックデートなど母集団単位のチェックは締め前／定期監視で発火する（意味定義側でも母集団単位であることが示される場合がある）。**この二分法には両側からの例外がある**——レコード単位でも期間内の取り残しとして意味を持つもの（観点(d) の滞留・却下後の放置）は締め前でも再走し、逆に母集団単位でも締め後に是正できないもの（下記の [REQUIRED] の3つ）は承認前へ前倒しする。

**例外——締め前では遅い母集団チェックは承認前へ置く [REQUIRED]**。次の3つは母集団を読むが、**締めロックがかかってから分かっても戻せない**ため承認前フェーズで発火させる。

- **(g) 承認の網羅性**: 「1件だけ承認されて残りが未承認」は締めに入ってから気づいても取り返せない。対象と同じ業務キーを共有する兄弟の状態は、統計的な母集団監視（Benford・structuring）とは性質が違い、**単票の承認判断に直接効く近傍情報**である。
- **(a) の実働との突合**: 未割当・超過は社員×対象期間という母集団で読むが、承認するかどうかを決める材料そのものなので承認前に出す。
- **(h) の集計整合**: 集計値・予算・残高の不整合と、作成経路の不適合、**および計上日の欠落・期間のずれ**は、**締めロックがかかると是正手段が残らない**（正規経路での作り直しは下流ごと作り直すことになり、締め後にはできない）。対象の配下と上流という近傍を読むだけで、統計的な母集団監視ではない。

判断軸は「母集団かどうか」ではなく、**その情報が単票の承認判断を変えるか**・**締め後に是正できるか**。

**(i) の帳票記載内容も申請前・承認前に置くが、理由の半分だけが共通する。** 読むのは母集団ではなく近傍（同一取引先の直近の同種帳票）で、**締め後に是正できないどころか、承認の直後に外部へ送付されるため承認後の是正が相手の手元に届かない**。是正可能性の観点では最も後戻りできない位置にある。

### 集約スイート（1オブジェクト＝1本）

主要なトランザクションには**申請前/承認前/締め前/無効前を1本に集約した「ロック前チェックスイート」**が1本ずつ用意される（操作フェーズ別に分けない）。**全オブジェクトを網羅する保証はない**ので、未収録のオブジェクトに当たったら §標準フレームの実行手順 のチェックリストで回す。スイートは意味定義側にあり、`atlas_domain_index` で対象オブジェクトのドメインからロック前チェックスイートを選び、`atlas_recipe` で本体を取得する（§標準フレームの実行手順 step1）。スイートは (1) そのオブジェクト自身の入力規則系チェック、(2) 内部統制・設定漏れ・類似取引・差額分析などの**共有チェック**、(3) スイート独自の読み取りチェック、を標準フレーム(a〜f)へ割り付けて束ねる。**観点(g)(h)(i) の割付だけは形が違い、独立した行が担う**——(g) は「業務キー（何を兄弟とみなすか）」、(h) は「集計経路（何と何を突き合わせるか・正規経路の上流はどれか）」、(i) は「帳票項目（どれが帳票に出るか・どれを空にしてよいか）」を示す行で、いずれも束ね単位がオブジェクト固有で共有チェック側に畳めないため、スイートが束ね単位と参照先の名前を1行で示す。共有チェックはドメインを跨いで複数スイートから参照される（利益率異常＝売上系、類似取引単価＝売上・購買両用、3wayマッチ＝調達、職務分掌・設定漏れ・バックデート・二重支払・限度額分割・Benford＝内部統制の横断）。対象は承認/締め/無効ロックを持つトランザクション。マスタは承認前チェックの実益が薄く、スイートは持たないか薄い。マスタ品質の共有チェック（重複・設定漏れ・類似マスタ乖離）は per-object スイートに束ねず、マスタが承認プロセスを持つ場合の点検、または入力支援のマスタ突合検証から単独で発火させる。

## 標準フレームの実行手順（自己完結チェックリスト）

承認前チェックの本体（ロック前チェックスイートと共有チェック）は ti-reference（Atlas）の意味定義にあり、**スイートを引いて回すのが本命経路**。Atlas が未接続・403、または対象オブジェクトのスイートが未収録（`found:false`）のときも、**本チェックリストで自己完結して回せる**（フォールバック）。手順は対象非依存で、見積を第一実装ドメインとする。

**step0 対象の取得**: 見出し＋明細を読む（見積なら見積ヘッダ＋見積明細）。ロック・承認ステータス・論理削除フラグも取る（承認前は承認待ちを承認ワークアイテムSOQLで捕捉）。

**step1 標準フレーム(a)〜(i)を判定**。判定の本体は意味定義から引く。引き方は次の2経路で、どちらも対象オブジェクトの API 名を手掛かりにする。

- **スイートと共有チェック**: `atlas_domain_index` で対象オブジェクトのドメインからロック前チェックスイートを選び、`atlas_recipe` で取得する。スイートが (a)〜(f) への観点割付・**業務キー（観点(g)の束ね単位）**・**集計経路（観点(h)の突合対象と正規経路の上流）**・**帳票項目（観点(i)の対象項目と空欄を許さない項目）**・フェーズごとの重み・参照する共有チェック（内部統制・不正防止・設定漏れ・類似取引・差額分析・利益率異常・網羅性）を持つ。**共有チェックは、スイート本文が挙げる名前をそのまま `atlas_recipe` に渡して引く**（索引のタイトル照合は補助。共有チェックのタイトルは観点名で書かれていることがあり、タイトル照合だけでは同定できない）。**名前の供給源は観点割付の行だけではない [REQUIRED]**——観点(g) の共有チェックは業務キーの行、観点(h) の共有チェックは集計経路の行、観点(i) の共有チェックは帳票項目の行が名前を挙げるので、**観点割付だけを読むと (g)(h)(i) が実行時に不可視になり、黙って落ちる**。スイート本文に現れる共有チェック名はすべて拾う。

  **何が共有チェック名かは、行の種類でなく `atlas_recipe` で引けるかどうかで決める [REQUIRED]**——スイート本文に現れる識別子を行の種類（観点割付・業務キー・フェーズ）で絞り込まず、識別子の形をしたものを一律に `atlas_recipe` へ渡し、**本体が返ったものを共有チェックとして採る**。行の種類で絞る運用は、新しい種類の行が増えるたびに同じ取りこぼしを再生産する（(g) の業務キー行がその実例）。**引けなかった識別子を「無い」と断定しない**——未収録・未接続・403 のいずれかなので、下表のフォールバックへ倒し、引けなかった名前を結果に残す。
- **レコード自身の入力規則**: `atlas_explain` で対象オブジェクト（見出し・明細の両方）を引き、入力規則（validation）の各項目を読む。必須項目・日付順序・条件付き必須の相互整合・品目適格性・転記元マスタは、ここに意味と根拠が入っている。

  **明細は見出しと同じように単独で引ける**（実機確認済み。明細の入力規則がスイート側で一括表記されていても、この経路で個別の意味と根拠まで到達できる）。引くときの作法は2つある。

  - **名前空間を含むフル形の API 名で引く [REQUIRED]**。短い形（名前空間なし）では「該当なし」が返る。**この「該当なし」を「意味定義が無い」と読み違えない**——名前の形が違うだけで、同じ対象が引ける。
  - **入力規則は、返ってきた意味定義の挙動（behavior）の中に validation として並ぶ**。入力規則だけを集めた独立の一覧は無いので、それを探して見つからないことを根拠に「入力規則の意味定義が無い」と断定しない。各 validation は、業務上の意味（何を守るための規則か）と、規則の名前・利用者に出るメッセージを対で持つ。

スイートも共有チェックも引けないとき（未接続・403・未収録）は、下表の判定内容をレコード・明細から自前導出する。

**チェックのレコード名・レシピ名を本 reference に列挙しない**（配信側が正本で、版差で陳腐化する）。索引から引く。

**step2 会社ポリシー層の重ね合わせ**: **org のルールストア（会社共通）→ 作業フォルダのファイル（個人の観点）の順**に読み、利益率レンジ・必須項目・許容乖離率・承認金額レンジ・分掌マトリクス・機微マスタ範囲で判定を上書き／追加する（**ファイル層は緩める向きの上書きをしない**・§会社ポリシー層）。無ければ標準フレームのみ（フォールバック）。**ポリシーはあっても項目が未記入（雛形の `（…）` が残っている）なら、その項目は無いものとして扱い、値を推測して補わない**（0 や既定値で埋めない）。未記入のために実施しなかった会社ポリシー判定があれば、レポート末尾に「会社ポリシー未設定のため未実施: 〜」の1行で示す（判定が黙って消えないようにする）。**ただし標準側に既定を持つパラメータは、未記入なら標準の既定で動く**——差額分析の遡る期数と引き当て軸、承認までの許容経過日数と却下後の再申請待ち日数、バックデートの乖離日数と期末窓がこれにあたる。**既定の値そのものは意味定義側が持つので本 reference に数値を書かない**（版差で陳腐化する）。「未記入なら判定しない」が効くのは**既定を置きようがないもの**＝会社ごとに決めないと意味が定まらないもの（利益率レンジ・承認限度額・分掌マトリクス・機微マスタの範囲・除外区分）に限る。既定があるものまで止めると判定自体が消え、§標準 / 会社ポリシーの境界 の「**数値の提示そのものは会社ポリシーに依存させない [REQUIRED]**」と衝突する。

**step3 出力**: 下記 §出力規律（✅／⚠️＋理由＋承認後の影響・業務言語のみ）で1レポートに統合。⚠️ のみ詳細、✅ は集約1行。

> 本チェックリストは、スイートが引けないとき（未接続・403・未収録）のフォールバックとして残す。**判定内容の正本は意味定義側**で、両者が食い違ったら意味定義側を採る。スイートが引けたときは本チェックリストで観点の抜けを確認するだけにとどめ、同じ判定を二重に走らせない。

## 出力規律（更新系の全出力に効く最上位原則）

- **業務言語のみ**。API名・内部項目名・レコードID・SOQLを利用者向け出力に出さない（内部の結合キーとしてのみ使う）。業務ラベルの供給源は意味定義。
- 出力形式は「✅ 問題なし ／ ⚠️ 要確認 ＋理由 ＋承認後の影響」。承認者が判断に使えない情報は載せない。
- 例＝「粗利率が100%です（原価が入っていない可能性）」／「明細が未確定のため、このまま承認すると売上・請求が生成されない可能性があります」／「入金条件が未設定です。取引先マスタ側にも支払条件が未登録のため、まずマスタ登録が必要です（このままでは次回の取引でも空になります）」／「実績原価が予算を超過しています（超過の所在は人件費）」／「実績はありますが単価が設定されていないため、金額が0で計上されます」／「実働に対して未割当の時間が残っています。どの原価集計単位にも付いていない工数がないか確認してください」／「同じ業務単位に未承認の対象が残っています。この1件だけ承認すると、残りが未承認のまま締めに入ります」／「請求書に印字される備考が空です。同じ取引先の前回の請求書には記載がありました（このまま承認すると、但し書きのない請求書が送付されます）」。
- **「対象外」は4つめの値で、判定不可に混ぜない [REQUIRED]**。帳票を持たない対象での (i) のように、**観点そのものがその対象に成り立たない**ものは「対象外」とする。判定不可＝見るべきなのに見られなかった（要因が消えれば見られる）、対象外＝見る対象がそもそも無い（org の状態が変わっても見ることにならない）。**対象外は ✅ と同じく集約1行に寄せ、⚠️ と同列に詳細を並べない**——毎回「帳票がないので対象外」が並ぶと、実際に見られなかった判定不可が埋もれる。
- **判定不可は「問題なし」と書き分ける [REQUIRED]**。予算未設定・業務キーが解決できない等で判定できなかったものは、✅ に混ぜず「判定不可（理由）」として示す。承認者が「見て問題が無かった」と「そもそも見られなかった」を取り違えないようにする。
- **何を引いて点検したかを証跡1行で残す [REQUIRED]**。承認者向けのレポート本体とは分け、**利用者への応答の作業記録として**、取得したロック前チェックスイートと共有チェックの名前を1行で並べる（業務言語のみの規律はレポート本体に掛かる。証跡は作業の記録なので識別子のままでよい）。**引いた結果として無かったときは「スイート: なし」と明記する**——引いて無かった回と、引かずに済ませた回を区別できるのはこの1行だけで、**本命経路を飛ばしてフォールバックだけで出力しても、出力の形は変わらない**。証跡が無いこと自体が、本命経路を通っていない合図になる。

## 不変条件

承認前チェックに使うレシピは**ロック前チェックスイートと共有チェックに限って**取得する（オブジェクトの意味記述・集計レポート用・入力支援用のレシピと混線させない）。引く前にタイトルが「ロック前チェックスイート」または「共有チェック（承認前チェックの標準観点）」であることを確かめ、集計レポート用・入力手順用のレシピを承認前チェックの根拠に流用しない。

## レポートと監査証跡

承認者ごとに1通へ集約（メンションは実機確認したID形式）。⚠️要確認のみ詳細（理由・該当値・推奨アクション）、✅は「N件・問題なし」と1行集約（アラート疲れ対策）。各行に承認待ちレコードの直リンク。アドバイスは断定でなく支援（「申請者と承認者が同一です。職務分掌を確認してください」等）。**実送信（Slack等）はユーザー承認後**（外部書き込み承認ゲート）。監査証跡は最低1経路（対象レコードのフィードへ要約投稿）を固定する（この投稿履歴が§承認真実源の既報判定の記録先を兼ねる）。
