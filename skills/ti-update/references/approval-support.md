# approval-support — 承認支援（人間の承認を助ける読み取りチェック）

承認支援は両輪のもう片方。承認者・申請者が判断する前に、AIが矛盾・チェックポイントを検査して点検助言を届ける。**承認操作そのもの（承認申請の画面フロー実行・承認/却下）にはAIは一切触れない**。承認支援は**読み取りのみ**でレコードを書かない（書込は入力支援だけ）。

**非対称**: 承認支援は承認プロセスを持つ対象＝主にトランザクションに効く。マスタは承認プロセスがある場合のみ（多くのマスタは承認プロセスを持たないため、マスタは入力支援の突合検証が主で承認支援は薄い）。

## 承認真実源（承認待ちの捕捉）

通知メールはトリガにしない（取得が壊れやすい）。**標準の承認ワークアイテムをSOQLで直接拾う**ことを一次真実源にする。「誰の承認待ちか」と「対象レコード・種別」が確実に取れ、オブジェクト種別で対象プロセスに絞れる。承認ステータス（申請中）は補助。Slack/メール通知は「人が気づく」用。

**申請者の二層性**: 業務上の申請者はレコード側（申請担当者）、システムの申請者はログインユーザ。**職務分掌チェック（申請者≠承認者）はレコード側の申請者を見る**。

定期スケジュール（営業時間中に一定間隔）で「抽出→チェック→レポート」を冪等に実行し、二重報告しない。**既報判定の記録先は監査証跡（対象レコードのフィードへの要約投稿履歴＝下記§レポートと監査証跡で固定する経路）**とし、そこに report 済みの痕跡が残っているレコードは再報告しない（別途の状態ストアを持たず、監査証跡を単一の真実源にする）。

## 承認前/申請前チェックの2層構造（ti-update内包）

承認前チェックは**別スキルにせず ti-update に内包**する。点検フレームは**標準フレーム × 会社ポリシー層**の重ね合わせ。

### 標準フレーム（全社共通・薄い）

会社によらず常に成り立つ点検の方法と、常に異常な普遍ルールだけを持つ。

| 観点 | 標準が検出する普遍ルール |
|---|---|
| (a) 利益率・数値矛盾 | 粗利マイナス／粗利率100%（原価未投入の疑い）／数量×単価≠金額 |
| (b) 類似取引との相違 | 同一商品・得意先・契約形態の過去取引を引いて単価・粗利率・単位・期間を並べる（比較の**手順のみ**標準・警告要否は会社ポリシー） |
| (c) 注文書の抜け漏れ | 得意先・担当・部門・入金条件・計上期間・税区分など、業務上ほぼ普遍の必須項目の欠落 |
| (d) 金額・日付 | 見積↔受注の金額突合／開始日＜終了日／計上期間が契約期間内／税区分未設定（売上が立たない）／自動作成ONのとき承認後に何が生成されるかの予告 |
| (e) 期間契約の契約条件 | 期間契約タイプの明細を含む取引で、契約開始日・契約終了日・自動更新の有無・解約通知期限のいずれかが未入力（検収基準のみの取引では不要） |
| (f) 内部統制・不正防止 | 職務分掌（申請者≠承認者・発注者≠検収者≠支払承認者）／調達3wayマッチ（発注↔検収↔請求）／二重支払・二重請求／承認限度額の分割（structuring）／数値分布の異常（Benford）／機微マスタ（口座・取引先・単価）の変更。バックデート（計上日と実操作日の乖離）は日付観点として(d)で判定し、母集団監視として締め前でも再走する。**普遍的に異常なパターンのみ標準**。閾値・分掌マトリクス・機微範囲は会社ポリシー |

過去取引の引き当て・利益率の算定・母集団の統計検定など**集計の実体は ti-reference のレシピ／共有チェックの意味定義へ委譲**する（`boundaries-and-gates.md`）。ti-update は「何を点検するか（判定の是非）」を持ち、集計手順は持たない。

### 転記由来項目の遡及2段判定（マスタ不備の根本原因検出）

(c) の必須項目のうち**マスタから転記される項目**が空のときは、レコード単体で「未入力」と報告して終わらせず、**転記元マスタまで1段遡って根本原因を切り分ける**:

- **マスタも空** → マスタ未整備が根本原因。レコード側だけ直しても次回の取引でまた空になる旨を明示し、まずマスタ登録を促す。
- **マスタは設定済** → 転記漏れ（作成経路がクライアント側のマスタ自動取得を通っていない等）。再取得・再転記で解消する旨を示す。

判定に使う「どの項目がどのマスタから転記されるか」は意味定義の転記元（provenance）を辿る（`atlas_explain` で対象オブジェクトを引くと、転記される項目とその転記元マスタが意味記述に示される。対応する意味定義が未整備なら、対象マスタを直接読んで空か否かを確認するフォールバックで回す）。マスタ未整備が根本原因のときは、そのまま入力支援の**マスタ不備のその場修正ループ**（`input-support.md`）へ接続できる（検知は承認支援＝読み取り、書込は入力支援）。

### 標準Flow非依存（重要）

過大請求・過大支払・未請求チェック等の標準の通知系Flowは**顧客環境で無効化されうる**（Atlas上も一部が Obsolete）。承認前チェックはこれらのFlowの有効/無効に依存せず、**条件をレコード・明細から自前導出する**。標準Flowを前提にも参照にもしない（再実装もしない）。標準機能が動くための設定漏れ（税区分・入金条件・自動作成フラグ等）は (f) の設定漏れガードとして別に点検する。

### 標準 / 会社ポリシーの境界

標準＝普遍的に異常なパターン＋「標準機能が動かない／後工程が壊れる設定漏れ」＋検知の手順。閾値・限度額・分掌マトリクス・機微マスタの範囲・許容乖離率・「類似取引」の定義軸は**会社ポリシー層**（顧客保守。無ければ標準のみでフォールバック）。会社ごとの違いは標準に入れず会社ポリシーへ逃がす。

### 会社ポリシー層（顧客保守・マークダウン・無ければ標準のみで動作）

業種・会社で変わるパラメータと方針を持つ。標準フレームはこのファイルを読み込んで判定を上書き・追加する（スキル同梱の雛形＝ti-update 直下の `templates/承認前チェック_会社ポリシー_雛形.md` を複製して自社基準に書き換える）。**ファイルが無ければ標準フレームのみで動く**（フォールバック）。内容例＝利益率の妥当レンジ（業種・商品区分別）／注文書の必須項目（契約形態別）／「類似取引」の定義軸と許容乖離率／承認金額レンジ・与信限度／学習済み注意事項・例外／期間契約の細部（解約通知日数・自動更新既定）。**会社ごとの細かな違いは標準に入れず会社ポリシーへ逃がす**。

### フェーズの切り分け（ロックがかかる前の4フェーズ）

対象は承認だけでなく**ロック（＝以後編集不可）がかかる前**すべて。ロックは**承認ロック**（オブジェクト別に有効/無効を切り替える）・**締めロック**（組織一括）・**無効ロック**（論理削除）の3種で、いずれも確定前が最後の点検機会。対象オブジェクトにどのロックが存在するかは意味定義から引く（`atlas_explain` で対象オブジェクトを引き、更新の判定に示されるロック状態の項目を読む）。ロック中でも更新を許す項目の指定（更新可ホワイトリスト）とロックの有効/無効は組織のカスタム設定で切り替わり、これも同じ判定に示される。フェーズごとに観点の重みを変える。

- **申請前（申請者向け・入力完全性）**: 承認申請を出す前に、承認申請の開始条件（部門設定等）と入力完全性を点検する。レコード単位。
- **承認前（承認者向け・業務妥当性）**: 承認待ちレコードを捕捉し、標準フレーム×会社ポリシー×承認者プロファイル（可変・AIに指示/記憶する承認者ごとの観点）＋職務分掌(f)を重ね合わせて1レポートに統合する。レコード単位。
- **締め前（月次締・意味定義のドメイン名は `financial_record`）**: 締める前に、未確定・未転記・未承認明細・未締め依存を検出する。加えて**母集団単位の不正・異常チェック**（二重支払・structuring・Benford・バックデート）はここで発火する。単一レコードでなく期間内の取引母集団が対象。
- **無効前（論理削除の前）**: 無効化して安全かの影響チェック。入力完全性でなく、無効化が下流伝票・残高・消込へ及ぼす波及を点検する。

**レコード単位と母集団単位の区別**: 職務分掌・機微マスタ変更などレコード単位のチェックは申請前/承認前で発火。二重支払・structuring・Benford・バックデートなど母集団単位のチェックは締め前／定期監視で発火する（意味定義側でも母集団単位であることが示される場合がある）。

### 集約スイート（1オブジェクト＝1本）

主要なトランザクションには**申請前/承認前/締め前/無効前を1本に集約した「ロック前チェックスイート」**が1本ずつ用意される（操作フェーズ別に分けない）。**全オブジェクトを網羅する保証はない**ので、未収録のオブジェクトに当たったら §標準フレームの実行手順 のチェックリストで回す。スイートは意味定義側にあり、`atlas_domain_index` で対象オブジェクトのドメインからロック前チェックスイートを選び、`atlas_recipe` で本体を取得する（§標準フレームの実行手順 step1）。スイートは (1) そのオブジェクト自身の入力規則系チェック、(2) 内部統制・設定漏れ・類似取引・趨勢比較などの**共有チェック**、(3) スイート独自の読み取りチェック、を標準フレーム(a〜f)へ割り付けて束ねる。共有チェックはドメインを跨いで複数スイートから参照される（利益率異常＝売上系、類似取引単価＝売上・購買両用、3wayマッチ＝調達、職務分掌・設定漏れ・バックデート・二重支払・限度額分割・Benford＝内部統制の横断）。対象は承認/締め/無効ロックを持つトランザクション。マスタは承認前チェックの実益が薄く、スイートは持たないか薄い。マスタ品質の共有チェック（重複・設定漏れ・類似マスタ乖離）は per-object スイートに束ねず、マスタが承認プロセスを持つ場合の点検、または入力支援のマスタ突合検証から単独で発火させる。

## 標準フレームの実行手順（自己完結チェックリスト）

承認前チェックの本体（ロック前チェックスイートと共有チェック）は ti-reference（Atlas）の意味定義にあり、**スイートを引いて回すのが本命経路**。Atlas が未接続・403、または対象オブジェクトのスイートが未収録（`found:false`）のときも、**本チェックリストで自己完結して回せる**（フォールバック）。手順は対象非依存で、見積を第一実装ドメインとする。

**step0 対象の取得**: 見出し＋明細を読む（見積なら見積ヘッダ＋見積明細）。ロック・承認ステータス・論理削除フラグも取る（承認前は承認待ちを承認ワークアイテムSOQLで捕捉）。

**step1 標準フレーム(a)〜(f)を判定**。判定の本体は意味定義から引く。引き方は次の2経路で、どちらも対象オブジェクトの API 名を手掛かりにする。

- **スイートと共有チェック**: `atlas_domain_index` で対象オブジェクトのドメインからロック前チェックスイートを選び、`atlas_recipe` で取得する。スイートが (a)〜(f) への観点割付・フェーズごとの重み・参照する共有チェック（内部統制・不正防止・設定漏れ・類似取引・趨勢比較・利益率異常）を持つ。**共有チェックは、スイートの観点割付が挙げる名前をそのまま `atlas_recipe` に渡して引く**（索引のタイトル照合は補助。共有チェックのタイトルは観点名で書かれていることがあり、タイトル照合だけでは同定できない）。
- **レコード自身の入力規則**: `atlas_explain` で対象オブジェクト（見出し・明細の両方）を引き、入力規則（validation）の各項目を読む。必須項目・日付順序・条件付き必須の相互整合・品目適格性・転記元マスタは、ここに意味と根拠が入っている。

スイートも共有チェックも引けないとき（未接続・403・未収録）は、下表の判定内容をレコード・明細から自前導出する。

**チェックのレコード名・レシピ名を本 reference に列挙しない**（配信側が正本で、版差で陳腐化する）。索引から引く。

| 観点 | 判定 | 引き方 |
|---|---|---|
| (a) 利益率・数値矛盾 | 数量×単価×期間＝金額／税率×税抜＝税額／粗利マイナス・粗利率100%（原価未投入の疑い） | 金額式は明細の自動計算値と突合。利益率異常はスイートの (a) 割付が指す共有チェック |
| (b) 類似取引との相違 | 同一品目・得意先・契約形態の過去取引を引き、単価・粗利率・単位・期間を並べる | スイートの (b) 割付が指す共有チェック（引けないときは過去明細を直接SOQLで引く） |
| (c) 必須項目の欠落 | 得意先・請求先・納品先・担当・部門・入金条件・収益認識・税区分（販売）の欠落。マスタ転記由来の項目（入金条件・収益認識・単位・販売原因・債権債務・税区分 等）が空なら§転記由来項目の遡及2段判定で転記元マスタまで遡る | `atlas_explain` の入力規則（**支払条件（入金条件）と請求締日・入金期日の整合**・条件付き必須の相互整合・品目適格性・収益認識と期間の整合・取引先区分による相手先制約）。転記元マスタは同じ explain の意味記述が示す |
| (d) 金額・日付 | 有効期限＞発行日／計上期間が契約期間内／見積↔受注の金額突合／税区分未設定（売上が立たない）／自動作成ONなら承認後生成物を予告 | `atlas_explain` の日付順序・適用期間順序の入力規則＋バックデート監視の共有チェック |
| (e) 期間契約の契約条件 | 期間契約タイプの明細で契約開始日・終了日・自動更新・解約通知期限のいずれか未入力（検収基準のみは不要）／更新・変更契約は前回契約との趨勢比較 | `atlas_explain` の契約期間順序の入力規則＋趨勢比較の共有チェック。期間契約か否かは収益認識の方法で判定 |
| (f) 内部統制・不正防止 | 職務分掌／3wayマッチ／二重支払・二重請求／承認限度額の分割／数値分布の異常／設定漏れガード。レコード単位は申請前/承認前、母集団単位は締め前/定期監視 | いずれもスイートの (f) 割付が指す共有チェック（内部統制・調達の各ドメイン）。標準Flow非依存で自前導出する点は共有チェック側でも同じ |

**step2 会社ポリシー層の重ね合わせ**: 顧客ポリシーがあれば利益率レンジ・必須項目・許容乖離率・承認金額レンジ・分掌マトリクス・機微マスタ範囲で判定を上書き／追加。無ければ標準フレームのみ（フォールバック）。**ポリシーはあっても項目が未記入（雛形の `（…）` が残っている）なら、その項目は無いものとして扱い、値を推測して補わない**（0 や既定値で埋めない）。未記入のために実施しなかった会社ポリシー判定があれば、レポート末尾に「会社ポリシー未設定のため未実施: 〜」の1行で示す（判定が黙って消えないようにする）。

**step3 出力**: 下記 §出力規律（✅／⚠️＋理由＋承認後の影響・業務言語のみ）で1レポートに統合。⚠️ のみ詳細、✅ は集約1行。

> 本チェックリストは、スイートが引けないとき（未接続・403・未収録）のフォールバックとして残す。**判定内容の正本は意味定義側**で、両者が食い違ったら意味定義側を採る。スイートが引けたときは本チェックリストで観点の抜けを確認するだけにとどめ、同じ判定を二重に走らせない。

## 出力規律（更新系の全出力に効く最上位原則）

- **業務言語のみ**。API名・内部項目名・レコードID・SOQLを利用者向け出力に出さない（内部の結合キーとしてのみ使う）。業務ラベルの供給源は意味定義。
- 出力形式は「✅ 問題なし ／ ⚠️ 要確認 ＋理由 ＋承認後の影響」。承認者が判断に使えない情報は載せない。
- 例＝「粗利率が100%です（原価が入っていない可能性）」／「明細が未確定のため、このまま承認すると売上・請求が生成されない可能性があります」／「入金条件が未設定です。取引先マスタ側にも支払条件が未登録のため、まずマスタ登録が必要です（このままでは次回の取引でも空になります）」。

## 不変条件

承認前チェックに使うレシピは**ロック前チェックスイートと共有チェックに限って**取得する（オブジェクトの意味記述・集計レポート用・入力支援用のレシピと混線させない）。引く前にタイトルが「ロック前チェックスイート」または「共有チェック（承認前チェックの標準観点）」であることを確かめ、集計レポート用・入力手順用のレシピを承認前チェックの根拠に流用しない。

## レポートと監査証跡

承認者ごとに1通へ集約（メンションは実機確認したID形式）。⚠️要確認のみ詳細（理由・該当値・推奨アクション）、✅は「N件・問題なし」と1行集約（アラート疲れ対策）。各行に承認待ちレコードの直リンク。アドバイスは断定でなく支援（「申請者と承認者が同一です。職務分掌を確認してください」等）。**実送信（Slack等）はユーザー承認後**（外部書き込み承認ゲート）。監査証跡は最低1経路（対象レコードのフィードへ要約投稿）を固定する（この投稿履歴が§承認真実源の既報判定の記録先を兼ねる）。
