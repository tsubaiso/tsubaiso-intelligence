# input-support — 入力支援（＝唯一の書込）

入力支援は ti-update で**唯一レコードを書く**両輪の片方。入力元（Excel/Markdown/PDF）を読み込み、マスタ形式へ整形して登録し、**入力元と一致することまで突合検証**する。トランザクション（販売・購買・在庫・経費・仕訳）とマスタの日常メンテの両方に、同じ型で効く。

## 正規経路（項目更新→自動起動フロー委譲・承認は人間）

中核は「**AIはCRUDと項目更新だけを行い、後続レコードの生成・承認連鎖はパッケージの自動起動フローに委譲する**」こと。標準（ホステッド）Salesforce MCP はレコード操作・参照のツール（create/update/SOQL/describe）は持つが、「フローを起動する」専用ツールを持たない。したがって「承認ボタンを押す」相当はできず、代わりに**フローの引き金になる項目を更新する**ことで後続をパッケージ側に走らせる。

- **フロー種別と起動可否**: 画面フロー＝API/MCPからヘッドレス起動不可（画面要素でユーザー入力待ち）／自動起動フロー＝可（Actions API に POST）／レコードトリガフロー＝可（対象レコードの作成・更新DMLが引き金）。
- **承認の役割分担**: 承認状態は承認ステータス項目（作成中／申請中／承認済／却下）、承認ロックは承認ロック項目（操作項目と状態項目が別）。承認後の後続自動生成の発火条件は「承認ステータス＝承認済 かつ 承認後自動作成フラグ＝true」。**承認操作は人間が行い、AIは承認状態を直接書いて承認を偽装しない**。本書で「承認の引き金」と書く箇所は autoflow を発火させる確定状態を指す。
- **非同期性**: autoflow は中間フラグを立てるだけで実生成はバッチ（非同期）。「更新→直後に後続が揃う」同期前提は成り立たない。締め→売上/請求の起点は納品。
- **項目の意味は推測しない**: 承認ロック等の項目は表示ラベルがオブジェクトごとに意味が異なることがある。**末尾の数字や命名から意味を推測せず**、必ず承認用途の正しい項目をコード（正本・ref明示）で確認して使う。フィールド・フロー・入力規則の実名はコードを一次情報として確認する（このスキルの本文には実名を焼き込まない）。

## 書込基盤＝UI 同等化（明細エディタ保存経路）

明細入力は明細エディタ（LWC）が制御するため、AI直接登録で何が同一で何が外れるかを切り分ける。

- **整合の壁の本体は両経路で同一**: 入力規則（VR）とサーバー側トリガは、UI経路でもAI直接登録でも同一に発火する。外れるのは (i) クライアント側のマスタ自動取得（既定値転記）と (ii) 明細種別ごとのトリガ前提（引当のバイパス等）の2点のみ。
- **本命経路（依存）**: UI同等を最もきれいに得るのは、明細エディタのサーバー処理を AI/MCP から呼べるようにする**サーバーAPI開放**（パッケージへ薄いラッパーを追加）。これは開発チームへ要件として依頼済みで、開放されれば入力支援を暫定経路から本命経路へ寄せられる。
- **暫定経路**: AI側でマスタ取得ロジック（既定値マッピング）を再現し、直接レコードを書いて突合検証する。受注ドメインはこの暫定経路で完走実証済み。パッケージ版差リスクがあるため、本命経路が入れば寄せる。

## 領収書など画像からの経費精算（越境フロー）

領収書画像から経費精算を作るときは、AIが画像を手組みで書き起こさない。標準の流れ:

1. 経費精算原因マスタ（id・名称・説明）を集める。
2. 製品のOCR抽出機能に画像と原因マスタ候補を渡し（**画像も原本バイトをAIの出力トークン経由で運ばず参照渡しで渡す。§添付の受け渡し（規律）**）、支払日・金額（税込）・インボイス登録区分・インボイス番号・原因カテゴリ・支払先・摘要を得る（抽出はAIの手書き起こしでなく製品機能に任せる）。
3. 原因マスタから税区分を確定（インボイス登録事業者は登録用税区分、未登録は未登録用税区分）。**インボイス登録区分など判定に必要な項目をOCR結果から確定できない場合は、推測で埋めず人間へ確認する**（突合の思想と同じ＝穴を隠さない）。
4. 見出しの下に経費明細を作成（金額ロールアップは自動計算に委ねる）。
5. 原本（領収書画像）を証憑として添付（バイトはAI経由させず参照渡し。§添付の受け渡し（規律））。
6. 明細数・合計・各項目が入力と一致するか突合検証し、差分は人間へ提示。承認は人間。

- 各機能（OCR抽出・明細書込・添付）は担い手が分かれることがある（越境フロー）。抽出だけを担う機能と明細を書き込む機能が別システム／別APIのこともある。呼び出し可否は着手時に実機確認し、特定の経路名・システム名を手順に焼き込まない。

## マスタ突合・VR充足の書込前検証（AI側）

品名→マスタId、税区分・収益認識・単位の確定と**VR充足チェック**は**AI側（書込前）**で行い、書込には確定済みIdを渡す。突合は外部文書の表記揺れ・業務判断（適合マスタが無い場合の新規作成可否等）を含むため、決定的処理に載せずAIが担う。

手順:

1. **入力元を構造化抽出**（明細＝品目・数量・単価・税、取引先、自社情報、振込先 等）。
2. **マスタ名寄せ**（意味定義を使用）: 抽出項目を商品・サービス／税区分／取引先マスタへ突合し、API名・Id・規定値を解決。**取引先は得意先/請求/出荷の対象フラグ（VR対象）まで確認**。マスタが無い項目は「登録が必要」として依存グラフで検知。
3. **整形入力**: ヘッダー＋明細を作成。**合算禁止**（明細構成をそのまま再現）。
4. **突合検証**: 登録結果をSOQLで読み戻し、明細数・合計（税抜/税込/消費税）・各明細（品目・数量・単価・税・数量×単価＝金額）・ヘッダー・**承認申請の開始条件充足**が入力元と一致することを検証。不一致は差分表で提示（既定は提示→人間判断）。

冪等性: 作成済フラグ・外部ID項目・マスタの一意キーで二重作成を防止。

**マスタ日常メンテへの適用**: マスタ自体を作る/直す場合も同じ型（名寄せ→整形→VR充足→突合検証）が効く。マスタは承認プロセスを持たないことが多く承認支援は薄いが、**一意制約・参照整合（他マスタへのlookup条件）・入力規則**は書込前にAI側で検証する。

> **VR充足 と 書込前構造ゲート の違い**: 本書のVR充足は「書くレコード自身の入力規則を満たすか」（ti-update が書込前に検証）。`boundaries-and-gates.md` の書込前構造ゲート（作れない工程の検出・参照先の有効性）は ti-reference が正本の機構。字面は近いが射程が異なる。

## マスタ不備のその場修正ループ（承認支援との接続）

承認支援（`approval-support.md §転記由来項目の遡及2段判定`）が、取引の空項目の根本原因を**転記元マスタの未整備**と切り分けたら、そのまま取引の登録・承認を止めず、**その場でマスタを直してから取引に戻る**ループを回す。マスタ不備はトランザクション作成中に頻出するため、検知→その場修正→取引へ戻る、を一連にして摩擦を減らす。

1. **検知（読み取り＝承認支援）**: 「取引の空項目＝転記元マスタが未整備」を業務言語で提示。
2. **不足値の確認**: 発明が要る値（支払条件の締日・入金サイト、収益認識区分 等）は**AIが決めず人間へ確認**する（突合の思想と同じ＝穴を隠さない）。マスタから機械的に定まる値のみAIが埋める。
3. **マスタ修正案の提示（VR充足を先に検証）**: 確認できた値でマスタ更新ドラフトを作り、対象マスタの**入力規則の相互整合を書込前にAI側で充足チェック**する（例：取引先関連情報の債権側支払条件は「サイクルなら請求締日が必須」「請求締日を入れたら入金期日（月）も必須」等、条件付き必須が相互に絡む）。満たせない条件は人間へ確認へ戻す。
4. **承認→書込（入力支援＝マスタ日常メンテ）**: `ti-core references/safety-gate.md`（ドラフト提示＋明示承認＋PIIマスキング）を通し、承認後にマスタを更新する（マスタ日常メンテの射程＝1件〜数件）。承認ロック等がかかっている場合は正規の解除を経てから更新する。
5. **取引へ再転記/再取得・突合**: マスタ更新後、取引側へ値を再取得・再転記し、突合検証で空が解消したことを確認する。

**原則の維持**: 承認支援は読み取りのみで書かない。**書くのは入力支援（本ループのマスタ更新・取引更新）だけ**で、マスタ更新もトランザクション作成と同じ安全ゲート（ドラフト提示＋明示承認）を必ず通す。マスタと取引を同時に大量投入するのは初期一括／移行＝ ti-data-load の射程で、本ループは稼働後の1件〜数件のその場修正に限る。

## 型別切替（安全側）

型は受注ドメインで確立し他対象へ展開する。**API必須は主従親のみ・実境界は入力規則（VR）**。**型別切替**＝定量的に揃う型（工数・スポット等）はAI直接作成可、条件付きVRを入力元だけでは満たせない型（期間情報が要る等）は「人間作成＋AI突合」へ切替。VRや画面フロー開始条件をどうしても満たせないオブジェクト・型はAIが直接作らず、人間作成＋AI突合に切り替える。この判断は他トランザクション・マスタへ展開するときも同じ（対象ごとの確認軸は `process-coverage.md`）。

## 親子一括作成の高レベルI/F（見積等）

外部文書から親（案件/ヘッダー）＋明細を1リクエストで作成し原本添付まで行う高レベルツールのI/F。逐次CRUDの遅延・添付破損の置き換え。**親子1リクエスト作成の経路（親子一括の書込API）とホステッドMCPからの呼び出し可否は要確認**で、当面は直接書込（暫定）で成立させる。金額・ロールアップは入力せずパッケージの自動計算に委ねる。この発想は他の明細付きトランザクション（受注・発注・在庫移動等）へも展開しうる。

## 添付の受け渡し（規律）

原本（Excel/PDF/領収書画像）をレコードに添付する経路。**バイナリをAIの出力トークン経由（base64インライン）で渡すのはLLMの書き起こしで破損するため不可**（実証済み）。

- **規律 [REQUIRED]**: 原本バイトをAIの出力トークン・チャット・ブラウザ経由で運ばない。原本添付は次のどちらかに限る:
  1. **抽出機能に画像を渡す経路の一部として、経路側が原本を証憑として添付する**（画像経費の第一候補＝§領収書など画像からの経費精算（越境フロー））。
  2. **コネクタ間のファイル参照渡し**＝アップロード済みファイルを参照（ContentVersion／ContentDocumentId）でツールへ渡し、レコードにはリンクのみ張る。経費明細の証憑は ContentDocumentLink／ContentVersion で明細に紐づく。
- 参照渡し経路の実在可否は環境依存事実として着手時に実機確認する。呼べないなら添付は人手にフォールバックし、レコード本体の作成と添付を切り離して進める。

## write_action の読み取りと書込計画への利用

書込アクションは散文でなく**意味定義レコードの種別 `write_action` として構造化して読む**（対象・操作種別・目的/前提・ルール〔必須項目・内部統制・冪等性・明細規約〕・作成/更新テンプレ・引き金＋自動副作用・依存順序・自動起動フロー名・画面フロー依存フラグ）。**画面フロー依存フラグ**が true なら「MCP不可・人手or要変換」を計画生成時にユーザーへ明示する。意味定義レコードは種別（意味記述＝既定／`write_action`／`approval_check`）で区別して読み、取得時は種別でフィルタする。物理格納・配信は意味定義サーバー（層0）に native に持ち、本スキルは論理スキーマと利用契約だけを持つ。

## この reference を読む発火点

- org へ書き込む直前は ti-core `references/safety-gate.md`（ドラフト提示＋明示承認＋PIIマスキング）を必ず通す。
- 突合結果を差分表で提示して人間判断を仰ぐ往復は ti-core `references/spec-roundtrip.md`。
- 書込前の構造ゲート（作れない工程の検出・参照先の有効性）は ti-reference の書込前ゲートへ委譲（`boundaries-and-gates.md`）。
