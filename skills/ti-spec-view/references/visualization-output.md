# 可視化出力・鮮度保証・誤誘導防止・段階導入

構造層（`structure-enumeration.md`）と意味層（`overlay-model.md`）を組み立てて、読み手の役割に応じてカスタマイズを見せる。出力・鮮度・誤誘導防止・段階導入をここで定義する。

## 出力形態（初期スコープ＝一覧＋差分）

| 出力形態 | 内容 | 段階 |
|---|---|---|
| カスタマイズ一覧 | 顧客固有のオブジェクト・項目・入力規則・フローを、意味付け・author帰属・確信度・鮮度とともに一覧化 | 第1段（初期スコープ） |
| 標準との差分ハイライト | 標準PSA/IMA構造に対し顧客が追加・変更した箇所を強調 | 第1段（初期スコープ） |
| オブジェクト関係図 | カスタムオブジェクトを含む関係の図示 | 第2段以降 |
| プロセス影響の説明 | 入力規則・フローが「どの操作の・どの段階で・何を起こすか」を観測可能な挙動として記述 | 第2段以降 |

**トレードオフの明示 [REQUIRED]**: 第1段は「何があるか・何が標準と違うか」まで。**入力規則・フローが「何を起こすか」（ブラックボックス化の核心）は第2段以降に持ち越す**。第1段だけではカスタマイズの存在と差分は見えるが挙動の業務的意味は出ない。読み手が初期スコープの到達点を誤解しないよう明記する。

**出力規律（全形態共通）**: 利用者向け出力にAPI名・SOQL・レコードIDを出さず業務語へ翻訳し、レコード・カスタマイズはリンク化する。author帰属・確信度・鮮度を各項目に常時併記する。カスタマイズ一覧を技術ドキュメントとして出す場合の源データ項目のAPI名は管理者・コンサル向けに限る（利用者向けの帳票・回答とは射程が別）。

## 鮮度保証（陳腐化防止・既存ドリフト検知の再利用）

当社が初期に意味付けを author するため、顧客が構造を変えた後も古い意味付けが残ると可視化が誤誘導する。**新しい監視サブシステムを作らず、既存のドリフト検知を再利用**する。

> ドリフト連動の自動 stale 化は段階導入の第3段（下記「段階導入」）。第1〜2段では鮮度更新は再確認・手動運用で、本節の「自動更新」は第3段の到達形として読む。

- **stale化のトリガ**: ドリフト検知が意味付けの「対象API名」を欠落（missing）または版差（version_diff）で報告したら、鮮度状態を「構造変化後未確認（stale）」へ自動更新する。突合キーは対象API名（実行時合成と同一キー）。
- **鮮度3値**: 未author（構造はあるが意味付けが無い・機能網羅ゲートが検出）／確認済／構造変化後未確認（stale）。対象構造の削除も missing として stale に含め「対象が見当たらない」を併記し、論理削除のみ人手判断とする。**未authorは意味付けレコード不在から出力時に合成する表示値（レコードには保存されない）で、確認済／staleは意味付けレコードの保存属性**。
- **役割分担**: 機能網羅ゲート＝意味付けが**欠けている**（未author）を検出／ドリフト検知＝意味付けが**古くなった**（stale）を検出。両者は別軸で、可視化は両方を表示する。
- **確認済への復帰**: 当社または顧客が再確認・更新したら「確認済」へ戻し、最終確認日・対象構造の版識別を更新する。
- **実効性の依存**: ロジックはorg非依存で完結するが、実効性（入力規則・フローの構造変化を実際に stale として拾えるか）は `structure-enumeration.md` の機械列挙網羅率に依存する。取得できていない種別は鮮度保証の射程外。

## 誤誘導の防止と責任所在

当社推定の意味付けを「確定仕様」と顧客が誤認すると誤った業務判断につながる。**意味層の属性と表示規律で担保し、追加の仕組みは作らない**。

- **author帰属の明示**: 各意味付けに「当社推定」か「顧客記述」かを必ず表示する。当社推定は**推定である旨**を明示し、断定的な権威付けを付さない。
- **確信度ラベル**: 高/中/低。当社推定の初期値は中以下、顧客の確認・追記で上昇、stale化したら再確認まで据え置き。
- **確定仕様誤認の防止規律**: 当社推定はサポート補助の解釈で、業務仕様の最終確定・責任は顧客にある旨を出力へ明記する。
- **訂正経路・是正フロー**: 顧客が編集・コメントで訂正できる導線を用意し、訂正レコードは author帰属を「顧客記述」へ更新する。誤りは版として旧記述を残し（監査）、stale と同じ再確認導線で通知する。
- **責任分界は契約へ [REQUIRED]**: 可視化の表示（「最終責任は顧客」）は当社の表明であって、当社推定が誤って顧客が損害を被った場合の免責射程・誤author時の責任分界を確定しない。これは可視化では閉じず契約・利用規約で担保する（`ip-governance.md` の契約終了と同じく法務連動）。

## 段階導入と二層モデル

- **段階導入**: 第1段＝構造層の可視化（一覧＋差分・author帰属を最初から組込・当社authorの最小セット）／第2段＝意味付けの拡充と当社・パートナーの許可つき閲覧経路（軸2維持）・関係図／第3段＝ドリフト連動の鮮度自動化。
- **二層モデル [REQUIRED]**: 道具と型（構造列挙の経路・意味層のデータモデルと鮮度3値・author帰属/確信度の表示規律・機能網羅ゲートとドリフト検知のロジック・出力フォーマット）は**標準**、あてはめ（顧客固有カスタマイズの構造・意味付けの中身・確信度の値・閲覧許可の顧客ごとの担保・ブランド）は**顧客ごとに都度生成**。取り違えない。
- **評価軸**: 可視化の十分性は「正しい実行（SOQLが組めるか）」ではなく**「理解の達成（ブラックボックス化が解消されるか）」**で測る。
