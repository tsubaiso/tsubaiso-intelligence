# 可視化出力・鮮度・誤誘導防止・段階導入

構造層（`structure-enumeration.md`）と意味層（`overlay-model.md`）を組み立てて、読み手の役割に応じてカスタマイズを見せる。出力・鮮度・誤誘導防止・段階導入をここで定義する。

## 出力形態（初期スコープ＝一覧＋差分）

| 出力形態 | 内容 | 出力の段階 |
|---|---|---|
| カスタマイズ一覧 | 顧客固有のオブジェクト・項目・入力規則・フローを、意味付け・書き手・確信度（推定のみ）・鮮度とともに一覧化 | 第1段（初期スコープ） |
| 標準との差分ハイライト | 標準PSA/IMA構造に対し顧客が追加・変更した箇所を強調 | 第1段（初期スコープ） |
| オブジェクト関係図 | カスタムオブジェクトを含む関係の図示 | 第2段以降 |
| プロセス影響の説明 | 入力規則・フローが「どの操作の・どの段階で・何を起こすか」を観測可能な挙動として記述 | 第2段以降 |

**トレードオフの明示 [REQUIRED]**: 第1段は「何があるか・何が標準と違うか」まで。**入力規則・フローが「何を起こすか」（ブラックボックス化の核心）は第2段以降に持ち越す**。第1段だけではカスタマイズの存在と差分は見えるが挙動の業務的意味は出ない。読み手が初期スコープの到達点を誤解しないよう明記する。

**出力規律（全形態共通）**: 利用者向け出力にAPI名・SOQL・レコードIDを出さず業務語へ翻訳し、レコード・カスタマイズはリンク化する。書き手（顧客記述／推定）と出所（この組織の説明欄・ヘルプテキスト・意味付けの型）を各項目に併記し、推定には確信度を添える。カスタマイズ一覧を技術ドキュメントとして出す場合の源データ項目のAPI名は管理者・コンサル向けに限る（利用者向けの帳票・回答とは射程が別）。

**意味付けの読み方（いまの段階）**: 意味付けはti-core `references/customization-meaning.md` の読み方で説明欄・ヘルプテキストから読む。本文の無いメタデータは「意味付けなし」とし、AIが推測した本文を推定として添え、確認一覧に加える。

## 鮮度（最終更新日時と確認日の比較）

ツバイソの導入担当・パートナーが初期に意味付けを書くため、顧客が構造を変えた後も古い意味付けが残ると可視化が誤誘導する。**鮮度は組織のメタデータの最終更新日時と、意味付けの確認日を比べて判定する。** 共通の意味定義のドリフト検知は使わない（意味付けの対象は顧客の組織のメタデータで、その変更は組織の最終更新日時で捉える）。

> 鮮度の判定と表示は、意味付けの型を読む段階（下記「段階導入」のPhase 2）から行う。**Phase 1（説明欄・ヘルプテキストを読む段階）では鮮度を表示しない。** 本節はPhase 2で加える動作として読む。関係するメタデータでの判定、一部が削除されたときの扱い、最終更新日時を読めないときの「鮮度未確認」、鮮度を判定しない意味付けは、Phase 2の改訂で加える。

- **表示する値**: 意味付けなし（構造はあるが意味付けが無い）／確認済み／構造変化後未確認／対象が見当たらない。
- **判定**: 比べる単位は組織のタイムゾーンでの日付で、メタデータの最終更新日が確認日より**後**のときだけ構造変化後未確認とする（同じ日は確認済み）。入力規則・フローの意味付けは、その入力規則・フロー（実装しているメタデータ）の最終更新日時で判定する。
- **パッケージのメタデータは最終更新日時と比べない**（アップグレードのたびに変わるため）。組織から削除されたときだけ「対象が見当たらない」と示す。標準のメタデータは鮮度を判定しない。
- **制約**: 最終更新日時からは、説明欄が変わったのかほかの定義が変わったのかを区別できない。同じ日のうちの変更も検知できない。
- **確認済みに戻す手順**: 構造変化後未確認の意味付けは確認一覧に加え、顧客の管理者の再確認で確認日を改める。

## 誤誘導の防止と責任所在

推定の意味付けを「確定仕様」と顧客が誤認すると誤った業務判断につながる。**意味層の属性と表示規律で担保し、追加の仕組みは作らない**。

- **書き手の明示**: 各意味付けに「顧客記述」か「推定」かを必ず表示する。推定は**推定である旨**を明示し、断定の形で示さない。
- **確信度ラベル**: 高/中/低。**推定にのみ付ける**。顧客の管理者が本文を確認すれば顧客記述になり、確信度は付けない。
- **確定仕様誤認の防止規律**: 推定は、サポートのためにAIや導入担当が推し量った解釈で、業務仕様の最終確定・責任は顧客にある旨を出力へ明記する。
- **訂正経路**: 顧客の管理者は確認一覧への回答で意味付けを確定・修正する（ti-core `references/customization-meaning.md`）。回答した意味付けは顧客記述になる。
- **食い違いの扱い**: 同じ事柄について内容の食い違う意味付けが複数あるとき（説明欄とヘルプテキストが食い違うときを含む）は、どれも断定の形で使わず、出所つきで並べる。
- **責任分界は契約へ [REQUIRED]**: 可視化の表示（「最終責任は顧客」）は当社の表明であって、推定が誤って顧客が損害を被った場合の免責の範囲・誤った意味付けの責任分界を確定しない。これは可視化では閉じず契約・利用規約で担保する（`ip-governance.md` の契約終了と同じく法務連動）。

## 段階導入

| 意味付けの段階 | できること |
|---|---|
| Phase 1（いま） | 説明欄・ヘルプテキストを読み、意味付けとして一覧・応答に使う。本文の無いメタデータと推定・書き手不明の説明欄を確認一覧に載せ、顧客の管理者の回答を受け取る（回答は確認一覧に残す）。鮮度は表示しない |
| Phase 2 | 意味付けの型を含むtb_PSAの版を導入した組織で、意味付けの型を読む。説明欄・ヘルプテキストの取り込みと、確認一覧の回答の登録を行う。鮮度を判定・表示する |
| Phase 3 | 顧客が追加したメタデータを意味付けの型のレコードと突き合わせ、カスタマイズ一覧（意味付けの型と突き合わせた一覧）として、標準との差分・意味付けの無いメタデータとともに表示する。§出力形態の第1段のカスタマイズ一覧は、Phase 1から説明欄・ヘルプテキストの意味付けを付けて表示する。Phase 3で変わるのは意味付けの出どころ |

- **道具と型は標準・あてはめは顧客ごと [REQUIRED]**: 道具と型（構造列挙の経路・意味付けの読み方・書き手と確信度の表示規律・鮮度の判定・出力フォーマット）は**標準**、あてはめ（顧客固有カスタマイズの構造・意味付けの中身・確信度の値・閲覧許可の顧客ごとの担保・ブランド）は**顧客ごとに都度生成**。取り違えない。
- **評価軸**: 可視化の十分性は「正しい実行（SOQLが組めるか）」ではなく**「理解の達成（ブラックボックス化が解消されるか）」**で測る。
