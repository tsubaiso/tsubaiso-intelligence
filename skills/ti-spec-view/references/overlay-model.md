# テナント依存の意味層とデータモデル・IP保護2軸

構造層（`structure-enumeration.md`）は「何があるか」を出すが「業務的に何を意味するか」は出ない。意味付けは顧客固有＝テナント依存で、共通の意味定義（テナント非依存IP）とは**物理的に別系統**に持つ。この意味層をここで管理する。

## 不変条件（共通IPとの分離） [REQUIRED]

- **共通の意味定義（テナント非依存IP）**はサーバー基盤側に保持し、顧客へ配らない。
- **顧客固有の意味付け（テナント依存）**は顧客の情報として扱い、共通IPとは**別の物理ストア**に持つ。
- **実行時結合**: 可視化は「構造＋共通意味＋顧客固有の意味付け」をAPI名で実行時に重ねて構成する。
- **非焼込**: 可視化ビューに共通IP本体（意味定義の説明文）を顧客org内へ永続化しない。保存するのはAPI名骨格＋顧客固有の意味付けのみで、共通IP由来の説明文は含めない。
- **昇格は抽象パターンのみ**: 顧客固有の値・命名・実データに紐づく意味付けは共通IPへ昇格しない（`ip-governance.md`）。

## 二層の置き場

顧客固有の意味付けは編集頻度が高い（会話駆動・顧客追記）ため、構造マップ（読み取り専用・低頻度）と同じ置き場設計をそのまま適用しない。二層で扱う。

| 層 | 置き場 | 性格 |
|---|---|---|
| 編集層 | 顧客org内のカスタムオブジェクト | 高頻度upsert（当社author＋顧客追記） |
| 確定層 | スナップショット（メタデータ扱い） | 低頻度・読取。配備は ti-metadata の機構へ委譲（`ip-governance.md`） |

確定層はメタデータ扱いで、通常のレコード書込（REST/DML insert）では作成できずメタデータAPIのデプロイになる（プラットフォーム制約・実証状態は開発側の裏取り正本に従い、内部の型名・エラーコードは本文に焼き込まない）。

## 編集層のデータモデル（1カスタマイズ＝1レコード・初期運用）

編集層は顧客org内のカスタムオブジェクトに1カスタマイズ＝1レコードで持つ。初期運用で必須の属性:

| 属性 | 役割 |
|---|---|
| 対象API名（オブジェクト/項目/入力規則/フローの識別） | どのカスタマイズへの意味付けか。実行時合成とドリフト突合のキー |
| 対象種別（object / field / validation_rule / flow） | 構造層メタデータの種類 |
| 意味付け本文 | 業務的に何を意味し何を起こすかの説明 |
| author帰属（当社推定 / 顧客記述） | 誰が書いたか。確定仕様誤認の防止 |
| 確信度（高 / 中 / 低） | 意味付けの確からしさ |
| 鮮度状態（確認済 / 構造変化後未確認） | 陳腐化の表示（`visualization-output.md`） |
| 最終確認日・対象構造の版識別 | ドリフト突合・鮮度判定の基準 |
| 版・更新者・更新日時 | 高頻度編集の競合解決・監査 |

- 鮮度状態の保存値は確認済／構造変化後未確認（stale）の2値。未authorは意味付けレコードが存在しない状態で、レコード属性としては保存されず、構造の存在と意味付けレコード不在から出力時に合成する（`visualization-output.md`）。
- 昇格状態は初期運用では持たない（共通IPへの昇格を仕組み化する将来フェーズで追加）。
- 物理項目名・型はパッケージ化時に確定し、標準機能（カスタムオブジェクト＋カスタム項目）で表現できる範囲に収める。
- 高頻度編集（当社author＋顧客追記）の版管理・同時編集の解決規則は運用設計時に詰める。

> **author区分の拡張（確認事項）**: 判断層からの記録プロトコル（`ip-governance.md`）は author に「実際のビルド主体（提供側／顧客／パートナー）」を求める。現状の author区分は当社推定／顧客記述の2値で、提供側・パートナーを表す値の追加は未確定。この拡張は `visualization-output.md` の表示規律（提供側・パートナー author の表示）の追随も伴うため、パッケージ化時にまとめて確定する。author定義の正本は本ファイルなので、拡張の確認事項もここで管理する。

## IP保護2軸（可視化の必須前提） [REQUIRED]

可視化は次の2軸を必ず守る。片方だけを見て「逆向きだから安全」と結論しない。

- **軸1: ツバイソIPの外流出の不在** — 共通の意味定義を顧客へ渡さない。可視化は顧客固有の意味付けと構造を扱い、共通IPを顧客可視範囲に持ち込まない（非焼込）。
- **軸2: 当社（サーバー側）は顧客データを受け取らない** — 当社・パートナーが顧客カスタマイズを閲覧する経路では顧客org構造データが当社側に渡りうる。閲覧データを当社環境に**非永続＝都度取得・非滞留**で保つ。

軸2の担保（閲覧経路・当社が編集層へ書く経路・意味付けの共通化）は `ip-governance.md` で扱う。**当社が軸2を保ったまま編集層へ書けるか**は接続アプリのスコープ・許可担保と一体の未実証事項で、実装時に出典つきで確定する。

**書込前構造ゲートの射程 [注意]**: 参照スキル（ti-reference）が持つ書込前の構造ゲート（作れない工程の検出・参照先の有効条件チェック）は、意味層レコードが自動作成の連鎖を持たない独立カスタムオブジェクトへの素直な upsert では空振り＝適用対象外。編集層upsertの安全は ti-core の安全ゲート（承認・PIIマスキング）で担保する。両ゲートは射程が別で、取り違えない。
