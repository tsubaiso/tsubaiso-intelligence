# 昇格ガバナンス・閲覧経路・意味付けの記録・契約終了・判断層が実装したカスタマイズの記録

意味層の共通化（昇格）、当社・パートナーの閲覧経路、意味付けの記録（ti-metadataの配備に含める）、契約終了時の扱い、判断層（ti-lifecycle）が実装したカスタマイズの記録を扱う。いずれもIP保護2軸（`overlay-model.md`）を崩さないことが前提。

## 意味付けの共通化（昇格）ガバナンス

同種カスタマイズが複数顧客に現れたとき、当社サポート効率のため意味付けを共通IPへ再利用したくなる。だが顧客固有情報を共通IPへ持ち込むと分離の不変条件が崩れる。

- **昇格可否の判定基準 [REQUIRED]**: 顧客固有の値・命名・実データに紐づく意味付けは昇格不可（意味層に留める）。**顧客固有要素を捨象した抽象パターンのみ共通IPへ昇格可**。
- **初期運用は人手の随時運用**: 顧客数が少ないうちは当社が随時、人手で行う例外運用（横断検出・ステートマシン・再昇格ガードは作らない）。抽象化判定は人手レビューを最終ゲートに置き、判定者を明確にする。
- **軸2の担保（人手運用の注意）**: 複数顧客の意味付けを当社環境へ集約・保存して突き合わせる形は取らない。各顧客orgでの個別確認に留め、手元に持ち出すのは抽象化後のパターンのみ。
- **誤昇格時の戻し（revert）**: 共通IPに顧客固有要素が混入したと判明したら、当該エントリを撤回し、配布済み意味定義への影響範囲を特定して是正（再ビルド・再配布）、抽象化チェックリストへ事例追加。
- **将来フェーズ**: 顧客数増で手運用が回らなくなったら、昇格状態のレコード管理・抽象指紋のみの横断検出（軸2を保つ）・再昇格ガードを設計する。自動化のしきい値は将来フェーズで定める。

## 当社・パートナーの閲覧経路（非永続）

閲覧者の優先順位: 顧客（自社org内・一次・追加許可不要）／当社サポート・コンサル（二次・顧客許可）／パートナー（二次・顧客許可）。

- **閲覧経路**: 当社・パートナーは**スコープを限定した接続アプリで顧客orgへ接続**し、**閲覧データを当社環境に非永続（都度取得・非滞留）**で保つ（軸2維持）。クレデンシャル借用は不採用、顧客実行結果の受け渡しは受動的で当社の能動的サポートに不足。
- **閲覧限定ペルソナ**: サポート・外部コンサルは顧客orgの常設ロール（Profile／権限セット）を持たず、スコープ限定接続アプリでti-spec-viewの閲覧のみを行う（org常設権限とは別のサーバー側経路）。閲覧に留まり、書込・カスタマイズの権限は持たない。なお、この**常設閲覧経路（非永続・閲覧のみ）と、管理者の権限でti-metadataの配備に意味付けを含めて書く経路は別**で、両立する（矛盾ではない）。
- **「顧客許可」の担保方式**は未確定（権限セット／接続アプリのスコープ／共有設定のどれで担保するか）。閲覧経路の実装時に出典つきで確定する。

## 意味付けの記録（ti-metadataの配備に含める）

意味付けの型のレコードはメタデータの配備でしか書けない。記録の機構（取得→差分→検証→反映）は本スキルが持たず、ti-metadataの中核ループに含める。

- **本スキルの射程**: 意味付けの中身（`overlay-model.md` のデータモデル）と、読み方・表示まで。配備の実行機構はti-metadata。
- **いまの段階（Phase 1）**: 意味付けの型はまだ組織に無い。ti-metadataは新しく作成するメタデータの説明欄に本文と属性行を設定し、意味付けの型に記録する予定の意味付けを確認一覧に加える（ti-core `references/customization-meaning.md`）。

## 契約終了時の扱い（方針・確定は契約連動）

- 顧客org内の意味付けは顧客資産として顧客側に残る（当社が削除する性質ではない）。
- 当社側に一時取得分・処理ログが残る場合は契約終了時の削除義務を明記し、削除対象・期限を契約条項と運用手順で定める（軸2の事後保証）。
- 解約で当社の閲覧用接続アプリを失効させ、当社・パートナーの閲覧経路を断つ。顧客org内の意味付けは残るが、共通IPとの実行時合成が止まるため共通IP由来の説明は表示されなくなる。
- 削除対象範囲・保持期間・接続アプリ失効手順は、閲覧経路の許可担保方式の確定を前提に契約・法務と連動して確定する。

## 判断層（ti-lifecycle）が実装したカスタマイズの記録

ti-lifecycleが「どう実装するか」を決めて配備したカスタマイズは、記録を残さないと、手を加えた範囲が大きいカスタマイズほどブラックボックス化する。これは本スキルの目的に反する。

- **記録の契機は配備そのもの**: 意味付けはti-metadataの配備に含めて記録する。配備の成功を待って別の操作で記録する形は取らない（配備が失敗すれば意味付けも組織に入らず、組織に実在しないカスタマイズの記録は残らない）。
- **向き**: ti-lifecycle → ti-metadata → 意味層。ti-spec-viewは記録・可視化層として受け身で、判断はしない（層分担を崩さない）。
- **書き手**: 顧客の管理者が配備の承認で本文を確認すれば顧客記述、確認していなければ推定（ツバイソの導入担当・パートナーが配備した場合を含む）。確信度は推定にのみ付ける。推定で記録した意味付けは確認一覧に加え、顧客の管理者の回答を求める。
- **記録内容・粒度**: 対象・区分・意味付け本文（実装意図＝なぜ・業務要件）を初期値にし、以後は顧客の管理者の回答で補い、改める。1つの判断が複数のメタデータを生む場合は、それぞれのメタデータの意味付けを持ち、共通の要件は本文で結ぶ。
- **既存の意味付けを上書きしない**: 他者（顧客等）が既に記した意味付けは、顧客の管理者の確認なしに書き換えない。既存のメタデータの説明欄・ヘルプテキストも変えずに配備する（手順はti-metadata）。
- **誤認防止**: 提供側主導のカスタマイズの記録は、確定仕様と誤認させない表示規律（`visualization-output.md`）に従う。
