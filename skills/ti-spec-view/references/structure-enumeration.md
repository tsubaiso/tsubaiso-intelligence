# 構造層メタデータの取得・列挙

顧客固有のカスタマイズを可視化する第一歩は、org に実在する構造メタデータを機械列挙し、標準構造との差分の素材を作ること。**構造の実在と定義だけを扱い、業務的な意味付けは意味層（`overlay-model.md`）が持つ**。

## 取得経路の使い分け

構造の種類で取得経路が分かれる。抽象的に「メタデータを取る」で済ませず、型ごとに正しい経路を使う。

| 対象 | 取得経路 | 注意 |
|---|---|---|
| カスタムオブジェクト・カスタム項目・関係・レイアウト | sObject describe | 構造は describe で取得できる（意味定義・構造で実証済みの経路） |
| 入力規則・フローの実在と定義 | Tooling/Metadata API（`ValidationRule`／`Flow` 等） | describe では取れない。定義メタデータ（構成要素）を機械列挙する |

- 取得するのは「どんなオブジェクト・項目・入力規則・フローが**存在し**、どんな**構成要素**か」まで。「その入力規則・フローが業務的に何を起こすか」は意味層が受け持つ（構造と意味の分担）。
- 標準PSA/IMA構造に対する追加・変更が「標準との差分」の素材になる（`visualization-output.md` の差分ハイライト）。

## 両パッケージの後付けを捕捉する [REQUIRED]

PSA と IMA は双方向にオブジェクト・入力規則・フローを後付けで拡張する。**片方のパッケージ由来だけを数えて「これで全部」と結論しない**。列挙は両パッケージの後付けを捕捉して初めて完全性が成り立つ。片方だけの列挙は網羅漏れになる（両パッケージ併存環境の判断完全性）。

## 網羅率は「取れるか」でなく「漏れなく取れるか」

論点は「入力規則・フローが取れるか」ではなく、**機械列挙の網羅率**（列挙が実機の全件を漏れなく拾えるか）。この網羅率は実機で実証済みだが、次の性質を持つ。

- **実証は検証org・特定リリース版に依存する**: 網羅率の実測は検証環境と版に紐づく。検証orgの失効後は org 更新・代替orgでの再実証が要る。実測の数値・org名・版・再現手順は開発側の検証記録（裏取り正本）にあり、本 reference には数値を焼き込まない。
- **鮮度保証の射程は網羅率に従属する**: 機械列挙が拾えないメタデータ種別は、鮮度保証（`visualization-output.md`）の対象外になる。「設計が完結すること」と「機能が全カスタマイズに効くこと」は別。取得できていない種別は可視化から漏れる旨を明示する。

裏取りは開発側の検証記録とコードを正本とし、ref を明示して確認する（`code-investigation`・`salesforce-platform-capabilities`）。プラットフォーム制約（画面フローのヘッドレス起動不可 等）は実機実証済だが更新で緩和されうるドリフト対象のため、本文では実証状態を注記した**プラットフォームの型**として書き、内部API名・実測値は出さない。

## 読取の位置づけ

構造列挙は読取で、org への書込を伴わない。可視化に添えるレコード実データの参照解決・SOQL実行が要るときは ti-reference の能力を参照ファイル経由で借りる（本スキルは構造の**列挙**まで、レコードの検索実行は ti-reference）。
