# 顧客カスタマイズの意味付け（customization-meaning）

> **ベータとして先行提供している機能です。** 記述が変わることがあります。扱いは `beta-status.md` を参照してください。**ti-coreでベータなのは本referenceと `support-escalation.md` だけで、他の共通機構は正式提供です。**

顧客が組織へ追加したメタデータが業務上何を意味するかを、応答に使うときと、顧客の管理者に確認を求めるときの共通の規則。**規則の正本は本書だけで、ti-reference・ti-update・ti-spec-view・ti-metadataは書き写さずに本書を参照する。**

| 用語 | 意味 |
|---|---|
| 顧客が追加したメタデータ | 名前空間の無い、カスタムのオブジェクト・項目（API名が `__c` で終わるもの）と、名前空間の無い入力規則・フロー。標準のオブジェクトに顧客が追加した項目・入力規則を含む。標準のオブジェクト・項目そのものは含まない |
| 管理者 | 組織のカスタマイズ権限を持つ利用者。顧客の組織でこの権限を持つツバイソの導入担当・パートナーを含む |
| 顧客の管理者 | 管理者のうち、顧客の社員。組織の権限では管理者のうちの誰が顧客の社員かを区別できないため、AIは本人に確かめる（§属性行） |

## いまの段階（Phase 1）

意味付けの格納先は、tb_PSAに同梱するカスタムメタデータ型（以下「意味付けの型」。tb_PSA 7.1で同梱する予定）である。型名・項目名はツバイソの開発チームの詳細設計で決まる。型名・項目名が決まり、本書を改訂するまでの段階をPhase 1とし、スキルは次のように動く。

| すること | しないこと |
|---|---|
| 説明欄とヘルプテキストを読んで応答に使う（§読み方） | 意味付けの型のレコードを読む・書く（型が組織にあっても、本書を改訂するまでは読まない） |
| ti-metadataで新しく作成するメタデータの説明欄に、本文と属性行を設定する（§属性行） | 説明欄・ヘルプテキストの本文を意味付けの型へ取り込む |
| 確認一覧を作り、顧客の管理者の回答を受け取る（§確認一覧） | 回答を組織に登録する（回答は確認一覧に残し、意味付けの型を含むtb_PSAの版を組織に導入した後に登録する） |
| — | 意味付けの鮮度（構造変化後未確認）を判定・表示する |

## 読み方 [REQUIRED]

**いつ読むか**: 顧客が追加したメタデータの意味、またはツバイソのパッケージ・標準の項目をこの組織でどう使っているかを応答に使う瞬間（業務上の意味を説明する、点検・判定の根拠にする、抽出の条件に使う）。応答に使うメタデータごとに、その説明欄とヘルプテキストを読む（パッケージ・標準の項目はヘルプテキストだけ）。

**取得経路**:

| 対象 | 説明欄 | ヘルプテキスト |
|---|---|---|
| 項目 | 通常のSOQLで `FieldDefinition` の `Description`（オブジェクトのAPI名で絞り、1つのオブジェクトにつき1回の照会で読む） | オブジェクトのdescribeが返す `inlineHelpText` |
| オブジェクト | Tooling APIの `CustomObject` の `Description` | — |
| 入力規則 | Tooling APIの `ValidationRule` の `Description` | — |
| フロー | Tooling APIの `Flow` の `Description`。有効なバージョン（無ければ最新のバージョン）を読む | — |

> - **依存事実**: 上表の4経路で説明欄（`Description`）を取得できること
> - **実証日**: 2026-10-25（検証組織で4経路ともエラーなく照会でき、項目とオブジェクトは本文が返ることを確認）
> - **実証コマンド**: `sf data query -o {組織} -q "SELECT QualifiedApiName, Description FROM FieldDefinition WHERE EntityDefinition.QualifiedApiName = '{オブジェクト}'"`、Tooling APIは同じコマンドに `-t` を付け、`SELECT DeveloperName, Description FROM CustomObject`／`SELECT ValidationName, Description FROM ValidationRule`／`SELECT Definition.DeveloperName, Status, Description FROM Flow WHERE Status = 'Active'`

**読んだ本文の扱い**:

| 読んだもの | 扱い |
|---|---|
| 属性行の無い説明欄 | 顧客記述・確認日なしとして応答に使う |
| 顧客が追加した項目・標準項目のヘルプテキスト | 顧客記述・確認日なしとして応答に使う |
| 「書き手=顧客記述」の属性行が付いた説明欄 | 顧客記述として応答に使い、確認日を添える |
| 「書き手=推定」の属性行が付いた説明欄 | 推定であることと確信度を添え、断定の形にしない。その本文を、確認一覧の「本文の案」として加える |
| 最後の行が `[TI:` で始まるが、属性行の書式どおりに解析できない説明欄（書き手不明） | 書き手不明と添え、断定の形にしない。その本文を、確認一覧の「本文の案」として加える |
| ツバイソのパッケージ（tb_PSA・tb_IMA）の項目のヘルプテキスト | AIは、パッケージの初期値か、顧客が書き換えた値かを区別できない。出所を「ヘルプテキスト」と示して製品の意味と並べ、顧客記述の意味付けとしては扱わない |
| 説明欄・ヘルプテキストのどちらにも本文が無い（顧客が追加したメタデータ） | AIがAPI名・表示ラベル・定義（データ型・数式・条件など）から推測した本文を、推定として確信度つきで応答に添える。そのメタデータを確認一覧に加える |
| 権限・経路が無く読めなかった | 「未確認（説明欄を読む権限が無い）」「未確認（説明欄を読む経路が無い）」のように、何が読めなかったかを1行で示して処理を続ける。確認一覧には加えない |

- **1つのメタデータの説明欄とヘルプテキストが食い違うときは、どちらも断定の形で使わない。** 両方を出所つきで並べる。
- **出所を示す。** 応答では「この組織の説明欄では」「この組織のヘルプテキストでは」のように出所を添え、製品の意味（Atlasの意味定義が返すもの）と区別する。
- **鮮度の表示を付けない**（鮮度の判定は意味付けの型を読む段階から）。
- **意味付けの本文をAtlasのサーバーへ送らない。** 製品の意味はAtlasの意味定義から引き、この組織の意味付けとは利用者側の実行環境で組み合わせる（ツバイソのサーバーは顧客のデータを受け取らない）。
- **ti-referenceが項目のヘルプテキストを「転記」「自動設定」の手がかりとして読む手順**（`ti-reference references/write-index.md`）は、値の出どころを確かめるためのもので、本節の意味付けの読み方とは別である。手がかりとしての読み取りは続け、その結果を意味付けとしては示さない。
- 説明欄（とくにオブジェクト・入力規則・フロー）を読めるかは、利用者に割り当てた権限で決まる。TIの利用者に、説明欄を読むためだけのシステム権限（「設定・定義を参照する」など）は加えない。

## 属性行

AIが説明欄に本文を書くとき（ti-metadataで新しく作成するメタデータ）は、説明欄の最後の1行に属性行を付ける。属性行は、読み方（上の表）で説明欄の本文の書き手を判別するために使う。

```
{本文}
[TI:書き手=推定,確信度=中,確認日=2026-10-25]
```

| キー | 値 |
|---|---|
| 書き手 | `顧客記述`（顧客の管理者が本文を確認した）／`推定`（顧客の管理者がまだ確認していない。書いた人は問わない） |
| 確信度 | `高`／`中`／`低`。**書き手が推定のときだけ付ける** |
| 確認日 | `YYYY-MM-DD`（組織のタイムゾーンでの日付）。書き手が推定なら本文を組織に書き込んだ日。顧客記述なら顧客の管理者が本文を確認した日（配備の承認で確認したときは、承認の日と配備した日の遅いほう） |

- **顧客記述にしてよいのは、顧客の管理者が本文を確認したときだけ。** 組織の権限では、承認する人が顧客の社員かツバイソの導入担当・パートナーかを区別できない。AIは承認を求めるときに、承認する人が顧客の社員で管理者かを本人に確かめる。確かめられなければ推定とする。
- **推定の本文には、どの手段で説明欄に書き込む場合も「書き手=推定」の属性行を付ける。** 属性行の無い説明欄は顧客記述として読まれるため、属性行を付けずに書いた推定の本文は、顧客の管理者が推定と知らないまま顧客の業務仕様として扱われうる。
- 解析の規則: 説明欄の最後の行が `[TI:` で始まれば属性行とみなす。キーと値が上表のとおりに読めなければ書き手不明とする（人が設定画面で属性行の一部を削除した場合など）。書き手が顧客記述で確信度が付いているときは、確信度を無視して顧客記述として読む。
- **字数**: 項目の説明欄の上限は1000字（属性行を含む）。項目以外のメタデータの上限は未確認のため、同じ1000字に収める。本文が収まらないときは、説明欄には上限に収めた要約を書き、全文を確認一覧に加える。
- 属性行の書式を改めるときも、次の4点は保つ: (1) 人が読んで理解できる (2) スキルが属性行を本文と機械的に区別できる (3) 属性行の無い説明欄は顧客記述・確認日なしとして読む（記入済みの本文を書き直さずに使うため） (4) 解析できない属性行は書き手不明として扱い、断定の形で使わない。

**AIは既存のメタデータの説明欄・ヘルプテキストを書き換えない。** 説明欄が空でも書かない。ヘルプテキストは画面で利用者に表示される文言で、意味付けの格納先にしない。AIがヘルプテキストを設定・書き換え・削除するのは、顧客の管理者が変更後のヘルプテキスト（削除するなら、削除すること）を配備の承認で確認したときだけとする（手順はti-metadata）。

## 確認一覧

意味付けの無いメタデータと、顧客の管理者の確認を待つ意味付けを集め、顧客の管理者に回答を求める一覧。

### 置き場と形式

- **正本**: 利用者の作業フォルダの直下の `TI_意味付けの確認一覧.yml`（1つの組織につき1ファイル。複数の組織を扱う作業フォルダでは、ファイル名の末尾に組織を表す名前を付ける）。作業フォルダを複数の利用者で共有する運用では、1つのファイルにまとめる。
- **顧客の管理者へ送るファイル**: 正本から `.xlsx` を書き出す（1件1行。回答の列だけを編集できるようにする）。正本（機械が読む）と送付用のファイル（人が書く）を分けて持ち、IDで突き合わせる考え方は `spec-roundtrip.md` と同じ。書き出せない実行環境ではMarkdownの表で送る。
- **作業フォルダの無い実行環境**（コネクタ・MCPだけを使う会話など）: 確認一覧に加える件があった応答の末尾に、「確認一覧に加える件が{n}件ある（作業フォルダが無いため保存していない）」と1行だけ添え、利用者が求めたら、その会話で加えた件をまとめて示す。全件の確認一覧は、作業フォルダのある実行環境で作る。

正本の1件の形:

```yaml
meaning_review:
  org: 組織のホスト名
  created_by: 作成した利用者
  items:
    - id: MEAN-001                 # 一度付けたら変えない
      added_by: 加えた利用者
      kind: field                  # 区分（object/field/relationship/behavior/master_ref/lifecycle）
      target: "{オブジェクト}.{項目}"  # 対象の API 名
      label: 見出し
      role_tag: ""                 # 役割タグ（入力規則は validation など）
      domain: ""                   # 特定できなければ空
      implemented_by: []           # 実装しているメタデータ（"ValidationRule:{オブジェクト}.{入力規則名}" "Flow:{フロー}"）
      related: []                  # 関係するメタデータ（種類:API 名）
      current:                     # 載せた時点の意味付け（無ければ空）
        text: ""
        source: ""                 # 説明欄／ヘルプテキスト／会話／配備
        writer: ""                 # 推定／書き手不明／顧客記述
      proposal:                    # 本文の案
        meaning: ""
        rule: ""
        structured: {}             # 区分が behavior・master_ref・lifecycle のとき
        confidence: 中             # AI が推測した案に付ける
        basis: ""                  # 推測の根拠にした定義
      reason: ""                   # 下の「載せる対象」の番号と名前
      added_on: 2026-10-25
      answer:
        status: 未回答             # 未回答／確定／修正／分からない
        meaning: ""
        rule: ""
        structured: {}
        corrections: {}            # 区分・役割タグ・ドメインの修正
        answered_by: ""            # 回答した顧客の管理者
        answered_on: ""
      registered: false            # Phase 1 では常に false
```

区分・役割タグ・ドメインはAIが決めた値を示し、顧客の管理者は回答で修正できる。本文の案は欄ごと（意味・ルール。区分がbehavior・master_ref・lifecycleなら構造化値も）に示し、顧客の管理者は欄ごとに確定・修正する。implemented_by・relatedの値の接頭辞（`CustomField:`・`ValidationRule:`・`Flow:` など）はMetadata APIの型名とfullNameに合わせる。

### 載せる対象（Phase 1）

1. **本文の無いメタデータ**: 説明欄・ヘルプテキストのどちらにも本文の無い、顧客が追加したメタデータ。AIが推測した本文の案に確信度と推測の根拠を添える
2. **推定・書き手不明の説明欄**: その本文を本文の案とする
3. **会話から抽出した意味付け**: 利用者が会話で述べた意味（ツバイソのパッケージ・標準のメタデータをこの組織でどう使っているか、複数のメタデータにまたがる業務ルール（以下「横断ルール」）を含む）を本文の案とする。会話の相手が顧客の管理者であることをAIが本人に確かめたうえで、その管理者がAIの示した本文の案をその場で確認したときは、その確認を回答として記録する
4. **ti-metadataの配備から**: 書き手を推定として説明欄に書いた意味付け、説明欄に収まらなかった全文、既存のメタデータの説明欄に書かなかった新しい本文、意味付けの型に記録する予定の意味付け（ti-metadataの手順による）。顧客の管理者が配備の承認で本文を確認した意味付けは、回答を `確定`、回答した顧客の管理者と回答日（承認の日）を記録した状態で加え、送付の対象にしない
5. **応答の途中での追加**: 読み方の表で「確認一覧に加える」とした場合

**重複して加えない。** 同じ対象（入力規則・フローの意味付けは実装しているメタデータで、横断ルールは同じ横断ルールかで判断する）が未登録のまま一覧にあれば、加えずに既存の1件を更新する（未回答なら本文の案を最新の内容に置き換え、回答済みなら回答を残す）。

### 全件の確認一覧を作る

次のいずれかのときに作る: (1) 管理者が求めたとき (2) TIの導入時（導入担当が案内する） (3) 本書を含むスキルの版を配布する前からTIを導入している組織で、配布後に初めてti-spec-viewを使うとき（作業フォルダのある実行環境で、作業フォルダに確認一覧が無ければ、作成をその会話で1回案内する）。

1. 顧客が追加したメタデータ（冒頭の用語のとおり。標準のオブジェクト・項目そのものは含めない）を全件一覧にする。取得経路はti-spec-view `references/structure-enumeration.md` による
2. 各メタデータの説明欄・ヘルプテキストを、§読み方の「取得経路」の表に従って読む
3. 載せる対象の1・2に当たるものを確認一覧に加える（既存の確認一覧があれば重複の規則に従う）
4. 件数を示す: 一覧にしたメタデータ、本文があり顧客記述として読めたもの、確認一覧に載せたもの、読めなかったもの。読めなかったものがあれば、管理者の権限で作り直すと読める場合があることを添える

**作り直すとき**は、未回答の1件は新しい本文の案に置き換え、回答済みの1件は残す。説明欄・ヘルプテキストに属性行の無い本文か「書き手=顧客記述」の属性行が付いた本文が書き込まれた対象（顧客記述として読める）と、組織から削除された対象は、未回答なら除き、除いた件数を1行で示す。

### 回答を受け取る

- 確認一覧を作成した利用者が、顧客の管理者へ送る。送る前に、AIは未回答の各件について、対象のメタデータの説明欄・ヘルプテキストを読み直し、属性行の無い本文か「書き手=顧客記述」の属性行が付いた本文が書き込まれた対象は除く。
- 顧客の管理者は、本文の案を確定・修正するか、「分からない」と回答する。そのメタデータを使っていないことも本文として回答できる。
- 受け取った回答をIDで正本へ反映し、回答した顧客の管理者と回答日を記録する。**Phase 1では組織に登録せず、回答を確認一覧に残す**（意味付けの型を含むtb_PSAの版を組織に導入した後に登録する）。

### 確認一覧は組織の意味付けとして扱わない [REQUIRED]

- AIは、確認一覧を作成した利用者との会話でだけ、未登録の本文の案と回答を「未登録」と示して応答に使う。
- 作業フォルダを共有していても、作成した利用者以外の会話では、確認一覧の本文の案と回答を応答に使わない。読み込んでよいのは、件を加える前の重複の確認（加えた利用者は件ごとの `added_by` に残す）と、顧客の管理者が回答する場合と、管理者が登録する場合だけ。
- 確認一覧の回答を根拠に、説明欄・ヘルプテキストを書き換えない（既存のメタデータの説明欄を書き換えない規則は、回答があっても変わらない）。
