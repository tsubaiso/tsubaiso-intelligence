# 計画の台帳と引き継ぎ（plan-and-handoff）

複数セッション・数日以上にまたがる TI の仕事（導入・移行・帳票やカスタマイズの往復・PoC）で、当初の目的と決定を読み返せる形で残し、次のセッションが調べ直さずに再開できるようにする。

**AI ホストのプロジェクト・メモリ・タスク一覧の機能に依存しない。** Markdown を 1 枚（以下 `plan.md`）、利用者が決めた置き場に置くだけで成り立つ。ホストのタスク一覧はセッション内の作業メモで、消えることがある。セッションをまたいで残したいものは `plan.md` に書く。

## いつ読むか

- 複数セッションにまたがる見込みの仕事を始める瞬間
- 当初の依頼に無かった要望・派生作業が合流した瞬間（スコープが膨らみ始めた）
- セッションを区切る・中断する瞬間／主要な成果物が一区切りついた／org への反映・承認依頼を出した瞬間

小さな単発作業・即答では読まない。

## `plan.md` の最小構成

```
# {仕事の名前} plan

## 目的 / 依頼（変えない）
最初の依頼と、達成したいこと。変えるときは決定事項に理由を残す。

## 方針

## スコープ
- やること
- やらないこと（今回から切り出したもの）

## 決定事項（追記式・理由つき）
- YYYY-MM-DD 〇〇に決定（理由: …）

## 残務 / 次の一手
- [ ] …

## 未解決・確認したいこと（誰のボールかを対で書く）
- …（ボール＝利用者／AI／第三者）

## 経緯 / 申し送り（追記式・上書きしない）
### YYYY-MM-DD {セッション名}
- 終わったこと / 分かったこと（試したが違ったことを含む） / 次の一手
```

§残務・§未解決 は「いまの状態」なので消化すると消える。§決定事項 は結論だけ。**何をやって何が分かったかが残るのは §経緯 / 申し送り だけ**なので、ここは消さずに積み上げる。**積むのと直すのは対で行う**——1 ブロック積んだら、同じ区切りで §残務・§未解決 をいまの状態に直す。

`plan.md` が長くなったら、節を増やしたり古い経緯を消したりせず、仕事のほうを分ける（新しいテーマの `plan.md` を作り、前の `plan.md` の場所を §目的 に 1 行書いて辿れるようにする）。

## 3 つの照合

1. **スコープ拡大の判断** — 当初の依頼に無い要望が来たら、すぐ着手せず「今回に取り込む／別に切り出す」を決め、§決定事項 に 1 行残す。黙って作業を増やさない。
2. **本筋の照合** — セッション開始時と区切りで §目的 を読み返し、いまの作業がそれに資するかを点検する。逸れていれば利用者に知らせ、方針を確認する。
3. **抜け漏れの確認** — 区切りごとに §残務 を見直し、後回し・棚上げにしたものが落ちていないかを拾う。

## 区切りの引き継ぎ

**先に `plan.md` へ書き、次にチャットへ出す。順序を逆にしない。** チャットに出しただけのメモは会話履歴に埋もれ、次のセッションからは読めない。

1. §経緯 / 申し送り に、日付とセッション名で 1 ブロック追記する（上書きしない）
2. §残務・§未解決 をいまの状態に書き直す
3. 同じ内容をチャットに出し、再開プロンプトをコードブロックで出す

書く内容は 5 点: **終わったこと／分かったこと（試したが違ったことを含む）／次の一手／置き場所（成果物・`plan.md`・決定のありか）／未完了の外部アクション（承認待ち・org 反映待ち等）**。

```
{仕事の名前} の続き。plan.md: {置き場}
plan.md の §経緯 / 申し送り の最新ブロックを読んでから再開してください。
直前に終わったこと: {1 行}
次の一手: {1 行}
```

## やらないこと

- 「区切ります／終了します」と一方的に宣言しない。引き継ぎは提案として出し、続けるかは利用者が決める。
- 長大な内部ログを貼らない。次が動ける最小限に絞る。
- 利用者のフォルダ構成・命名・レビュー体制に踏み込まない。台帳は 1 枚で、置き場と名前は利用者の作法に従う。

## 局面スキルとの関係

`ti-onboarding` の工程マップは「何を順にやるか」、モード遷移（PoC → 導入）は局面をまたぐ引き継ぎを扱う。本 reference はそれらの中で「当初何を決めたか・逸れていないか・次に何をするか」を残す台帳で、工程や局面を問わず同じ 1 枚を使う。
