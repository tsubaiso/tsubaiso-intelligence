# 安全ゲート（safety-gate）

org へメタデータを書き込む（デプロイ・カスタム項目追加・本番反映）すべてのドメインスキルが、書込の直前に通す共通ゲート。各ドメインスキルは「org へメタデータを書き込む直前」に本書を読み、deploy 対象と承認ドラフトを揃えてから下記チェックを満たす。

## 射程はメタデータ書込だけ。データ（レコード）の書込は本書ではない [REQUIRED]

**本書が扱うのはメタデータのデプロイであって、レコードの作成・更新ではない。** 下のチェックリスト4項目（checkonly・承認・カバレッジ75%・PIIマスキング）は、いずれもデータ書込には当たらない。

**レコードを作成・更新する直前に通すのは ti-reference `references/write-index.md` の書込前ゲート＝`atlas_write_seam(target=<API名>)`。** そちらが `function_only`（直接 INSERT が整合性を壊す対象）・`auto_create_as_target`（別シームの自動生成先＝手動作成禁止）・`reference_filters`（参照先マスタの有効条件）を判定する。

**この区別を本書の冒頭に置くのは、呼ぶ側の索引がデータ書込の語で本書を名指ししていた実績があるため**（`ti-update` の発火点行が「org へ書き込む直前（作成・トリガ項目更新・マスタ書込）」と書いて本書を指していた）。**開いた側は本書の射程では正しいことを読むので、射程違いに気づく契機が無い。** 本書を名指しする索引の語が「メタデータ」で限定されているかを、参照を足す側が確かめる。

### スキルが読まれなくても出る案内（書込前の警告フック）

**書込前ゲートはスキルの文面なので、TI のスキルが一度も読み込まれないまま組織へ書く経路では働かない。** 業務の依頼を受けたAIが、スキルを読まないままコマンドラインから本番の組織へ直接レコードを作る計画を立てることは起こりうる。この経路を拾うため、配布プラグインは書込前の警告フック（`scripts/write_gate_notice.py`。`.claude-plugin/plugin.json` の `hooks` で登録）を同梱する。

| 項目 | 内容 |
|---|---|
| 拾う呼び出し | コマンドラインの `sf data create`／`import`／`upsert` と `sf api request rest` の POST、MCP の `dispatch` の POST のうち、`tb_PSA__`／`tb_IMA__` のオブジェクトのレコードを作るもの |
| 出すもの | 利用者へ「先に書込前ゲートで確かめる」案内、モデルへ `atlas_write_seam` を引く手順の案内 |
| 止めるか | **止めない。** 呼び出しは通常の権限の確認を経てそのまま進む。許可の判定を返すと権限の確認を飛ばしてしまうため、判定は返さない |
| 動く環境 | **Claude Code（ターミナル・IDE拡張・デスクトップアプリ・クラウドのセッション）と、プラグインを読み込んだ Claude Agent SDK だけ。** claude.ai のチャット・Cowork・Cursor・ChatGPT・Copilot Studio では動かない（スキルを1つずつアップロードする環境には同梱されない） |

**フックは案内であって防壁ではない。** 案内が出なかったことは、書いてよいことを意味しない。モデルへの案内は呼び出しの結果と一緒に届くため、読んだ時点で作成が済んでいることもある。フックが動かない環境では、スキルの書込前ゲートが唯一の層になる。機能経由でしか作れないオブジェクトを、経路を問わず組織の側で止める仕組みは製品側で用意する予定で、それが入るまではこの2層に頼る。

## org 書込前のチェックリスト（4 項目）

| # | チェック | いつ・何を止めるか |
|---|---|---|
| 1 | **checkonly（validate）先行** | 本番反映の**前**に validate デプロイで通す。検証を通らないメタデータの本番反映を止める |
| 2 | **承認ゲート** | **本番反映**は、org の変更権限を持つ承認者（導入責任者・管理者ロール）の承認を得てから行う。未承認のまま本番へ反映することを止める |
| 3 | **本番カバレッジ 75%** | **本番 org への deploy** はテストカバレッジ 75% を必要とする（トライアル org は NoTestRun でデプロイ可）。カバレッジ不足のまま本番 deploy を止める |
| 4 | **PII マスキング** | フィードバック等の**外部送信時**に業務データ本体を送らない（テレメトリのみ）。業務データ・PII が org 外へ出ることを止める |

## 運用メモ

- 反映は「checkonly で検証 → 承認 → 本番反映」の順を固定する。validate を飛ばして本番へ直接デプロイしない。
- カスタマイズ支援系（メタデータ生成・差分デプロイ）でも本ゲートを共通で通す。低リスクの種から PoC し、本番反映は承認ゲート＋checkonly 先行を必ず経る。
