# 製品知識の引き当て（knowledge-lookup）

AI は、製品の仕様や操作手順を知らないことがある。そのとき既定の行動は **推測ではなくナレッジを引くこと**である。

## なぜ要るか

知らないことに気づくのは難しい。仕様を知らない AI は「知らない」と自覚せず、**手元にあるもの（Apex コード・フロー・入力規則・メタデータ・実データ）から挙動を組み立てはじめる**。組み立てた答えは筋が通って見えるため、誤りが誤りとして現れない。

現れ方は 4 つある。いずれも読めるものだけから組み立てた結果で、**共通しているのは「引けば載っていた」ことである**。

| 失敗の形 | なぜ気づけないか |
|---|---|
| **仕様どおりの挙動を障害と呼ぶ** | 期待と違うことは観測できるが、期待の側が誤っていることは観測できない |
| **すでに起きていることを、起きていないと報告する** | 「起きていない」の根拠は自分の組み立てた前提であって、実測ではない |
| **誤った仕様の前提が、回答ではなく選択肢・作業計画に混入する** | 前提は文になって出てこない。利用者は結論だけを見て選ぶので、前提を検算する機会が無い。**最も高くつくのはこの形である** |
| **対象の範囲を自分で数え上げ、部分だけ処理して完了と報告する** | 射程の一覧は仕様側にある。引かずに数えると、落とした分は形跡を残さない |

**この文書に製品の仕様そのものを書かない [REQUIRED]。** 例として書いた仕様は、ナレッジが更新されても追随しない。仕様の出所は常にナレッジである。

## いつ読むか

次の 4 つは**行動で判定できる**。どれかに手をかけた瞬間に読む。**「自分は仕様を知らない」という自覚は判定条件にしない**（自覚できないことが問題の中身だから）。

1. **製品そのものを読もうとした瞬間** — Apex クラス・フロー・トリガ・項目ヘルプ・パッケージのメタデータを開こうとした。**構造の解決（describe で型・ラベル・実行時の関係名を取ること）と、意味定義が返す自動化・入力規則の読み取りは含まない。** これらは参照タスクの正規の手順である（`ti-reference` §参照タスクの手順）。**含むのは、そこで取れたものを材料にして、ナレッジへ当たらないまま手順・可否・理由の文を書こうとしたときである。**
2. **可否・手順・理由を書こうとした瞬間** — 「できますか」「どうやりますか」「なぜこうなりますか」に答える文。**回答だけでなく、利用者へ出す選択肢・作業計画・段取りの前提に仕様を置こうとしたときを含む [REQUIRED]。**
3. **実測した値が期待と違い、「不具合」「障害」「バグ」「おかしい」と書こうとした瞬間 [REQUIRED]** — 仕様どおりの挙動を障害と呼ぶ事故がここで起きる。**ナレッジで仕様を確かめる前に不具合と書かない。**
4. **作業の対象範囲を自分で数え上げようとした瞬間 [REQUIRED]** — 「どれとどれを処理すればよいか」を手元の観測から数えない。**射程は仕様側にある。**

> **`not_found` は本作法の発火点ではない。** 意味定義（Tsubaiso Atlas）が `not_found` を返すのは「守備範囲の外へ出た」ではなく「**引き方を間違えた**」の第一シグナルである（`ti-reference` §業務プロセスの図・順番を描くとき）。まず指し先の名前で引き直す。ナレッジへ移るのは、上の 4 つのどれかに当たったときだけである。

## 守ること

- **推測で挙動を組み立てない [REQUIRED]。** コード・メタデータ・実データは「何がどうなっているか」を示すが、「そうあるべきか」は示さない。
- **読んだものを根拠として出典を添える。** どの記事で確かめたかを示す。示せないなら確かめていない。
- **確かめられなかったことは「未確認」と書く。** 引けなかったことを、引いた結果のように書かない。
- **出力の書き方は `ti-reference` §出力規律（最上位原則）に従う [REQUIRED]。** 本書は独自の出力規律を持たない（同じ規律が複数の場所に分かれると、弱いほうが使われる）。ヘルプ記事の公開 URL は同規律の対象外で、出してよい。

## 意味定義（Atlas）とナレッジの使い分け

**同じ「知識」だが守備範囲が違う。** 混同すると、片方を引いて満足して止まる。

| 問い | 引く先 |
|---|---|
| このデータは業務的に何を意味するか／どう集計するか／レコードができる順番はどれか | **意味定義（Atlas）** |
| ドメイン固有の規則（消込の判定項目・予実の集計区分・進行基準の進捗率・返品の方向判定 等） | **意味定義（Atlas）が正**（`ti-reference` §SOQL 実行規約 7）。ナレッジの記述と食い違ったら意味定義を採る |
| 画面でどう操作するか／設定はどこで行うか／この機能はできるか／この挙動は仕様か | **ナレッジ** |

**実測と期待が食い違ったときは両方引く [REQUIRED]。** 意味定義でその値の意味を確かめ、ナレッジでその挙動が仕様かを確かめる。**両方そろって初めて「仕様と違う」と言える。**

どちらを先に引くかは依頼の性質で決まるため、順序は各能力スキルが自分の手順の中で持つ（本基盤は型を持ち、あてはめはドメインスキルが持つ）。

## 接続

ナレッジは組織公開コネクタとして提供され、**取得できる範囲と深さはサーバー側が本人の資格で制御する**。**返らなかった情報を推測で補わない。**

道具は 2 つある。**問いの文字列を渡して本文を検索するもの**と、**記事の名前を指定して開くもの**である。**領域を指定してタイトルを一覧する道具は無い**ため、「まず一覧を眺める」から始める手は取れない（§引けなかったときの立て直し）。ツールの名前は実行時にツール一覧から解決し、本文に焼き込まない。

**未接続・検索の道具が見えないとき [REQUIRED]**

1. **検索を装わない。** 引いていないものを引いたように書かない。
2. 未接続であることを告げ、接続の案内は `ti-rollout` へ渡す。
3. **そのうえで退避路を示す。** 公開のヘルプセンター（`https://support.tsubaiso.jp/hc/ja`）は接続がなくても読める。該当しそうな記事を利用者自身が探せるよう、製品と機能の呼び名を伝える。
4. **未接続を理由に仕様を推測しない。** 接続が無いことは、推測してよい理由にならない。

## 引けなかったときの立て直し

**この検索はキーワード指向である [REQUIRED]。** 業務の対象と機能名を **2〜3 語**並べたときに最もよく当たり、**同じ内容を自然な一文にすると落ちる**（一文にした問いが 0 件になる一方、2 語では答えの本文そのものが返る、という差が実測されている）。**0 件のときに語を足さない。減らす。**

**1 回の検索で「無い」と結論しない [REQUIRED]。** 全文検索は品質が落ちても告知せずに落ちる。0 件と「無い」は別のことである。**「無い」を利用者に返すときの書き分けは `capability-preflight.md` §「無い」と「対応していない」を書き分ける に従う。**

### 立て直しの合図

- 0 件だった
- 全体像を扱う記事だけが返り、訊いた挙動そのものが本文に無い
- ヒットが機能名の一語で拾った雑多な一覧に見える
- 操作手順を訊いたのに、仕様書・設計資料の側にばかり寄っている

### 立て直しの手（この順で）

1. **総論で射程を取り、指し先の個別記事へ降りる [REQUIRED]。** その機能の全体像を扱う記事をまず引き、扱いの範囲と対象の一覧を取る。**総論は機構と射程を教えるが、個々の挙動は各領域の使い方の記事にある。総論で止まらない。** 総論が挙げている個別の名前で引き直すか、記事の名前が分かればその記事を直接開く。これは意味定義側の「正準シーケンスは各工程を別のレシピ名で指す。その指し先を名前で引く」（`ti-reference`）と同じ形である。**§いつ読むか の 4（射程を自分で数え上げない）も、この手で解ける。**
2. **語を減らす [REQUIRED]。** 助詞・動詞・疑問形を落とし、業務の対象＋機能名の 2〜3 語にする。**それでも 0 件なら、機能名 1 語まで減らす。** 実測では、同じことを訊いた一文が 0 件、機能名 1 語で総論記事の本文が返った。**文を足して具体化しない**（この検索では逆効果になる）。
   - **記事の見出しや画面に出ている名前を、そのまま長い 1 語として投げない [REQUIRED]。** 実測では、見出しの完全一致で最上位に当たる記事と、0 件になる記事の両方がある。0 件になった記事も、語を減らして 2 語にすると最上位で返った。**なぜ落ちるかは特定できておらず、投げる前に当たるかどうかを見分ける手がかりも無い**（検索側の是正は当社で調査中）。したがって名前は、そのまま投げる材料ではなく**語を減らす材料**として使う。
3. **利用者の言い方で 0 件なら、製品側の呼び名が違うと疑う [REQUIRED]。** 用語の対応表は持たない（組織ごとに語が増え、表に無い語で同じことが起きる）。疑って引き直す規律だけを持つ。
4. **複合語を分解する。** 自社の言い方でつないだ語（外部システム名＋動作など）は、製品側では別の 1 語になっていることがある。分解し、機能名ではなく**やりたいこと**の語で引く。

**2〜3 回立て直しても届かなければ、そこで止めて起票する**（下記）。断定はしない。

## 引けなかったものを残す

引けなかったことは、ナレッジ側の穴か検索の届かなさのどちらかである。**どちらも次の人のために残す。**

`feedback.md` の作法で `event_type` を `knowledge_gap` として記録し、`classification` で区別する。**イベントのスキーマ本体（7 キーの構造・送信の作法）は `feedback.md` が正本**で、本表はそのうち `knowledge_gap` 系統の `classification` の値域だけを定める。

| `classification` | 何が起きたか |
|---|---|
| `knowledge_missing` | 記事が無い |
| `knowledge_stale` | 記事はあるが実態と違う |
| `knowledge_unreachable` | 記事はあるが引けない（呼び名の食い違い・検索の届かなさ） |

> **P1 の挙動**: `feedback.md` の送信 IF は **P1 ではローカルスタブ（記録のみ・実送信しない）で、オプトインは既定 OFF**。記録は残るが当社へは届かない。実送信は P2（Tsubaiso Feedback MCP 立上げ後）から。

**意味定義側の穴はここでは扱わない。** 構造の版ズレ・意味定義の欠落は `atlas_drift_check` で検知し、能力スキル側の §鮮度・ドリフト検知 で扱う（守備範囲が違うものを同じ受け口に入れると、直す場所を取り違える）。

利用者が当面の解決を必要としていて一次解決で片づかないなら、あわせて `support-escalation.md` の作法で起票する。

## 分担

| 層 | 役割 |
|---|---|
| ti-core（本 reference） | 「推測しない → 引く → 立て直す → 残す」の共通の型と、意味定義との守備範囲の切り分け |
| `ti-rollout`（接続・環境セットアップ） | コネクタの接続手順と、つながっているかの確かめ方 |
| 各能力スキル | 自分の手順の中で §いつ読むか の 4 つを発火点として持ち、到達したら本作法を通す。どちらを先に引くかの順序も各能力スキルが持つ |

**能力スキルの発火点表に行が無ければ、この作法には到達しない [REQUIRED]。** 能力スキルは ti-core の reference を発火点表からパスで名指しして読む設計で、**ti-core の SKILL.md 全体を読むわけではない**。したがって本作法が ti-core の一覧に載っていても、能力スキル側に行が無いセッションでは 1 度も発火しない。**新しい能力スキルを足すとき、および本作法を改訂するときは、org を触る／手順・可否・理由を書く能力スキルすべてに行があるかを数え上げる。**

実際に、この委譲は長らく片側だけが実装されていた（`knowledge-lookup` を発火点として持っていたのは `ti-reference` だけで、投入・更新・帳票の各スキルには行が無かった）。そのため投入や更新から入ったセッションでは、製品の使い方を引かないままコードやメタデータから挙動を組み立てる経路が開いたままだった。
