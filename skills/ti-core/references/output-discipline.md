# output-discipline — 利用者向け出力の規律（業務言語とレコードのリンク化）

TIのどのスキルから出す出力にも同じように効く横断規律。**本書がこの規律の実体（正本）で、各ドメインスキルは自分の側に書き写さず本書を参照する。**

## この reference を読む発火点

| チェックポイント | やること |
|---|---|
| **利用者へ渡すファイルを書き出す直前**（回答書・資料・レポート・帳票の下書き・チャットへ貼る本文。書き出しのツールを呼ぶ手前） | §業務言語だけで書く を当てて内部識別子を業務語へ翻訳し、§レコードのリンク化 に従ってリンクを付けてから書き出す |
| **利用者へ見せる出力に、レコードを名前・番号・件名で示そうとした瞬間**（一覧・点検結果・レポート・確認依頼・承認待ちの提示・調査報告のいずれでも） | §レコードのリンク化 に従い、そのレコードを開けるリンクを付ける。ホスト名の解決手順も本書が持つ |
| 利用者へ見せる説明文を書こうとした瞬間 | §業務言語だけで書く に従い、内部識別子を業務語へ翻訳する |

**発火点を「書こうとした瞬間」だけにしない [REQUIRED]。** 「書こうとした瞬間」は主観の切れ目で、**下書きを組み立てているあいだは自分では発火していない**（もう書き始めているのに、まだ書く前のつもりでいる）。**ファイルを書き出すツールを呼ぶ手前**は主観が入らない切れ目なので、そこを最後の関門に据える。実際、意味定義の戻り値をそのまま素材にして顧客提示想定の資料を書き、**識別子が残ったまま提示まで到達した**事例がある。

**戻り値をそのまま素材にしない [REQUIRED]。** 意味定義（Atlas）の戻り値は識別子を主に組み立てられており、業務語（`meaning`）は各項目の内側にある。**最小抵抗の経路（戻り値を写す）をたどると、この規律に違反した文章ができる。** 戻り値から文章を起こすときは、識別子を業務語へ置き換える一手を必ず挟む。この一手は忘れられるので、上表の最後の関門で拾う。

**発火点を「参照・集計の返却時」に限定しない [REQUIRED]。** レコードを示す出力は参照系だけで出るものではなく、承認待ちの点検結果・入力支援の突合結果・仕様の可視化・移行の投入報告からも出る。**規律を参照系のスキルの中だけに置くと、参照系が読み込まれない場面（承認前チェックだけを回した回など）では規律そのものに到達できず、リンクの無い出力が黙って出る。** 本書を ti-core に置くのはこのためで、どのドメインスキルからも同じチェックポイントで到達できる。

## 業務言語だけで書く

利用者（業務ユーザー）に見せる説明文では業務言語だけを使う。

- API名・内部項目名・レコードId・SOQLは説明文に出さない。**名前空間接頭辞の有無、省略形とフル形の別に関わらず対象**（標準項目・顧客組織が追加した項目も含む）。これらは内部の結合キー・クエリ生成にのみ使う
- 項目を言及するときは意味定義の業務的意味（`atlas_explain` の `meaning`）に翻訳して呼ぶ（例: 内部の粗利率項目→「粗利率」、未確定フラグ→「明細が未確定」）
- §レコードのリンク化 とは住み分ける: レコードへの**クリックできるリンク**は出してよい（原本を開く導線）。出さないのは説明文中の**生のAPI名・内部項目名・SOQL**
- 管理者・コンサル層向けの技術ドキュメント（項目マッピング設計書・カスタマイズ設計書など）は射程が別で、源データ項目のAPI名を扱ってよい。エンドユーザー向けの回答・帳票と混同しない

## レコードのリンク化

利用者へレコードを示すとき、クリックでSalesforce原本レコードを開けるようリンクを付与する。原則は「**開ける対象（レコード）＝リンク、測る値・分類値＝そのまま**」。

- **リンク化する（必須）**: (1) 行そのもののレコードId、(2) ナビ可能な参照（取引先・案件・受注・請求・発注・納品・売上・制作指図・調達・返品申請 等の開けるレコード）。表示名があれば名前をリンクテキストにし、無ければIdをリンクテキストにする
- **リンク化しない**: 金額・数量・日付・割合・集計結果の数値、選択リスト/ステータス/区分・コード値、参照でない単なるテキスト
- **書式**: `https://{myDomain}.lightning.force.com/lightning/r/{Id}/view`（オブジェクト名不要）
- **`{myDomain}`（組織のホスト名の先頭部分）の解決**: 一次手段は `SELECT Domain FROM Domain` の実行。返った行のうち末尾が `.my.site.com` / `.my.salesforce-sites.com`（Salesforceホストの既定形）のものを採り、**その末尾だけを取り除いた残り全体**を `{myDomain}` とする。実行時に一度だけ解決してセッション内でキャッシュする
  - **区画（sandbox・開発組織等）を最初の `.` で切ると存在しないホストになる。** 既定形の手前には区画のラベルが入ることがあり（形は `{My Domain 名}--{区画名}.{区画種別}.my.site.com`）、先頭ラベルだけを採って `.lightning.force.com` を付けると解決しないホストを組み立てることになる。**取り除くのは末尾の既定形だけ**で、`--` や区画種別を含む残りはそのまま残す。区画種別を列挙して分岐しない（列挙は将来増える区画に追従できない）
  - `getUserInfo` はインスタンスURLもMy Domainも返さない（返るのは利用者Id・氏名・プロファイル・ロール・タイムゾーン等）。`Organization` もインスタンス名を持つだけでMy Domainを持たない。**どちらもホスト解決には使えない**
  - `Domain` が返すのはExperience Cloudサイト・独自ドメインのDNSレコードで、**Lightningのホストとは別物**。ドメイン文字列をそのままリンクのホストに使わない。採るのは既定形を除いた先頭部分だけで、`.lightning.force.com` は固定で付ける。独自ブランドのCNAMEだけを持つ行にはMy Domain名が入らないので使わない
  - **解決できないとき（`Domain` が0件・既定形の行が無い等）は推測でホスト名を組み立てない。** リンクを省いたうえで「組織のホスト名が解決できずリンクを省いた」ことを利用者に伝え、必要なら組織のURLを尋ねる
- **集計（GROUP BY）の結果**: 行Idが無いため軸の値は直接リンク不可。ドリルダウン導線（該当条件の明細クエリ、またはリスト/レポートへのリンク）を併記する
- **クエリ側への含意**: レコードを列挙するクエリでは、リンク化する参照のIdをSELECTに必ず含める

### リンクを省いてよい場面と、省いたときにやること

- **省いてよいのはホスト名が解決できなかったときだけ。** レコード番号（見積番号・調達依頼番号など）が業務上そのまま通じることは、リンクを省く理由にならない——番号は「どれか」を示すが「開く」ことはできず、受け手が画面で検索し直す手間がそのまま残る
- 省いたときは**省いた事実と理由を1行で書く**。黙って省くと、受け手はリンクを付けられなかったのか、付ける規律を通していないのかを区別できない

### 外部システムへ書き出す文面での扱い

Slack・Jira・Chatter・メールなど、TIの外へ出す文面でも同じ規律が効く。**受け手がその組織のレコードを開ける立場にあるかを先に確かめ、開けない相手にはリンクでなく業務語での特定情報（番号・件名・取引先・金額）を書く。** サポートへの起票本文は `support-escalation.md` の定める例外に従う。
