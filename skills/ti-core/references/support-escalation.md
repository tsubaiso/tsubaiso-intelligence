# サポート起票（support-escalation）

ユーザーの問題を、AI がまず自力で解決し、それでも解決しない場合に**本人の許可のもとでサポートへ問い合わせとして起票する**共通機構。フィードバック（feedback）が「当社への匿名テレメトリ」なのに対し、本機構は「**ユーザーの未解決問題を本人文脈でサポート依頼として上げる**」対外の導線である。ドメインスキル・進行スキルは、ユーザーが当面の解決を要する未解決に至った瞬間に本書を読み、二段フローに従う。

## feedback との棲み分け（共通発火点）

| 機構 | 向き | 内容 | 業務データ | 承認 |
|---|---|---|---|---|
| feedback（既存） | 内部（当社へ） | 匿名テレメトリ（skill_friction／knowledge_gap） | 入れない（機械マスキング） | 不要（匿名・オプトインOFF既定） |
| support-escalation（本書） | 対外（サポートへ） | 未解決問題を本人文脈で起票 | 本人が意図した範囲のみ（下記「情報境界」） | 必要（承認＋投稿ゲート） |

**共通発火点**: 「未解決／回り道」の検知は feedback の `knowledge_gap` と条件が重なる。**未解決検知を単一の判定点にし、そこから (i) 内部 feedback（knowledge_gap）と (ii) 本サポート起票 に分岐**する。サポート起票の多くは knowledge_gap と重なる（ここでの `knowledge_gap` は「AI が解決に辿り着けなかった＝ナレッジの不足」を広義に取る）。ただし未解決には製品バグ・環境障害などナレッジ不足に起因しないものも含まれ得るため、`knowledge_gap` の厳密な部分集合とは限らない。両者は排他ではなく、匿名テレメトリ（feedback）と本人起票（本書）を同時に満たしてよい。

## 二段フロー

1. **一次解決（AI が自力で）**: まず Knowledge／Atlas で解決を試みる。ほとんどはここで解決する。
2. **未解決判定 → 起票分岐**: 一次解決で片づかず、ユーザーが当面の解決を要すると判断した瞬間に、上記の単一判定点から本サポート起票へ分岐する。
3. **窓口の分岐で起票**（下記「窓口ユーザーと3枠」）。

## 段階（P1／P2）

feedback と対称に段階を分ける。

- **P1＝下書き生成まで（実投稿しない）**。要約・再現手順・関連リンクを整えた**起票ドラフト**を作り、ユーザーへ提示するところまで。サポート接続が未確立なら、この下書き提示に留める。
- **P2＝実投稿（経路確定後）**。実際の起票は、**当社がホストするサポート起票経路を通す**。この経路が本人帰属での起票を担い、起票に必要な資格情報は**当社側に保持し、顧客環境には持ち込まない**（顧客環境から当社の管理資格で直接投稿しない）。P1 で固めたドラフト形式・発火点をそのまま P2 の実投稿へ差し替える。

## 窓口ユーザーと3枠（本人帰属の起票）

サポートへの正式な問い合わせ者は**窓口ユーザー**に限る。窓口は当社が登録・管理する問い合わせ担当者で、当社サポート基盤の**問い合わせ担当者組織のメンバーとして識別**する（利用者とサポートユーザーの同定はメール突合／SSO）。**組織あたりの枠数は契約上の上限**（既定＝3名。ライセンス上の制約ではなく契約で定めた上限で、システムで人数を強制しない）。問い合わせ資格の判定は当社サポート側の**組織メンバーシップ**で行い、人数は当社が登録時に運用管理する（4人目の追加もアカウント作成＋組織メンバー追加で足りる）。窓口ユーザーはサポートの一般の問い合わせ者（無償・人数制限のない区分）として扱う。窓口の登録・人数の運用管理・組織の用意といった**当社側の設定手順は内部運用に持ち、本書（配布）には含めない**。

顧客ごとに問い合わせ担当者の組織を分け、問い合わせ内容は同一組織内でのみ閲覧できる（決算など機微を含む問い合わせを、他の閲覧用ユーザーから分離する）。「担当者以外か」の判定はこの**組織メンバーシップ**で行う。

起票は**窓口ユーザー本人に帰属**する形で行う。当社ホストの起票経路が、検証済みの窓口ユーザーを起票者（requester）として設定し、本人の問い合わせとしてサポートに記録する。実行主体（AI・当社経路）と帰属先（窓口本人）が分かれるため、**本文に「AI が本人の代理で起票した」旨と実起票者を明記**して透明性を担保する。

### 分岐

- **窓口ユーザー（枠内）**: 本人の許可を得て、要約・再現手順・関連リンクを整え、**本人帰属の問い合わせとして起票**する（投稿は承認ゲートを通す）。
- **窓口以外**: 直接投稿しない（現行運用と同じく、**すぐ分かることは即答しつつ、基本は窓口＝担当者から改めて問い合わせてもらう導線に返す**）。整った下書きを作り窓口ユーザーへ回す場合は (i) 非窓口本人の同意（本人以外へ内容を渡す越境開示のため）、(ii) 窓口が投稿する時点での再承認、(iii) 本文に代理起票である旨と実起票者の明記。
- **窓口不在（枠未設定／離席／退職）**: 下書きが行き先を失わないよう、**当社サポート窓口への代替導線**、または**管理者への窓口設定の督促**へフォールバックする。

## 情報境界（機械規則化）

- **載せてよい**: 症状・再現手順・操作の軌跡・関連レコードの**リンク（ID）**・エラーメッセージ。
- **禁止**: 他者／他社のデータ、無関係な業務データ、認証情報。
- 承認ドラフト提示時に、上記の範囲チェック（PII・業務データ本体の混入がないか）を通す。ユーザー向けに見せる本文には内部識別子（API 名・SOQL・具体的な鍵値）を出さない。
- **群A出力規律との関係**: 起票本文の関連レコードのリンク（ID）は、サポート側での再現特定に必要なため、ti-core 群A の出力規律（利用者向け出力にレコード ID を出さない）の**例外**として載せてよい。この例外は起票本文に限り、利用者向けの通常応答では群A規律どおりレコード ID を出さない。

## 重複起票の防止（dedup）

feedback の `dedup_key` と同様、未解決の反復発火で同一問題が複数の問い合わせに分裂しないよう、**再現キー**を持たせる。

- `dedup_key ＝ hash(症状の正規化 ＋ 関連スキル／ステップ ＋ 対象の再現条件)`。同一問題を1件に集約する。
- 既存の起票があれば、新規作成でなく**追記／参照**に寄せる。
- ハッシュ対象・正規化の粒度は運用で調整する（初期値・確定済みの一次事実ではない）。

## 発火点

- **未解決を検知した瞬間**（一次解決で片づかず、ユーザーが当面の解決を要する）: 本書を読み、二段フローへ入る。あわせて feedback の `knowledge_gap` を匿名で記録する（feedback のオプトイン設定に従う。共通発火点の分岐）。
- **サポートへ投稿する直前**: 承認ドラフトを提示し、情報境界チェックと承認を通す（ti-core `references/safety-gate.md` と同じ承認規律）。
- 進行スキル（ti-rollout／ti-onboarding／ti-poc）および各層2スキルの発火点表に「未解決でサポートへ上げる必要が生じた瞬間 → `support-escalation.md`」を**持たせる（各スキルへの反映は後続 MR）**。現状は本書の新設のみで、既存スキルの発火点表にはまだ反映していない（feedback 行のみ）。

## 原則

- **AI が下書き、人が承認・本人帰属**。未解決の要約と再現手順は AI が整えるが、投稿は本人（または窓口）の承認を通し、本人に帰属させる。
- **本人が意図した範囲だけを載せる**。情報境界を機械規則で守り、他者・他社・認証情報は載せない。
- **濫造しない**。dedup で同一問題を1件に集約し、AI の自動発火でチケットを量産しない。
- **一次解決を尽くしてから上げる**。まず Knowledge／Atlas で解こうとし、上げるのは当面の解決を要する未解決に限る。
