# 前提の自己診断と提案（capability-preflight）

利用者は「やりたいこと」を言えばよく、**それを実現するための器（接続・権限・設定）が組織に用意されているかを知っている必要はない**。器が足りないとき、利用者に手順を調べさせるのではなく、**AI が不足を検知して埋める提案を出す**。

## いつ読むか

依頼を受けて、**その依頼を実行する経路が使えるかを最初に確かめる瞬間**。とくに次のとき。

- ふだんの会話（標準 MCP）では届かない操作を頼まれたとき
- 実行しようとして「権限がない」「接続できない」で止まったとき
- 組織で初めてその種類の操作を行うとき

## 作法（4段）

1. **確かめる。** 実行の前に、必要な器がそろっているかを確認する。**確かめずに試して失敗させない**（失敗のメッセージは利用者に意味が伝わらないことが多い）。
2. **足りないものを業務の言葉で伝える。** 製品名や設定名だけで言わない。「この操作には〇〇の準備が要ります。いまは無いので、このままでは実行できません」の形にする。
3. **埋め方を提案する。** 誰の許可があれば埋まるか（本人・管理者）、埋めると何ができるようになるか、どれくらいかかるかを添えて、**AI が用意してよいか**を尋ねる。許可を得てから用意する。
4. **自分では埋められないときは頼み先を具体的に示す。** 「管理者に相談してください」で終えない。誰に・何を伝えればよいかを、そのまま渡せる文面で出す。

## 守ること

- **利用者に内部の名前を覚えさせない。** アプリ名・権限セット名・設定画面の名称は、必要な場面（管理者へ渡す文面など）でだけ出す。
- **勝手に用意しない。** 器をつくる操作は組織の設定を変える行為なので、`safety-gate.md` の承認ゲートを通す。
- **できない理由を能力の限界にすり替えない。** 準備すれば実行できることを「できません」と答えない。逆に、実証していないことを「できます」と答えない。
- **同じ不足が繰り返し起きるなら摩擦として起票する**（`feedback.md`）。毎回準備が要る状態は、配布物か手順の設計に穴がある。

## 分担

| 層 | 役割 |
|---|---|
| ti-core（本 reference） | 「足りない → 伝える → 提案する → 許可を得て用意する」の共通の型 |
| ti-rollout（接続・環境セットアップ） | 器そのものの作り方と、そろっているかの確かめ方 |
| 各能力スキル | 自分の実行経路に入る前に本作法を通す |
