# 前提の自己診断と提案（capability-preflight）

利用者は「やりたいこと」を言えばよく、**それを実現するための器（接続・権限・設定）が組織に用意されているかを知っている必要はない**。器が足りないとき、利用者に手順を調べさせるのではなく、**AI が不足を検知して埋める提案を出す**。

## いつ読むか

依頼を受けて、**その依頼を実行する経路が使えるかを最初に確かめる瞬間**。とくに次のとき。

- ふだんの会話（標準 MCP）では届かない操作を頼まれたとき
- 実行しようとして「権限がない」「接続できない」で止まったとき
- 組織で初めてその種類の操作を行うとき
- **同じ対象へ届く経路が複数あり、どれで実行するかを決めるとき**（§経路の選び方）
- **ブラウザ・画面操作の道具を使おうとしたとき**（例外なく。§経路の選び方の順位を確かめてから）
- **そのセッションで組織を最初に参照・書込する直前**（測定・点検を含む。§接続先の組織を確認してから操作を始める）

## 接続先の組織を確認してから操作を始める [REQUIRED]

**発火点**: そのセッションで、組織のデータ・設定を最初に参照する直前と、最初に書き込む直前。測定・点検・検証のための参照も含む。**セッションが変わったら再確認する**（前のセッションで確認した結果は引き継がない。日数では判定しない）。

**なぜ [REQUIRED] か**: 接続先を取り違えても、処理はエラーなく成功する。読み取りは成功し、警告も出ない。誤って接続した組織（本番など）にも同じ名前のオブジェクトがあるので、結果を確認しても判別できない。書込なら意図しない組織へ書き込む。**書込前ゲートが判定するのは「何を書くか」で、「どの組織へ書くか」は判定しない。** コネクタの名前や「接続済み」の表示も接続先を示さない（ti-rollout の疎通確認と同じ）。

**手順**:

1. **使おうとしている接続で、接続中のユーザーの情報を1回取得する。** `getUserInfo` がある接続ならそれを呼ぶ。無い接続（`discover`／`dispatch_readonly` を備える接続）では、接続中のユーザーの情報を返す読み取り専用の呼び出しを1回行う（例: `GET /services/data/v64.0/chatter/users/me`。応答に `username` が含まれる）
2. **応答のユーザー名を、意図した組織のユーザー名と照合する。** Salesforce のユーザー名は全組織を通じて一意なので、ユーザー名が一致すれば接続先の組織を特定できる。**会社名の欄は組織の照合に使わない。** ユーザーごとに入力される値で、組織名と一致するとは限らない
3. **同じセッションに組織の接続が複数あるときは、使う接続ごとに確認する。** 1本を確認しても、ほかの接続を確認したことにはならない
4. **一致しなければ、その接続で参照も書込もしない。** 利用者に業務の言葉で伝える（例:「いまの接続は本番の組織に接続しています。検証の組織ではないため、ここでは操作しません」）。接続先の変更は ti-rollout

## 遮断が確認されている呼び出し先

**Headless 360 の `dispatch`／`dispatch_readonly` は、フローのカスタムアクション（`/services/data/vXX.0/actions/custom/flow` 配下）と、サブリクエストをまとめて送る `POST /services/data/vXX.0/composite` を遮断する。** どちらも 403 と「This endpoint is not permitted via dispatch and must not be retried」が返る。フローのカスタムアクションは、同じ組織・同じユーザーでも、REST を直接呼ぶ経路（ローカル実行）では同じパスが 200 で返る。**遮断の原因は組織の権限ではなく、`dispatch` の仕様である**。同じ `actions/custom/` 配下でも、Apex のカスタムアクション（`apex`）・クイックアクション（`quickAction`）と、標準アクション（`/actions/standard`）の一覧取得は 200 で返る。

- **サブリクエストの束（`/composite`）は使わない。** 束の中身が参照だけでも遮断される。一括の作成・更新は sObject Collections（`/composite/sobjects`。外部IDで突き合わせるなら `PATCH /composite/sobjects/{オブジェクト}/{外部ID項目}` の upsert）で送る。`/composite/sobjects` は、参照（`GET`）が 200 で返ることを確かめた。作成（`POST`）・更新（`PATCH`）・upsert が遮断されないかは確かめていない。403 と上の文面が返ったら遮断として扱い、ローカル実行（ti-local-automation）へ回す。`GET /composite` は使える束の種類の一覧を 200 で返すが、`POST /composite` を実行できることは意味しない。`/composite/batch`・`/composite/tree`・`/composite/graph` が遮断されるかも確かめていない
- **フローのカスタムアクションは、Headless 360 経由では実行できない。** §作法の1（確かめる）で、この呼び出し先を利用可能な経路に含めない。ローカル実行（ti-local-automation）か、同じ処理を持つ Apex のカスタムアクションがあるかを先に探す
- **403 を権限の問題として記録しない。** 権限による拒否か経路の遮断かは、**同じ対象を2つの経路で呼び出し、結果を比較して初めて判別できる**。片方の経路で拒否されただけで、権限セットの追加を提案しない
- 一覧が返ることと、実行（POST）が成功することは別。**Apex のカスタムアクションと標準アクションの実行は `dispatch` で遮断されない**（`dispatch` を通った呼び出しは Salesforce まで届き、成否は業務の検査や承認プロセスの入口条件で決まる）。失敗したときは、返ったエラーの文面で原因を判断し、遮断として扱わない。業務の検査を通る入力（承認申請の標準アクションは、承認プロセスの入口条件も満たす入力）なら、実行は成功する（明細エディタの公開アクションは見積明細などの明細を作成し、承認申請の標準アクションは承認プロセスを開始する）
- **承認申請の標準アクションは、承認プロセスを直接開始する。** 製品の承認申請の画面から申請したときと同じ結果になるかは確かめていない。承認申請の代行は ti-update `references/approval-execution.md` の起動口と自己診断に従い、この標準アクションを起動口の代わりの経路として使わない

> - **依存事実**: Headless 360 の `dispatch` がフローのカスタムアクションの一覧取得と `POST /composite` を遮断し、Apex・クイックアクション・標準アクションの一覧取得と、Apex・標準アクションの実行（POST）と、sObject Collections（`/composite/sobjects`）の参照（`GET`）は許可すること。sObject Collections の作成・更新・upsert と、`/composite/batch`・`/composite/tree`・`/composite/graph` は未確認（Salesforce 側の実装で告知なく変わりうる）
> - **実証日**: 2026-10-23（`/composite` の遮断と `/composite/sobjects` の参照。実行の成功の確認は 2026-10-21、検査でエラーが返る実行の確認は 2026-10-17、一覧取得は 2026-09-30、初回 2026-09-19。検証組織）
> - **実証コマンド**: `dispatch_readonly` で `GET /services/data/v64.0/actions/custom/flow`（403 が返る）と `GET /services/data/v64.0/actions/custom/apex`（200 が返る）を呼ぶ。`dispatch` で `POST /services/data/v66.0/composite` に参照1件だけの束（本文 `{"compositeRequest": [{"method": "GET", "url": "/services/data/v66.0/sobjects/Account/{Id}?fields=Id,Name", "referenceId": "r1"}]}`）を送り（403 が返る）、`dispatch_readonly` で `GET /services/data/v66.0/composite/sobjects/Account`（`queryParams` に `ids` と `fields`）を呼ぶ（200 が返る）。実行は、検証組織に確認用のレコードを1件作り、`dispatch` で `POST /services/data/v64.0/actions/standard/submit` と、Apex のカスタムアクション `POST /services/data/v64.0/actions/custom/apex/{アクション名}` をそれぞれ呼ぶ（返るのは 403 の遮断ではなく、Salesforce の検査のエラーか成功）。作ったレコードは削除する。承認者が、レコードの担当者に設定した社員のユーザーと同じときは、申請の直後に自動で承認済になる（承認履歴のコメントは「割り当て先のユーザがレコード担当者と同一であるため自動承認しました」）。承認済になったレコードは製品の承認のロックで削除できないため、ロックを解除してから削除する。承認待ちのレコードを削除できるかは確かめていない
> - **再実証**: Headless 360 を前提にした設計判断を書くとき

## 参照の条件の渡し方（`queryParams` と日本語） [REQUIRED]

**Headless 360 の `dispatch_readonly` では、`queryParams` の値に日本語（英数字と記号以外の文字）を入れると、400（本文 "Bad Request"）が返る。** SOQL の `GET /services/data/vXX.0/query` の `q` だけでなく、`GET /services/data/vXX.0/parameterizedSearch` の `q` でも同じになる。英数字と記号だけの条件は通る。取引先名・社員名で引こうとすると、最初の照会で止まる。

- **問い合わせの文字列は `queryParams` で渡す。** `url` に `?` から後ろを書くと、ツールが呼び出しの前に拒否する（400・「'url' must not contain an inline query string」）
- **日本語をあらかじめパーセントエンコードして渡さない。** 二重にエンコードされて、エラーにならずに0件が返る。この0件を「該当なし」と読まない
- **日本語の名前で引くときは、`dispatch` で `POST /services/data/vXX.0/parameterizedSearch` を使い、検索語を本文に入れる**（例: 本文 `{"q": "{検索語}", "sobjects": [{"name": "Account", "fields": ["Id", "Name"]}], "in": "NAME"}`）。本文の日本語は通る。POST だが参照で、組織のデータは変えない（`dispatch_readonly` は GET しか送れないため `dispatch` を使う）。全文検索なので、SOQL の `LIKE` の部分一致とは当たり方が違う。返った名前を手元で確かめてから使う。**全文検索はレコードそのものでなく検索の索引を引く**（Salesforce 公式の SOSL の説明）。投入・更新した直後に0件が返っても「該当なし」と読まず、Id か外部IDを条件にした SOQL で確かめ直す（索引へ反映されるまでの時間は確かめていない）
- **件数の少ないマスタは、英数字だけの条件（区分・フラグ・Id 等）で一覧を取り、名前は手元で突き合わせてもよい**
- **この 400 を組織の設定や権限の問題として扱わない。** 同じ照会を英数字だけの条件で送り直せば、経路の問題かどうかを切り分けられる

> - **依存事実**: Headless 360 の `dispatch_readonly` が `queryParams` の値の日本語で 400 を返し、エンコード済みの値を二重にエンコードし、`dispatch` の POST の本文の日本語は通すこと（Salesforce 側の実装で告知なく変わりうる）
> - **実証日**: 2026-10-23（検証組織。二重のエンコードで0件になることは 2026-10-22 の観測）
> - **実証コマンド**: `dispatch_readonly` で `GET /services/data/v66.0/query`（`queryParams` の `q` に `SELECT Id, Name FROM Account WHERE Name LIKE '%株式会社%' LIMIT 3`）を呼び（400）、英字の条件に変えて呼ぶ（200）。`GET /services/data/v66.0/parameterizedSearch`（`queryParams` の `q` に日本語）も 400。`dispatch` で `POST /services/data/v66.0/parameterizedSearch`（本文の `q` に日本語）を送る（200 で該当の取引先が返る）
> - **再実証**: Headless 360 を前提にした設計判断を書くとき

## 書き込みの `dispatch` には `userType` に `builder` を付ける [REQUIRED]

**Headless 360 の `dispatch` で作成・更新・削除するときは、`userType` に `builder` を指定する。** 指定なしで送らない。ツールの説明は `userType` を参考情報としつつ、`discover` の説明は業務の操作なら `business` を付けるよう促す。しかし `business` を付けると、書き込みが Salesforce の画面（Lightning）と同じ制約で検査される。指定なしは、接続の経路によって `business` と同じ扱いになる（Claude のコネクタでは通り、同じユーザーが直接 MCP で接続すると拒否された。理由は未特定）ため、当てにしない。

- ページレイアウト（または Dynamic Forms）で必須の項目が無いと拒否される（`REQUIRED_FIELD_MISSING`「These fields are required in the Lightning UI」。例: ToDoの割り当て先・優先度、商談の売上予測分類）
- ページレイアウトで参照のみの項目に値を入れると拒否される（「is read-only in the Lightning UI」）
- 自由入力できる選択リスト（ToDoの件名など）に、選択肢に無い値を入れると拒否される（`INVALID_OR_NULL_FOR_RESTRICTED_PICKLIST`）
- 画面から作らないオブジェクト（メール記録）は作成できない（`FUNCTIONALITY_NOT_ENABLED`「insert is not supported for entity type 'EmailMessage'」）

**`builder` が効くのは、接続しているユーザーが「アプリケーションのカスタマイズ」（`CustomizeApplication`）の権限を持つときだけ。** この権限を持たないユーザー（営業担当者など、標準ユーザーや業務用のプロファイル）は、`userType` に関わらず画面の制約で検査される。`builder` は、権限を持たないユーザーでは無視されるだけで害は無いので、常に付ける。

**`builder` を付けても上のエラーが返ったら、接続しているユーザーの権限による検査として扱い、ti-local-automation（本人権限のローカル実行）へ切り替える。** 選択肢に無い件名の ToDo・メール記録・画面で必須の項目が埋まらないレコードの作成がこれに当たる。同じユーザー・同じ値でも、ローカル実行なら作成できる。組織の設定の誤りとして扱わない。ユーザーに「アプリケーションのカスタマイズ」を付けて通す対処は採らない（組織の設定を変更できる管理者の権限のため）。参照（`dispatch_readonly`）は対象外。Claude Code では、プラグインのフック（`scripts/dispatch_usertype_guard.py`）が、`builder` の付いていない書き込みを送る前に止め、`builder` を付けてやり直すよう返す。

> - **依存事実**: Headless 360 の `dispatch` が、`userType: builder` かつ接続しているユーザーが「アプリケーションのカスタマイズ」を持つときだけ REST API と同じ扱いで書き込みを通し、それ以外（`business`・権限を持たないユーザーの `builder`・経路によっては指定なし）は画面と同じ制約で検査すること（Salesforce 側の実装で告知なく変わりうる。利用者の報告では、2026-10-20 までは同じ書き込みが標準ユーザーでも通っていた）
> - **実証日**: 2026-10-26（検証組織。同じユーザーのプロファイル・権限セットだけを付け替えて送り分けた。本番の組織でも、権限を持たないユーザーで同じエラーを利用者の報告で確認）
> - **実証コマンド**: 検証組織で、「アプリケーションのカスタマイズ」を持つユーザーと持たないユーザーの接続から、`dispatch` に `POST /services/data/v66.0/sobjects/Task`（本文 `{"Subject": "{選択肢に無い件名}", "WhoId": "{取引先責任者のId}", "Status": "Completed"}`）を `userType: builder` 付きで1回ずつ送る（持つユーザーは 201、持たないユーザーは 400 `INVALID_OR_NULL_FOR_RESTRICTED_PICKLIST`）。作ったレコードは削除する
> - **再実証**: Headless 360 を前提にした設計判断を書くとき

## 経路の選び方（器がそろっているとき）

器はそろっていて、**同じ対象へ届く経路が複数ある**ときは、次の順で選ぶ。**判断の起点は「どの道具が手近か」ではなく「その対象を保有しているのはどのシステムか。そのシステムに対して権限を持つ経路は何か」。**

| 順 | 経路 | 使う場面 |
|:--:|---|---|
| 1 | **対象を保有しているシステムの専用経路**（そのシステムの MCP・API・CLI） | まずここを探す。対象がそのシステムの中にあるなら、ここで取れる |
| 2 | 認証を持つローカル実行（スクリプト） | 専用経路では届かない操作（大容量・バイナリ・一括・複合） |
| 3 | 汎用の取得手段（URL の取得など） | 公開された資料で、どのシステムの持ち物でもないもの |
| 4 | **ブラウザ・画面操作** | **1〜3 のいずれも無いことを確かめてから。** 人間向けの画面しか持たないサービスが対象のとき、または**見え方そのもの**（レイアウト・表示崩れ）が確認対象のときに限る |

### 守ること

- **汎用の取得手段が空・失敗を返したことは、上位の専用経路が無い証拠にならない [REQUIRED]。** 空の応答・ログイン画面への転送・画面側で組み立てられる表示は、**配信のしかたの問題**であって経路の不在ではない。失敗したときに順位を下げる（画面操作へ移る）のではなく、**対象を保有しているシステムへ戻って専用経路を探す。**
- **対象が利用者ご自身の組織の持ち物なら、外から取りに行かない。** 自組織に置かれた資料・記録・設定は、外部の公開 URL として取得を試みる前に、その組織への経路で取る。
- **画面操作の道具を使おうとした瞬間が、この節を読み直す発火点。** 落ちる前に必ず一度立ち止まる。

### なぜ順位を守るか

**Tsubaiso Intelligence の前提は「画面を介さず、AI から自然言語で操作できる」こと。** 経路があるのに画面を操作するのは、この前提と正面から矛盾する。利用者から見れば、AI が画面を開いた時点で「結局は人が操作するのと同じ」になる。

加えて画面操作は、そのときのログイン状態・画面の作り・表示の待ち時間に依存する。**ひとつの環境で通っても、別の利用者の環境では通らない。** 専用経路は、権限さえあれば環境をまたいで同じように動く。

## 作法（4段）

1. **確かめる。** 実行の前に、必要な器がそろっているかを確認する。**確かめずに試して失敗させない**（失敗のメッセージは利用者に意味が伝わらないことが多い）。
2. **足りないものを業務の言葉で伝える。** 製品名や設定名だけで言わない。「この操作には〇〇の準備が要ります。いまは無いので、このままでは実行できません」の形にする。
3. **埋め方を提案する。** 誰の許可があれば埋まるか（本人・管理者）、埋めると何ができるようになるか、どれくらいかかるかを添えて、**AI が用意してよいか**を尋ねる。許可を得てから用意する。
4. **自分では埋められないときは頼み先を具体的に示す。** 「管理者に相談してください」で終えない。誰に・何を伝えればよいかを、そのまま渡せる文面で出す。

## 守ること

- **利用者に内部の名前を覚えさせない。** アプリ名・権限セット名・設定画面の名称は、必要な場面（管理者へ渡す文面など）でだけ出す。
- **勝手に用意しない。** 器をつくる操作は組織の設定を変える行為なので、`safety-gate.md` の承認ゲートを通す。
- **できない理由を能力の限界にすり替えない。** 準備すれば実行できることを「できません」と答えない。逆に、実証していないことを「できます」と答えない。
- **作成が機能経由のみ（`function_only`）のときは、経路の有無を確かめてから答える。** 「直接は作れない」と「作れない」は別で、前者を後者として返すと利用者は画面操作へ戻る。確かめ方は `ti-reference references/write-index.md` §`function_only` は「作れない」ではない。
- **同じ不足が繰り返し起きるなら摩擦として起票する**（`feedback.md`）。毎回準備が要る状態は、配布物か手順の設計に穴がある。

| 層 | 役割 |
|---|---|
| ti-core（本 reference） | 「足りない → 伝える → 提案する → 許可を得て用意する」の共通の型 |

## 組織の構造が意味定義に追いついていないとき

器（接続・権限）はそろっているように見えても、**その組織のパッケージが古く、意味定義が前提にしている項目やオブジェクトが存在しない**ことがある。症状は、組み立てたクエリが `INVALID_FIELD` や `INVALID_TYPE` で落ちる形で出る。

### 先に「権限で取得できない」のか「組織に無い」のかを分けて扱う [REQUIRED]

**意味定義にあるのに照会で取得できないオブジェクト・項目を、「この組織には無い」と判定しない。** 接続しているユーザーにそのオブジェクト・項目を参照する権限が無いと、組織に存在するオブジェクト・項目でも、定義を取得する照会が0件を返す・`INVALID_TYPE`／`INVALID_FIELD` のエラーを返すなど、組織に無いときと同じ結果になる。エラーにならずに0件が返ることもあるため、権限によって取得できなかったと判別できない。**利用者の接続からは、権限で取得できないのか、組織に無いのかを区別できない。**

1. **利用者へ、権限で参照できていない可能性を業務の言葉で伝える。** 例:「この情報は、ご利用中のユーザーの権限では参照できていない可能性があります。管理者に、〇〇を参照する権限があるかをご確認ください」
2. **管理者宛ての依頼文を添える**（§作法 の4）。どの業務の情報を、どのユーザーが参照できるようにしたいのかを、そのまま転送できる依頼文にする。オブジェクト名・項目名は、この依頼文にだけ添える（§守ること）
3. **この段階では、意味定義のずれとして報告しない**（`feedback.md`）。管理者が参照権限を持つユーザーで確認しても取得できない、つまり組織に無いと分かったときだけ、下の §やること へ進み、意味定義のずれとして報告する。ツバイソ社外の組織では、ツバイソへの問い合わせとして伝える

### やること

1. **推測でクエリを組み直さない [REQUIRED]。** 似た名前の項目へ差し替える、条件を外して通す、といった回避をしない。**通ってしまうと、利用者は違うものを見ていることに気づけない。**
2. **`atlas_drift_check` を実行する。** 組織の構造と配信中の意味定義の版ズレ・欠落を取る。
3. **次の3点を業務の言葉で返す [REQUIRED]。**

| 返すもの | 書き方 | 書かないこと |
|---|---|---|
| **なぜできないか** | 「この集計に必要な情報が、この組織のRobotERPツバイソには入っていません」 | 項目のAPI名・エラーメッセージの原文 |
| **どうすれば使えるか** | 「新しいバージョンをお使いいただくと利用できます」 | **どの版から使えるかの番号。** 同梱の開始版は組織によって食い違うことがあるため、番号で言うと外れる |
| **いまできること** | 「現在の環境では、〇〇までは集計できます」 | 代わりに何かを勝手に実行すること。提示までにとどめ、実行は依頼を受けてから |

### 「無い」と「対応していない」を書き分ける [REQUIRED]

| 区別 | 意味 | 返し方 |
|---|---|---|
| **この組織には無い** | 製品には存在するが、その組織のバージョンに入っていない | 上の3点。新しいバージョンで使えるようになる |
| **製品として対応していない** | どのバージョンでも存在しない | 「この機能は製品として対応していません」。**新しいバージョンを待てば使えるかのように言わない** |

**この2つを混ぜると、待てば解決すると誤解させるか、逆に諦めなくてよいものを諦めさせる。** 判別がつかないときは、判別がついていないことをそのまま伝える。

### 版で判定しない理由

同梱の開始版は、実装側の記録と案内で食い違うことがある。**利用者に「お使いのバージョンは何番ですか」と尋ねる形にすると、その食い違いがそのまま誤案内になる。** 判定は常に「その組織に現に有るか」で行う（`ti-rollout` のログイン用アプリの判定と同じ考え方）。
