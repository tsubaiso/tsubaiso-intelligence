# 前提の自己診断と提案（capability-preflight）

利用者は「やりたいこと」を言えばよく、**それを実現するための器（接続・権限・設定）が組織に用意されているかを知っている必要はない**。器が足りないとき、利用者に手順を調べさせるのではなく、**AI が不足を検知して埋める提案を出す**。

## いつ読むか

依頼を受けて、**その依頼を実行する経路が使えるかを最初に確かめる瞬間**。とくに次のとき。

- ふだんの会話（標準 MCP）では届かない操作を頼まれたとき
- 実行しようとして「権限がない」「接続できない」で止まったとき
- 組織で初めてその種類の操作を行うとき

## 作法（4段）

1. **確かめる。** 実行の前に、必要な器がそろっているかを確認する。**確かめずに試して失敗させない**（失敗のメッセージは利用者に意味が伝わらないことが多い）。
2. **足りないものを業務の言葉で伝える。** 製品名や設定名だけで言わない。「この操作には〇〇の準備が要ります。いまは無いので、このままでは実行できません」の形にする。
3. **埋め方を提案する。** 誰の許可があれば埋まるか（本人・管理者）、埋めると何ができるようになるか、どれくらいかかるかを添えて、**AI が用意してよいか**を尋ねる。許可を得てから用意する。
4. **自分では埋められないときは頼み先を具体的に示す。** 「管理者に相談してください」で終えない。誰に・何を伝えればよいかを、そのまま渡せる文面で出す。

## 守ること

- **利用者に内部の名前を覚えさせない。** アプリ名・権限セット名・設定画面の名称は、必要な場面（管理者へ渡す文面など）でだけ出す。
- **勝手に用意しない。** 器をつくる操作は組織の設定を変える行為なので、`safety-gate.md` の承認ゲートを通す。
- **できない理由を能力の限界にすり替えない。** 準備すれば実行できることを「できません」と答えない。逆に、実証していないことを「できます」と答えない。
- **同じ不足が繰り返し起きるなら摩擦として起票する**（`feedback.md`）。毎回準備が要る状態は、配布物か手順の設計に穴がある。

## 分担

| 層 | 役割 |
|---|---|
| ti-core（本 reference） | 「足りない → 伝える → 提案する → 許可を得て用意する」の共通の型 |
| ti-rollout（接続・環境セットアップ） | 器そのものの作り方と、そろっているかの確かめ方 |
| 各能力スキル | 自分の実行経路に入る前に本作法を通す |

## 組織の構造が意味定義に追いついていないとき

器（接続・権限）はそろっているのに、**その組織のパッケージが古く、意味定義が前提にしている項目やオブジェクトが存在しない**ことがある。症状は、組み立てたクエリが `INVALID_FIELD` や `INVALID_TYPE` で落ちる形で出る。

### やること

1. **推測でクエリを組み直さない [REQUIRED]。** 似た名前の項目へ差し替える、条件を外して通す、といった回避をしない。**通ってしまうと、利用者は違うものを見ていることに気づけない。**
2. **`atlas_drift_check` を実行する。** 組織の構造と配信中の意味定義の版ズレ・欠落を取る。
3. **次の3点を業務の言葉で返す [REQUIRED]。**

| 返すもの | 書き方 | 書かないこと |
|---|---|---|
| **なぜできないか** | 「この集計に必要な情報が、この組織のRobotERPツバイソには入っていません」 | 項目のAPI名・エラーメッセージの原文 |
| **どうすれば使えるか** | 「新しいバージョンをお使いいただくと利用できます」 | **どの版から使えるかの番号。** 同梱の開始版は組織によって食い違うことがあるため、番号で言うと外れる |
| **いまできること** | 「現在の環境では、〇〇までは集計できます」 | 代わりに何かを勝手に実行すること。提示までにとどめ、実行は依頼を受けてから |

### 「無い」と「対応していない」を書き分ける [REQUIRED]

| 区別 | 意味 | 返し方 |
|---|---|---|
| **この組織には無い** | 製品には存在するが、その組織のバージョンに入っていない | 上の3点。新しいバージョンで使えるようになる |
| **製品として対応していない** | どのバージョンでも存在しない | 「この機能は製品として対応していません」。**新しいバージョンを待てば使えるかのように言わない** |

**この2つを混ぜると、待てば解決すると誤解させるか、逆に諦めなくてよいものを諦めさせる。** 判別がつかないときは、判別がついていないことをそのまま伝える。

### 版で判定しない理由

同梱の開始版は、実装側の記録と案内で食い違うことがある。**利用者に「お使いのバージョンは何番ですか」と尋ねる形にすると、その食い違いがそのまま誤案内になる。** 判定は常に「その組織に現に有るか」で行う（`ti-rollout` のログイン用アプリの判定と同じ考え方）。
