# api スコープ ECA のセットアップ（管理者・組織ごとに1回）

ローカルスクリプト実行（ti-local-automation／ti-data-load）が使う「api スコープの本人接続」の受け皿となる**専用 ECA**を用意する。MCP 用 ECA とは別の ECA を使う（MCP は読み書き両用で 1 つのまま）。**専用 ECA は PSA のパッケージに同梱されている `Tsubaiso_Intelligence` を使い、同梱が無い組織だけ手作りする**（§0）。どちらも**フェイルクローズ**（権限セットを割り当てるまで誰も使えない）で運用する。

**本書の§5以降（設定ファイル・トークンの保管と読み戻し・ループバックの待ち受け）は、AIが実行時に生成するローカルヘルパーの仕様である [REQUIRED]。** ヘルパーは配布物に含まれておらず、別に実装されたものもない。AIが本書を読んでその場で生成・実行する。**したがって本書を直せばヘルパーの挙動もその値で変わり、別途の実装作業（開発への依頼・改修の工程）は要らない。** 細目が多いことを「対応する実装物がどこかにある」手がかりとして読まない。

**標準（ホステッド）MCP へ接続するための ECA は本書ではない。** そちらは `mcp-eca-setup.md`（OAuth 範囲 `mcp_api`・コールバックはクライアント別・命名は `{AIクライアント} MCP {環境}`）。本書の ECA は `api` スコープで、コールバックはローカルのループバックである。**設定値を相互に流用しない。**

## 0. どちらの ECA を使うか（同梱の有無で分岐）[REQUIRED]

設定 → クイック検索「外部クライアント」→「外部クライアントアプリケーションマネージャー」の一覧で、**`Tsubaiso_Intelligence` があるかを名前で判定する**（PSA のバージョン番号では判定しない。6.1 未満で稼働中の組織が実在する）。

| | 同梱あり（既定） | 同梱なし |
|---|---|---|
| 使う ECA | 同梱の `Tsubaiso_Intelligence`（作成しない） | 手作りの `TI Local Automation`（§1） |
| 管理者の作業 | §2 ポリシー → §4 権限セット → §5 値の配布（鍵は §3 の固定値） | §1 作成 → §2 ポリシー → §3 鍵 → §4 権限セット → §5 値の配布 |
| `client_id` | **当社が配る固定値**（§3。全組織で同一） | 組織ごとに設定画面から読む（§3） |
| `redirect_uri` | `http://localhost:8787/callback`（使用中なら `8788`・`8789`） | `http://localhost:1717/OauthRedirect` |
| リフレッシュトークン | 更新のたびに新しい値が返る（ローテーション） | 既定では返らない |

**同梱分の性質（2026-09-16 決定・2026-09-18 発行側確認）**: 用途（データ操作の本人接続）と OAuth 範囲（`api` `refresh_token`）は手作りと同じで、PKCE 必須・シークレットなしのパブリッククライアント。コールバックは `localhost` の `8787`／`8788`／`8789`（いずれも `/callback`）の 3 本で、**購読側では変更できない**。同梱分での認証成立は 2026-07-09 の疎通テスト（ldtest-hapimaru・PSA 6.1 ベータのサンドボックス）で PKCE 認可 → トークン交換 → CRUD → refresh 回転まで実証済み。リリース版のパッケージが入った組織でも、2026-09-28 に PSA 6.3.0.3 の組織で 8787 待ち受け → PKCE 認可 → トークン交換 → REST 呼び出し → refresh 回転まで通った。2026-10-03 には同じ組織で `8788`・`8789` でも PKCE 認可 → トークン交換 → refresh 回転まで通った（登録された 3 本のコールバックを、いずれも当社の本番組織で確認）。ポリシーはパッケージに載らず購読側の管理で、**インストール直後は全員が自己承認できる**（§2 で絞る）。

**既に手作りの `TI Local Automation` で運用している組織は、そのまま使ってよい**（手作りは引き続き動く）。同梱へ移すと `config.json` の `client_id`・`redirect_uri` の差し替えと全利用者の再認証が要るため、移行は求めない。使っていない同梱分の扱いは PSA のパッケージ側が持つ（§2 末尾）。

## 1. 同梱が無い組織：ECA を新規作成

同梱の `Tsubaiso_Intelligence` が一覧に無い組織だけ行う。設定 → クイック検索「外部クライアント」→「外部クライアントアプリケーションマネージャー」→「新規外部クライアントアプリケーション」。

| 項目 | 値 |
|---|---|
| 外部クライアントアプリケーション名 | `TI Local Automation` |
| API 参照名 | `TI_Local_Automation` |
| 取引先責任者 メール | 管理者のメール |
| 配信状態 | ローカル |

- 「API (OAuth 設定の有効化)」を展開 →「OAuth を有効化」にチェック
- コールバック URL: `http://localhost:1717/OauthRedirect`（ローカルヘルパーのループバック）
- OAuth 範囲（2 つ）: 「API を使用してユーザーデータを管理 (api)」＋「いつでも要求を実行 (refresh_token, offline_access)」。**mcp_api は選ばない**（MCP とは別用途）
- セキュリティ（チェックを入れる）: 「Proof Key for Code Exchange (PKCE) 拡張を要求」
- セキュリティ（チェックを外す）: 「Web サーバーフローの秘密が必要」「更新トークンフローの秘密が必要」（残すとループバック方式が失敗する）
- 作成（利用可能まで最大 30 分）

## 2. 対象者ゲート（フェイルクローズ）

対象は、同梱ありの組織は `Tsubaiso_Intelligence`、同梱なしの組織は §1 で作った `TI Local Automation`。アプリの「ポリシー」→「OAuth ポリシー」→「**プラグインポリシー**」→「**許可されているユーザー**」を「**管理者が承認したユーザーは事前承認済み**」に変更する。権限セットを割り当てるまで誰も使えない安全な状態にする（2026-09-16 に本番系組織の設定画面で確認）。

**§4 の紐付け欄は、ここを事前承認へ変えて初めて現れる。**「すべてのユーザーは自己承認可能」のあいだは、プロファイル・権限セットを選ぶ欄そのものが出ない。§2 → §4 の順に進める理由がこれで、順序を入れ替えると §4 で探すものが見つからない。

**同梱の `Tsubaiso_Intelligence` を使う組織では、本節を省かない [REQUIRED]。** インストール直後の「許可されているユーザー」は「**すべてのユーザーは自己承認可能**」で、ポリシーはパッケージに載らず購読側の管理なので、ここで絞らないと api スコープの本人接続が全員へ開いたまま使い始めることになる。既に使われていた組織で絞ったときは、自己承認で発行されたトークンが残っていないかを設定の「接続アプリケーションの OAuth の利用状況」で確認し、残っていれば取り消す（ECA のポリシー変更で既存トークンが失効するかは未実証）。

**§4 を使わない組織の同梱分は、本書と ti-rollout の射程外 [REQUIRED]。** 全員に開いた状態で入るのは PSA のパッケージの性質で、TI のセットアップの完了には関係しない。扱いは PSA のパッケージ側が持つ（2026-09-28 決定）。セットアップの途中で管理者に閉じる操作を求めない。

## 3. コンシューマ鍵

**同梱ありの組織**: `Tsubaiso_Intelligence` のコンシューマ鍵は当社（発行側）が保有する固定値で、**全インストール組織で共通**（2026-09-18 発行側確認。`oauthLink` が 2 組織で一致）。購読側の設定画面から読む必要はない（読み出せない場合もある＝§注意（読み取り側の制約））。値は次のとおり。

```
3MVG9d8..z.hDcPJZz__ZVmR5uWWoETu42QLXzULG9VXkOwmCutNF2_ZV0L.TNa4qXA.g2JUsMO8POZaZH3lJ
```

**同梱なしの組織**: アプリの「設定」→「OAuth 設定」→「コンシューマー鍵と秘密」→ **コンシューマ鍵**をコピー。

どちらも接続元の識別子で秘匿情報ではない（各利用者のヘルパーに配布してよい）。**秘密（Consumer Secret）は使わない**。

## 4. 対象者への展開（使い始めるとき）

**フェイルクローズを保ったまま、対象者を絞って開ける。**

1. **利用ゲート用の権限セットを作る**（例: `TI_Local_Automation_User`）。付与は最小限＝「API の有効化（ApiEnabled）」のみ（実操作は本人権限。オブジェクト権限は付けない）。メタデータでデプロイ可。
2. **ECA にこの権限セットを事前承認として紐付ける**: ECA の「ポリシー」タブ →「アプリケーションポリシー」→「権限セットを選択」で、この権限セットを「選択済みの権限セット」へ移して保存（＝保有者が事前承認される）。**プロファイルは紐付けない**——事前承認はプロファイルと権限セットの OR で効く（2026-09-16 実測）ので、プロファイルを選ぶとそのプロファイルの全員が通り、フェイルクローズが崩れる。
3. **対象者にこの権限セットを割り当てる**（絞った対象者から）。割当された人だけがこの ECA を使える。
4. **各利用者は初回だけブラウザで本人 OAuth**（ヘルパー起動）→ リフレッシュトークンを **OS の資格情報ストア**に保管。以後はブラウザなしで本人権限内の API 操作（ti-local-automation／ti-data-load）を行う。手順は §5。

## 5. 利用者側の初回接続（本人・1 回だけ）

**管理者が渡すのは次の 4 項目だけ。利用者が探して見つけるものではない。** コネクタ（MCP）一覧・接続アプリケーションのメタデータ・Setup 画面のどこにも出てこないので、探させると必ず詰まる（§6）。

| 項目 | 値 |
|---|---|
| instance_url | 対象 org の My Domain（`https://{組織}.my.salesforce.com`） |
| client_id | §3 のコンシューマ鍵（接続元の識別子・非秘匿・配布してよい） |
| redirect_uri | 同梱あり: `http://localhost:8787/callback`／同梱なし: `http://localhost:1717/OauthRedirect`（§0） |
| scope | `api refresh_token` |

**受け渡しの規約**: 組織ごとに異なる値（`instance_url`・同梱なしの `client_id`・`token_account`）は本スキルに書かない（設定値であって手順ではない）。同梱分の `client_id` は全組織で同一なので §3 に置く。**管理者は値を配り、`config.json` は利用者の AI が作る。** 管理者は上の 4 項目と `token_account` を、利用者の AI が読める場所（社内の手順書・社内向けに配るスキルなど）に置く。利用者の AI は、その値から利用者の端末の `~/.config/ti-local-automation/config.json`（Windows は `%APPDATA%\ti-local-automation\config.json`）を作る。既に `config.json` があれば、それを読む。AI がこのファイルを読めば、値を毎回利用者へ尋ねる必要がなくなる。管理者が各端末へファイルを置く作業は要らない。

```json
{
  "instance_url": "https://{組織}.my.salesforce.com",
  "client_id": "{§3 のコンシューマ鍵}",
  "redirect_uri": "http://localhost:8787/callback",
  "scope": "api refresh_token",
  "token_service": "ti-local-automation",
  "token_account": "{org の識別名・組織ごとに一意にする}"
}
```

（同梱ありの例。同梱なしは `redirect_uri` を `http://localhost:1717/OauthRedirect` にする。）

**初回の流れ**（ヘルパーは AI が生成・実行する。利用者は画面操作だけ）:

1. ヘルパーが `redirect_uri` のポート（同梱あり `8787`／同梱なし `1717`）に一時 HTTP サーバーを立て、PKCE（S256）の認可 URL を組み立ててブラウザを開く。**認可 URL は利用者が用意するものではない。** 同梱ありでポートが使用中のとき（Cursor の MCP 認証も `8787` を使う）は、`8788`→`8789` の順に空いているポートで待ち受け、`config.json` の `redirect_uri` を同じポートに書き換える。
2. 利用者は Salesforce のログイン画面で**本人の ID・パスワード（＋MFA）**を入れ「許可」を押す。**client_id を画面に入力する場面はない。**
3. ヘルパーが認可コードを受け取り、**client_secret なし**でトークンへ交換する（同梱分はシークレットを持たないパブリッククライアント、手作りは §1 で「秘密が必要」を外しているため成立する）。
4. リフレッシュトークンを OS の資格情報ストアへ保管する（下表）。
5. 2 回目以降は保管したトークンから `grant_type=refresh_token` でアクセストークンを更新する（**ブラウザは開かない**）。応答に `refresh_token` が含まれていたら保管を更新する（ローテーション追従）。**同梱分はローテーションする設定（`isRefreshTokenRotationEnabled=true`）なので、更新のたびに新しい値が返り、毎回保管を更新する**。古い値が直後に使えなくなるとは限らない（2026-09-28 の通しでは、回転の直後に古い値で更新しても成功した）が、いつまで使えるかは保証されないので、古い値を持ち続けない。手作りは既定ではローテーションしないので、通常は応答に含まれない。どちらも「返ったときだけ更新する」書き方で追従でき、手作りで返らないことを異常として扱わない。

**トークンの保管先（OS 別）**: **原則として平文ファイルには置かない。** 例外は Linux で Secret Service が使えない場合だけで、そのときに限り権限を絞った平文ファイルを使う。

| OS | 保管先と手段 |
|---|---|
| macOS | キーチェーン（`security add-generic-password` / `security find-generic-password`）。**呼び方は下記の「保管と読み戻しの規律」のとおりで、表の行を素で実行しない**（値が空のまま保管される・トークンが標準出力に出る） |
| Windows | `%LOCALAPPDATA%\ti-local-automation\refresh_{token_account}.bin` に DPAPI（利用者アカウント＋端末に紐づく暗号化）で保存。PowerShell 組込みの `ConvertFrom-SecureString` / `ConvertTo-SecureString` を `-Key` なしで使うと DPAPI になる（**未実証**） |
| Linux | libsecret があれば Secret Service（`secret-tool store` / `secret-tool lookup`）。無ければ `~/.config/ti-local-automation/refresh_{token_account}` を `chmod 600`（**未実証**） |

### 保管と読み戻しの規律 [REQUIRED]

**この節の4点は一体で守る。** どれか1つを外すと、トークンが露出するか、空のまま保管されて次の接続で初めて壊れる。

**1. 値をコマンドライン引数に置かない。** `-w` に値を書くとプロセス一覧とシェル履歴へ露出する。`-w` は値なしで呼び、標準入力から渡す。他 OS でも標準入力から渡し、コマンド行に残さない。**`printf` と `[` はシェル組込みを使う**（POSIX シェルでは組込みなので引数は argv に出ないが、`/usr/bin/printf` や `env printf` へ落とすと載る）。

**2. 保管する前に値そのものを検査する。** 空文字や `null`（欠損キーを文字列で返す JSON 抽出の既定値）をそのまま保管すると、**下のコード例の読み戻しの突き合わせが成立してしまい「保管できた」と判定される**。手作りの ECA では §5 の 5 のとおり更新時の応答に通常 `refresh_token` が含まれないので、その値で上書きすると保管済みの正しいトークンが消える。**同梱分は更新のたびに新しい値が返り、古い値がいつまで使えるかは保証されない**ので、保管に失敗すると有効なトークンを失い再認証になりうる。

**3. macOS の `-w`（値なし）へは同じ値を2行送る。** 入力と確認の2回を読むため、1回だけ流すと保管に失敗する。**失敗の出方が分かりにくい**——1回だけ流すと `passwords don't match` が出るが `security` の終了コードは 0 で、**キーチェーンの項目は作られ値だけが空**になり、読み出しも終了コード 0 で空文字を返す。**「保管できた」とみなす材料が終了コードにも項目の有無にも無い。**（2026-08-20・macOS 26.3.1 の1端末で実測。OS が上がったら再確認する。**2行送るのは macOS 固有**で、`secret-tool` は1行しか読まない。）

**4. 読み戻した値を表示しない。** `security find-generic-password -w` は値を標準出力へ出すので、確認のつもりで単体で実行すると**リフレッシュトークンが画面・ログ・会話へ残る**。比較の中で使い、一致したかどうかだけを出す。

```sh
# $TOKEN         = 初回のトークン交換（§5 の 3）で得た refresh_token
#                  更新時（§5 の 5）は応答に含まれたときだけ再保管する
# $TOKEN_SERVICE = config.json の token_service
# $TOKEN_ACCOUNT = config.json の token_account
case "$TOKEN" in "" | null) echo "refresh_token を取得できていません" >&2; return 1 ;; esac
printf '%s\n%s\n' "$TOKEN" "$TOKEN" | security add-generic-password -U -s "$TOKEN_SERVICE" -a "$TOKEN_ACCOUNT" -w
[ "$(security find-generic-password -s "$TOKEN_SERVICE" -a "$TOKEN_ACCOUNT" -w 2>/dev/null)" = "$TOKEN" ] \
  || { echo "キーチェーンへの保管に失敗しました" >&2; return 1; }
```

（スクリプトファイルとして実行するなら `return 1` を `exit 1` に読み替える。対話セッションで `exit` を使うとシェルごと終了する。）

### 保管の識別に組織を分ける値を含める [REQUIRED]

複数の組織を使い分けるため、**経路によらず** `token_account` を保管の識別に含める。

| 経路 | 識別の入れどころ | 備考 |
|---|---|---|
| macOS キーチェーン | `-a` の値 | 上の規律の呼び方で渡す |
| Linux Secret Service | `store` の属性と `lookup` 側の同じ属性 | `secret-tool store --label="TI local automation ($TOKEN_ACCOUNT)" service "$TOKEN_SERVICE" account "$TOKEN_ACCOUNT"` に値を**1行**流す／`secret-tool lookup service "$TOKEN_SERVICE" account "$TOKEN_ACCOUNT"` で取る（**未実証**。`secret-tool` は属性の組で項目を特定するため、`account` を落とすと 2 つ目の組織で衝突しうる） |
| Windows のファイル保管 | ファイル名の `refresh_{token_account}.bin` | DPAPI で暗号化。値は `Read-Host -AsSecureString` 等で受け、コマンド行に置かない |
| Linux のファイル保管（フォールバック） | ファイル名の `refresh_{token_account}` | `chmod 600` の平文 |

**`token_account` は組織ごとに異なる値にする [REQUIRED]。** 規約に従って識別へ含めていても、2 つの組織に同じ識別名を置けば同じことが起きる。管理者が §5 の値を配るときに、組織で一意になる値（組織の識別名・My Domain のホスト名など）を入れる。

**固定名にすると、2 つ目の組織を登録した時点で 1 つ目のトークンが黙って消える**（macOS で実測。`-a` を固定したまま 2 回書くと後の値だけが残る）。**上書きはエラーにならない**ので、気づくのは 1 つ目の組織へ接続しようとしたときになる。

**config とトークンで置き場所を分けているのは意図的。** Windows では config を `%APPDATA%`（ローミングされる）、トークンを `%LOCALAPPDATA%`（端末ローカル）に置く。DPAPI の暗号化が利用者アカウントと端末に紐づくため、トークンを別の端末へ持ち回っても復号できない。

## 6. 詰まりどころ（切り分け）

| 症状 | 原因 | 対処 |
|---|---|---|
| client_id が見つからない | コネクタ（MCP）一覧・接続アプリケーションのメタデータ照会・Setup 画面・メール／チャット検索は**いずれも対象外**。この接続は MCP コネクタとは別系統で、利用者に Setup 権限は要らない | §5 の値を管理者から受け取り、AI が config.json を作る |
| `redirect_uri_mismatch` | ECA のコールバック URL と実行時の値が不一致（ポート・パス・末尾まで完全一致が必要） | 同梱ありは `config.json` を `http://localhost:8787/callback`（または `8788`・`8789`）に揃える（ECA 側は変更できない）。同梱なしは双方を `http://localhost:1717/OauthRedirect` に揃える。同梱ありの組織で手作りの値（`1717`）を使っていないかも確認する |
| 「このアプリケーションを使用する権限がありません」 | §4-2 の ECA 事前承認への権限セット紐付け、または §4-3 の利用者への割当が未了（フェイルクローズの正常な挙動） | §4-2 / §4-3 を確認する |
| トークン交換で秘密を要求される／失敗する | §1 の「Web サーバーフローの秘密が必要」「更新トークンフローの秘密が必要」のチェックが残っている | 両方を外す（ループバック＋PKCE はシークレットを使わない）。同梱ありの組織で出たら購読側では直せないので、ツバイソへ問い合わせる |
| **初回の**トークン交換の応答に `refresh_token` が無い | scope に `refresh_token` が無い、または ECA の OAuth 範囲に「いつでも要求を実行」が無い | scope と §1 の OAuth 範囲を確認する（同梱ありは scope だけ。OAuth 範囲に不足があればツバイソへ）。なお手作りの ECA で**更新時**の応答に含まれないのは正常（既定でローテーションしないため・§5 の 5） |
| 同梱ありの組織で、しばらく使えたあと更新に失敗する | ローテーションで返った新しい `refresh_token` を保管し直さず、古い値で更新している／更新トークンの有効期限（購読側のポリシー）が切れた | §5 の 5 のとおり、返った値で毎回保管を更新する。失敗したら初回接続をやり直す |
| `invalid_client_id` | config.json の client_id が別 org・別 ECA のもの／同梱なしの組織で §3 の固定値を使っている／同梱の ECA を使うのに手作りの鍵を置いている | 使う ECA を §0 で確かめ、それに合う §3 の値か確認する（同梱の ECA は §3 の固定値、手作りの ECA は設定画面から読んだ値） |
| 保管したはずのトークンが空で返る（macOS） | `-w`（値なし）へ標準入力を1回しか流していない。`passwords don't match` が出るが**終了コードは 0・項目も作られる**ので、保管できたように見える | §5 のとおり同じ値を2行送り、直後に読み戻して突き合わせる |
| 2 つ目の組織を足したら 1 つ目が繋がらなくなった | 保管の識別に `token_account` が入っていない、または 2 つの組織に同じ `token_account` を置いたため上書きされた（macOS は `-a`、Secret Service は属性の組、ファイル保管はファイル名で 1 件を特定する） | §5 の識別の表のとおりに含め、値が組織ごとに異なることを確かめたうえで、1 つ目の組織の初回接続をやり直す |
| 作成・ポリシー変更の直後に認証が通らない | ECA の作成・設定変更が反映されるまで最大 30 分かかる | 待って再試行する |
| 待ち受けポート（`8787`／`1717`）が使用中 | 他プロセス（Salesforce CLI の認証中、Cursor の MCP 認証中など）が占有している | 終了を待つ。同梱ありは `8788`→`8789` の順に空いているポートへ変更し、`config.json` の `redirect_uri` も同じ値に書き換えてから待ち受ける（ECA 側に 3 本が登録されており、いずれも §0 のとおり通しを確認している）。同梱なしでポートを変えるなら ECA のコールバック URL も同時に変更する |

## 停止

対象者の権限セット剥奪で能力を停止できる（ライセンス制御と整合）。手作りの ECA は api スコープの除去でも止められる。**同梱の ECA は OAuth 範囲をパッケージが持つため、購読側での範囲の除去は当てにしない**——組織全体で止めるときは、紐付けた権限セットを ECA のポリシーから外す（事前承認のまま紐付けが空なら誰も通らない）。すぐに止めるときは、設定の「接続アプリケーションの OAuth の利用状況」で既存のアクセス権も取り消す。

## 注意（作成方法の制約）

ECA の OAuth（コンシューマ鍵・`oauthLink`）はプラットフォームが採番する。**4 つの構成要素（アプリ本体・OAuth 設定・グローバル OAuth 設定・ポリシー）を 1 回のデプロイにまとめて送れば、メタデータデプロイで新規作成できる**（2026-08-01 実測。実測はトライアル組織で行ったもので、本番系組織での実測は別途）。採番される 2 つの値は雛形から除去して送る。別 org の雛形を使う場合は `orgScopedExternalApp` を対象 org へ書き換える。

**構成要素を分けて送らない。**

| 分けて送った場合 | 起きること |
|---|---|
| OAuth 設定だけを単体で送る | デプロイは通るのにコンシューマ鍵が採番されず、接続に使えない。不足分を後から送れば回復する |
| ポリシーを OAuth 設定より先に送る | 「この外部クライアントアプリケーションの OAuth 設定がありません」で失敗する |

**部分的に失敗したときは、作り直しより先に不足分の追送を試す。** 順は (1) 足りない構成要素を追送して回復させる →(2) それでも揃わなければ本手順の Setup UI で作成する。いきなり削除して作り直すと、採番済みのコンシューマ鍵が変わり配布済みの設定を巻き込む。

## 注意（読み取り側の制約）

**コンシューマ鍵とコールバックURLは、パッケージ同梱でもローカル作成でも読み出せない [REQUIRED]。** 自分の組織で自分が作ったECAでも同じで、`sf project retrieve start --metadata "ExtlClntAppOauthSettings:{名前}"` が返すのは `commaSeparatedOauthScopes` / `externalClientApplication` / `isFirstPartyAppEnabled` / `label` / `oauthLink` の5つ、Tooling RESTの `GET /tooling/sobjects/ExtlClntAppOauthSettings/{id}` は `NOT_FOUND`（2026-09-18・トライアル組織のローカル作成ECAで実測）。**鍵は §3 のとおり設定画面から人が読む。** ローカル作成へ切り替えてもretrieveで取れるようにはならない。**同梱の `Tsubaiso_Intelligence` の鍵は当社が配る固定値（§3）なので、購読側で読み出す必要はない。**

**加えて、パッケージが同梱しているECAは、購読側から全部は読み出せない。** 書き込み側（デプロイ）は上の4構成要素で規定されているが、**読み取り側は4つとも返るわけではない**。同梱のECAと同じものを手で作り直そうとして、必要な値の半分が取れない形で詰まる。

| 構成要素 | 購読側からの見え方 |
|---|---|
| アプリ本体 | 一覧に出る・取得できる（パッケージ由来として返る） |
| OAuth設定 | 同上。**名前がアプリ本体と違う**ことがあるので、本体の名前だけで探して「無い」と判断しない |
| グローバルOAuth設定 | **パッケージ由来のものは一覧に出ない**。返るのは同じ組織で自分が作った分だけ |
| ポリシー | 同上 |

つまり購読側から読めるのは**許可された範囲まで**で、**接続先のURL・本人確認や秘密情報の要否・利用できる相手の方針・更新用の資格情報の有効期間は返らない**。これらは同梱ECAの挙動を決める中心的な設定なので、**「同じものを手で作ってください」という案内は、この4つが取れないことを前提に組む**（取れた範囲だけで案内を書くと、相手の組織で動かない設定ができる）。

**取れないと分かったら、推測で埋めずツバイソへ問い合わせる。** 同じ制約は、顧客組織のカスタマイズを棚卸しする場面（ti-spec-view）でも当たる。
