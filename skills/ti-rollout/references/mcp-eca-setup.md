# ホステッド MCP 接続用 ECA のセットアップ（管理者・組織 × AI クライアントごとに1回）

Salesforce の標準（ホステッド）MCP サーバー（`sobject-reads` / `sobject-mutations`）へ AI クライアントから OAuth 接続するための ECA を作る。**接続キー（コンシューマ鍵）をコネクタに設定するところまでが本手順**で、step 6 の組織コネクタ登録がこれを使う。

**1 つのアプリで参照も更新も受けられる。** あとで更新用（SObject Mutations）を足すときもアプリの作り直しは不要で、コンシューマ鍵もそのまま使える。

## 0. ECA を取り違えない（5 本の全体像）

同じ「外部クライアントアプリケーション」でも用途が違う。**片方の設定値をもう片方へ流用しない。**

| ECA | 出どころ | 用途 | OAuth 範囲 | シークレット | PKCE |
|---|---|---|---|---|---|
| **本手順** `{AIクライアント} MCP {環境}` | 管理者が作る | ホステッド MCP への接続（参照・少量更新） | `mcp_api` `refresh_token, offline_access` | 原則使わない（§4の例外あり） | 要求する |
| `TI Local Automation` | 管理者が作る | ローカルスクリプト実行の本人接続 | `api` `refresh_token` | 使わない | 要求する |
| `Tsubaiso F0 Login` | 管理者が作る（同梱が無い組織のみ） | TI のログイン基盤への Salesforce ログイン | `openid` `api` `refresh_token` | **必要**（当社へ預ける） | **要求しない** |
| `Tsubaiso_F0_Login` | **パッケージ同梱** | 上と同じはたらき（同梱版） | 同上 | — | — |
| `Tsubaiso_Intelligence` | **パッケージ同梱** | PSA/IMA データ操作の本人接続 | `api` `refresh_token` | — | — |

**同梱 ECA は本手順の代わりにならない [REQUIRED]。** どちらも `mcp_api` を持たないため、ホステッド MCP へは接続できない。同梱 ECA が入っている組織でも、本手順の ECA は別に作る。

**同梱 ECA の設定は購読側から全部は読み出せない**（`api-eca-setup.md §注意（読み取り側の制約）`）。画面で見えた範囲だけを根拠に「同じものが既にある」と判断しない。

## 1. 命名（組織 × AI クライアントごとに 1 つ）

**規則: `{AIクライアント} MCP {環境}`**（API 参照名は `{Client}_MCP_{Env}`）。公開ヘルプ記事の命名例と同じ規則で、**記事・本スキル・顧客向け手順書の三者で同じ名前を使う**。

| 外部クライアントアプリケーション名 | API 参照名 | 接続先組織 | AI クライアント |
|---|---|---|---|
| `Claude MCP 本番` | `Claude_MCP_Prod` | 本番組織 | Claude |
| `Claude MCP 検証` | `Claude_MCP_Sandbox` | Sandbox | Claude |
| `Cursor MCP 本番` | `Cursor_MCP_Prod` | 本番組織 | Cursor |
| `Copilot MCP 検証` | `Copilot_MCP_Sandbox` | Sandbox | Copilot Studio |

- **アプリは「組織 × AI クライアント」ごとに 1 つ**（参照用・更新用で分けない）。**コネクタは「組織 × サーバー」ごとに 1 つ**で、名前は `{組織がわかる名前}_{参照 または 更新}`（例 `ツバイソ本番_参照`）。増える単位が違うので、両者を同じ名前にしない。
- **製品名を冠した名前を付けない [REQUIRED]。** `Tsubaiso Intelligence MCP` のような名前は、PSA 6.1 以降の組織で同梱の `Tsubaiso_Intelligence` と一語違いになり、設定画面で並んだときに取り違える。用途が違う ECA どうしが似た名前で並ぶことが事故の原因になる。
- クライアントを足すときは、その組織・そのクライアントで本手順を実施してアプリを 1 つ足す（**コールバック URL がクライアントごとに違う**ため、1 クライアント 1 アプリにすると接続の停止・監査もクライアント単位でできる）。

### 同じサーバーURLのコネクタは1本しか置けない [REQUIRED]

**Claudeはコネクタを、サーバーのURLで区別する。** 同じURLのコネクタを2本目として足そうとすると「このURLのコネクタはすでに組織内に存在します」と出て登録できない（2026-09-21実機・Claudeの組織コネクタ）。**一方、ホステッドMCPのサーバーURLには接続先の組織が入らない。** 接続先の組織はサインインのときに決まる。

| 接続先の組織 | サーバーURLの形 |
|---|---|
| 本番組織 | `https://api.salesforce.com/platform/mcp/v1/platform/{サーバー}` |
| トライアル組織 | **本番組織と同じ**（サンドボックス扱いにならない） |
| サンドボックス | `https://api.salesforce.com/platform/mcp/v1/sandbox/platform/{サーバー}` |

したがって、**本番組織とサンドボックスは並べて登録できるが、本番組織とトライアル組織（または本番組織どうし）は、同じアカウントに並べられない。** §1の「コネクタは組織 × サーバーごとに1つ」は、URLが分かれる組み合わせでしか成り立たない。

複数の組織を同じサーバーで使い分けたいときの選び方は3つある。

| 選び方 | 成り立つか | 代わりに失うもの |
|---|---|---|
| 検証をサンドボックスで行う | URLが分かれるので並べて置ける | トライアル組織でしか確かめられないこと（まっさらな製品の状態など）は確かめられない |
| 使うときだけコネクタの接続先を差し替える | 成り立つ | 差し替えているあいだ、もう一方の組織は使えない |
| AIクライアントのアカウントを分ける | 成り立つ | どのアカウントでどの組織へつないでいるかを取り違えやすい |

**症状はエラーではなく「登録できない」「つながらない」なので、鍵・OAuth範囲・MCPサーバーの有効化など前の工程を疑いやすい [REQUIRED]。** 2本目のコネクタが登録できないときは、前の工程へ戻る前に、同じURLのコネクタが既にあるかを先に見る。Claude以外のクライアントが同じ区別をするかは未確認で、そのクライアントの画面で確かめる。

## 2. ECA を新規作成

設定 → クイック検索「外部クライアント」→「外部クライアントアプリケーションマネージャー」→「新規外部クライアントアプリケーション」。

| 項目 | 値 |
|---|---|
| 外部クライアントアプリケーション名 | §1 の命名規則で決める |
| API 参照名 | 同上（半角英数とアンダースコアのみ） |
| 取引先責任者 メール | 管理者のメール |
| 配信状態 | ローカル |

- 「API (OAuth 設定の有効化)」を展開 →「OAuth を有効化」にチェック
- コールバック URL: **クライアントごとに違う**（下表）
- OAuth 範囲（2 つ）: 「Salesforce でホストされている MCP サーバーにアクセス (mcp\_api)」＋「いつでも要求を実行 (refresh\_token, offline\_access)」
- セキュリティ（チェックを**入れる**）: 「Proof Key for Code Exchange (PKCE) 拡張を要求」「指名ユーザーの JSON Web トークン (JWT) ベースのアクセストークンを発行」
- セキュリティ（チェックを**外す**）: 「Web サーバーフローの秘密が必要」「更新トークンフローの秘密が必要」。**§4 の例外に当たるクライアントだけは逆にする**
- 作成（利用可能まで最大 30 分）

| AI クライアント | コールバック URL |
|---|---|
| Claude | `https://claude.ai/api/mcp/auth_callback` |
| Cursor | `cursor://anysphere.cursor-mcp/oauth/callback`<br>`http://localhost:8787/callback`<br>`https://www.cursor.com/agents/mcp/oauth/callback`（**3 本すべてを改行区切りで登録する**） |
| ChatGPT | クライアント側の設定画面に表示される値を使う（§4） |
| Copilot Studio | コネクタ作成後に発行される**コネクタ固有の URL**（§4） |

**表に無いクライアントの値を推測で埋めない [REQUIRED]。** コールバック URL はクライアントが決めるもので、Salesforce 側からは分からない。そのクライアントの設定画面が示す値を取る（§4 の 2 段構え）。

## 3. コンシューマ鍵

アプリの「設定」→「OAuth 設定」→「コンシューマー鍵と秘密」→ **コンシューマ鍵**をコピー。接続元の識別子で秘匿情報ではない（管理者が控えて step 6 のコネクタ設定に使う・利用者へ配ってもよい）。**コンシューマの秘密は原則使わない**（例外は §4）。

## 4. クライアントごとの差（コールバック URL と秘密の要否）

**この 2 点だけがクライアントで変わる。** 他（OAuth 範囲・PKCE・鍵の扱い）は共通。

**(a) コールバック URL が既知のクライアント**（Claude・Cursor）: §2 の表の値を入れて作成すれば終わり。順序も「Salesforce で作る → クライアントに鍵を入れる」の 1 方向で済む。**既知でも 1 本とは限らない [REQUIRED]**——Cursor は 3 本で、デスクトップの本線は `http://localhost:8787/callback`、`cursor://` は互換用。**1 本でも欠けると認可の途中で止まり、Salesforce へ戻って追記し反映を待つことになる**ので、3 本そろえてからクライアント側へ進む（2026-09-17 地主さん実機確認・Cursor 3.x）。

**ただしクライアント側で鍵を入れる欄は、既定では出ていないことがある [REQUIRED]。** Claude はコネクタの追加で名前とサーバー URL を入れて次へ進み、詳細設定で「独自の OAuth クライアントを使用する」を選ぶと Client ID の欄が現れる（2026-09-18 実機）。ChatGPT も同じ形で、詳細設定の「登録方法」に「ユーザー定義の OAuth クライアント」がある。**症状が「エラー」ではなく「欄が無い」ため、§3 の鍵の取得を疑って前の工程へ戻りやすい。**

**(b) コールバック URL をクライアント側が発行するクライアント**（ChatGPT・Copilot Studio 等）: **クライアント側で先に登録して URL を取り、それを Salesforce へ設定する**。ただしクライアント側の登録画面がクライアント ID（＝コンシューマ鍵）を先に要求するため、**実際には Salesforce → クライアント → Salesforce の 3 往復**になる。

1. Salesforce: §2 でアプリを作る（コールバック URL は仮の値で保存する。Salesforce 側で必須項目のため）
2. クライアント: MCP サーバーを登録し、コンシューマ鍵を入れて作成 → 表示されたコールバック URL を控える
3. Salesforce: 同じアプリのコールバック URL にその値を**そのままの文字列で**追記して保存 → 反映（最大 30 分）を待って接続

**貼るときにデコードしない [REQUIRED]。** クライアントによっては URL の一部を独自にエンコードして表示する。見やすく直すと末尾まで完全一致しなくなり、リダイレクト不一致で必ず失敗する。

**クライアントシークレットを必須入力にするクライアントがある。** その場合は §2 の「秘密が必要」系のチェックを**入れた状態**で作成し、コンシューマの秘密も控えてクライアントへ入力する（`api-eca-setup.md` の「外す」とは逆になる）。**クライアント側の入力欄が必須かどうかで決める**——当社側の既定は「秘密を使わない」だが、これは秘密を使えないという意味ではない。

**動的クライアント登録（DCR）を前提とする接続方式は選べない。** Salesforce は外部クライアントアプリケーションの事前作成が必須のため、クライアント側に「動的検出 / Dynamic」のような選択肢があっても成立しない。**手動（Manual）に相当する方式を選ぶ。**

## 5. 詰まりどころ（切り分け）

| 症状 | 原因 | 対処 |
|---|---|---|
| 接続でリダイレクト不一致になる | コールバック URL が未登録／デコードして貼った／末尾が違う | クライアントが示した文字列をそのまま登録し直す |
| 作成直後に接続できない | ECA が利用可能になるまで最大 30 分 | 待って再試行する |
| 認証画面は出るが許可後に失敗する | 秘密・PKCE の設定がクライアント側と食い違っている | ①秘密の要否を §4 で合わせる →②それでも失敗するなら PKCE 要求のみ外して切り分ける |
| クライアント側に Client ID を入れる欄が見つからない | 条件表示の欄で、既定では出ていない | 詳細設定で「独自の OAuth クライアントを使用する」に相当する選択をしてから入力する |
| 2本目のコネクタが「このURLのコネクタはすでに組織内に存在します」で登録できない | 同じサーバーURLのコネクタが既にある。本番組織とトライアル組織はURLが同じになる | §1「同じサーバーURLのコネクタは1本しか置けない」の3つの選び方から選ぶ |
| ツール一覧が空 | MCP サーバー（`sobject-reads` 等）が未有効、または反映待ち（最大 2 分） | step 3 の有効化を確認する |
| 一般利用者が接続できない | 利用者に「API の有効化」権限が無い／OAuth ポリシーの事前承認が必須になっている | 権限セットとアプリのポリシーを確認する |
| 同梱 ECA があるから不要だと判断してしまった | 同梱 ECA は `mcp_api` を持たない | §0 のとおり本手順の ECA を別に作る |
