# write-index — 書込前構造ゲート（作成・更新前の必須手順の参照エントリ）

書込スキル（ti-update／ti-data-load／ti-metadata）が PSA/IMA を作成・更新する直前に読む、書込前構造ゲートの参照エントリ（TI クライアントスキル体系 §8.2）。ゲートは `function_only` 判定・参照先マスタの有効条件（C5 参照フィルタ）・自動生成（auto_create）シームの両方向検出を担う。

**実体＝Atlas MCP `atlas_write_seam`（v12.1.0〜）**: 本ゲートの実体は Tsubaiso Atlas MCP サーバーの `atlas_write_seam(target=<API名>)` ツール。読み取り系（`atlas_explain`／`atlas_recipe`）と同じ薄いクライアント型で、意味・構造スナップショットを配布物に同梱しない。ローカルに同梱していた意味定義・構造スナップショットは除去済みで、配布物の同梱はゼロ。作れない工程の検出と参照先の有効条件フィルタも本ツールが判定する。

## 引き方

**本ゲートは書込タスクの手順の3番目で、単独では完結しない。** 手前に「書込レシピを引いて経路を確定する」があり、**ゲートだけを引いて作れる・作れないを決めない**（順序と食い違い時の規律は `SKILL.md §書込タスクの手順（作成・更新）` が正本）。

作成・更新する対象オブジェクトの API 名で `atlas_write_seam` を 1 回呼ぶ。

- ツール: `atlas_write_seam(target="<オブジェクトAPI名>")`（名前空間プレフィックス `tb_PSA__`／`tb_IMA__` は省略可・標準オブジェクトは接頭辞なし）
- 1 対象 1 応答。参照先マスタの逆引きはサーバー側で解決するためクライアントは 1 コールで済む。
- 全件一覧（旧 `--list`）は抽出防御方針により提供しない。対象 API 名を指定して都度引く。

## 応答の読み方

`atlas_write_seam` 応答の各フィールドで判定する。

- **`function_only`**（配列・機能経由でのみ作成・更新可）: 各要素の `detail.verdict`（`function_only`）・`detail.operation`（create／import 等）・`detail.function_ref`（正規の生成機能）・`detail.exception`（許容経路）・`detail.recipe`（正しい生成手順）・`detail.control_class`（C1 等）。該当 operation は直接 INSERT／インポートせず、正規機能・転記・自動生成・専用画面で生成する。
- **`auto_create_as_source`**（配列・源として）: 対象を保存すると何が自動生成されるか。`detail.arm`（生成機構）・`trigger`（意図フラグ）・`automation`／`service`・`creates_all`・`diff_update` に従い「フラグ→保存→読み戻し→差分 UPDATE→突合」で書く。
- **`auto_create_as_target`**（配列・作成先として＝二重計上ガード）: 対象が別シームで自動生成されないか。要素があれば手動 INSERT 禁止で、生成元 `source` 側のフラグ経由で生成する。
- **`reference_filters`**（配列・C5）: 参照先マスタの有効条件（`active_condition`）。参照項目を埋めるとき、参照先が有効条件を満たすレコードかを確認する。
- 共通 `semantics_version`／`source_sha`（配信版突合用）。`found:false` は、未収録のほかに渡し先の誤り・接頭辞の省略でも返る。まず索引で名前の種類と完全形を当て（`SKILL.md §Atlas のツールへ渡す名前の使い分け`）、それでも無ければ未収録として当て推量で書かない。

## 判定（総合）

- ❌ **直接 INSERT 禁止**: `auto_create_as_target` に要素がある（別シームの自動生成先＝二重計上リスク）。源オブジェクト側のフラグ経由で生成し手動作成しない。
- ❌ **機能経由のみ**: `function_only` に該当 operation がある。正規機能・転記・自動生成・専用画面で生成する（直 INSERT／インポート不可）。
- ⚠️ **シーム経由で書く**: `auto_create_as_source` に要素がある（フラグで下流を自動生成）。「フラグ→保存→読み戻し→差分 UPDATE→突合」で書く。
- ✅ **通常の作成・更新でよい**: いずれも空、**かつ更新する項目が転記・自動設定・積み上げの先でない**（下記 §更新する項目は、値の出どころを先に確かめる）。レコード自身の入力規則(VR)・必須項目・整合ルールは `atlas_explain` の対象オブジェクト各項目の `rule` を参照する。

上の判定はオブジェクト単位で、**統制が行の範囲を持つときは次節で行ごとに読み替える。**

## 統制が行の範囲を持つときは、行ごとに判定する [REQUIRED]

`function_only` の `detail` が **`scope`（統制を適用する行）と `out_of_scope`（適用しない行）の両方を持つとき、機能経由のみとするのは `scope` の行に限る**。同じオブジェクトに、自動作成の行と人が入力・修正する行が混在する場合に、意味定義はこの形式で記述する。

- **`scope` の行**は、上の ❌ のとおり作成・インポートしない。`detail` に `do_not_touch` があれば、更新・削除も `do_not_touch` に従う。
- **`out_of_scope` の行**は、利用者の作成権限の範囲で作成・更新してよい。`auto_create_as_target` に要素があるときは、各要素の `meaning` で `scope` の行を作成する経路であることを確かめ、そうであれば要素があっても `out_of_scope` の行の作成を中止しない（`meaning` が `out_of_scope` の行も作成すると読めるとき、または確かめられないときは、作成せず人へ確かめる）。`detail` に `manual_rows` があれば、設定方法（空にする項目・true にするフラグ・更新の順序）は `manual_rows` に従う。
- **どちらの行かは、`scope` / `out_of_scope` に書かれた条件で決める。** 条件に書かれた項目の値で判定し、条件に書かれていない項目やレコードの名称から推定しない。既存の行を更新・置き換えるときは、条件に当たるかを読み取りで確認してから書き込む。
- **判定できないときは `scope` の行として扱い、書き込まずに人へ確かめる。** 条件の項目を読み取れない、どちらの条件にも当たらない、両方の条件に当たる、のいずれかのときがこれに当たる。`out_of_scope` として書き込む側に倒さない。
- **新しく作成する行は、登録する内容が機能の作成対象でないことを確かめる。** 条件の項目を空にすれば `out_of_scope` の条件に当たることを、範囲外の根拠にしない。機能が作成する内容を、項目を空にして手で作成すると、機能経由のみの統制を外すことになる。
- **`scope` と `out_of_scope` の両方を持たない統制は、オブジェクト全体に適用する。** 片方だけを持つ統制も同じく全体に適用する。本節を理由に、範囲を書いていない統制を行ごとに区分して解釈しない。

**検知サイン:** `function_only` が返ったことだけを理由に、`out_of_scope` の行の作成も中止した／`out_of_scope` の行を作成するのに `manual_rows` を読まなかった／`scope` / `out_of_scope` の判定を条件に書かれた項目の値でなく、区分やレコードの名称で行った／判定できないまま `out_of_scope` として書き込んだ。

## 更新する項目は、値の出どころを先に確かめる [REQUIRED]

**`function_only` が挙げる operation に update が無いことは、項目を自由に更新してよいことを意味しない。** ゲートの判定はレコード単位で、項目ごとの「人が入力する項目か」は返さない。転記先・自動設定の項目・積み上げの合計も、describe では更新可能として返る。こうした項目へ手で値を入れても保存は通り、下流へ伝播するため、誤りが表に出ない（源の側の値が次に変わったときに上書きされる）。

update では、書く項目ごとに値の出どころ（転記元・計算元）を先に確かめる。

1. **転記元の側の `behavior` を見る。** 転記は、転記先ではなく**転記元のオブジェクト**の `atlas_explain` の `behavior` に書かれていることがある。対象オブジェクトの `relationships` が指す参照先も `atlas_explain` で引き、`behavior` に対象項目への書込（転記・自動設定）が無いかを見る。
2. **項目のヘルプテキストを見る。** describe が返す項目のヘルプテキストに「転記」「自動設定」「自動計算」とあれば、その項目は源の側で決まる。
3. **書けることを根拠にしない。** describe の更新可否や、権限セットでの編集可否は判定の根拠にならない（編集可の権限セットが同梱されていることがある）。

出どころがあれば、その項目を書かず**源の側を動かす**（源の保存・集計の実行など、`behavior` が挙げる契機）。出どころが確かめられないときは、推測で書かず人へ確かめる。

## 経路が複数あるとき、`creates` の一致で選ばない [REQUIRED]

**本ゲートは「どう作るか」に答えるが「作るべきか」には答えない。** `auto_create_as_source` / `auto_create_as_target` が複数返るとき、`creates` が目的のオブジェクトと一致することは、**その経路が目の前の業務に合うことを意味しない**。同じオブジェクトを作る経路が、まったく違う業務のために用意されていることがある。

選ぶ前に各要素の **`meaning` を読み、その経路が想定している業務と、いま作ろうとしている場面が一致するかを確かめる。** 一致しないなら、その経路は使わない（`creates` が合っていても使わない）。

**名称は根拠にならない。** 定義名・トリガ項目のラベルに目的オブジェクトの名前が入っていることは当てはまりの根拠ではない。ラベルは機構が何を作るかを表しており、どの業務のためかは表していない。

**検知サイン:** `creates` または `creates_all` が目的オブジェクトと一致したことだけを理由に経路を選んだ／`meaning` を読まずにトリガ項目を立てた／複数の候補が返っているのに、業務の当てはまりで絞らず最初の1件を採った。

**典型事例:** 案件を作ろうとして `auto_create_as_target` の候補を `creates` の一致だけで採ったところ、それは都度案件を作らずに受注を重ねる業種のための機能で、1商談1案件の場面には合わなかった。`meaning` にその旨が書かれていたが読んでいなかった。

## arm（生成機構）の別

各 auto_create シームに `detail.arm` が付く: `flow`（自動起動フローが下流を生成）／`flow_orchestration`（締め・承認で連鎖フラグを立て下流を起動）／`apex_post`（PSA の Apex が下流を insert）／`apex_inbound_sync`（ERP→PSA を定期 upsert＝手動の二重作成・キー衝突注意）／`external_erp`（PSA→外部 ERP 送信で **SF レコードは作らない**）／`apex_internal`（IMA の Apex が在庫操作の保存時に在庫オブジェクトを内部 materialize）／`apex_crosspkg`（**IMA→PSA 横断**＝在庫起点で PSA 財務記録・役務を自動生成。PSA 側を手動作成しない＝二重計上ガード）。

## 可用性と保留規律 [REQUIRED]

本ゲートはサーバー可用性に依存する（読み取り経路と同一 regime）。`atlas_write_seam` が未接続・403（エンタイトルメント失効）で応答しないときは、**書込を保留し、ゲートを迂回して INSERT／UPDATE しない**。利用者に Atlas MCP の接続状態と PSA 契約の有効性の確認を促す。`found:false` は、索引で名前の種類と完全形を当て直しても返るとき（＝未収録と確かめられたとき）に同様に扱い、機構を捏造せず人へ引き継ぐ。サーバーは常に最新の意味定義版を返すため、クライアント側での再生成・版追従作業は不要。

## 書込スキルからの呼び出し

ti-update／ti-data-load／ti-metadata は書込直前に本ファイルを発火点で読み、`atlas_write_seam` を引いてゲートを通す。書くレコード自身の入力規則（VR）の充足検証は書込スキル側（例 ti-update `references/input-support.md`）の射程で、本ゲート（構造由来の作成可否・参照先の有効条件）とは射程が異なる。

## `function_only` は「作れない」ではない [REQUIRED]

`function_only` が返ったら、**その機能を画面を介さず起こせる経路があるかを確かめるまで、作れないと結論しない。** 確かめずに「経路が無い」と答えると、利用者は画面操作へ戻る。実際には経路が在るのに戻らせた場合、その場で TI を使う意味が失われる。

確かめ方は 2 段。

1. **経路の型を引く。** `atlas_domain_index` の `recipes` から、ヘッドレス実行経路の総覧にあたる定義（`domain` は master・title は「UI専用の機能を画面を介さず正規に実行するための経路の総覧」）を見つけ、その `name` を `atlas_recipe(name=...)` へ渡して引く。総覧は型を 3 つ挙げる（公開アクションを呼ぶ／契機のチェックボックスを偽から真へ変えて保存する／指示レコードを 1 件作る）ので、対象がどれに当たるかを見る。`function_only` 応答の `function_ref`・`recipe` が個別のシーム定義を名指ししていれば、それも `atlas_recipe(name=...)` で引く。**総覧も個別のシーム定義も意味定義側の定義であってオブジェクトではないため、`atlas_explain` に渡すと `found:false` が返る。** 定義名を本 reference に書き写さず、索引と応答から引く（配布物に意味定義を焼き込まないため）。
2. **組織にその経路が在るかを確かめる。** 版番号では判定しない（`ti-core references/capability-preflight.md` §版で判定しない理由）。

| 型 | 実在の確かめ方 |
|---|---|
| 公開アクションを呼ぶ | 組織が公開しているアクションの一覧 2 本に名前が出るか（`GET /services/data/v{n}.0/actions/custom/flow` と `.../actions/custom/apex`）。Apex は global 宣言のものだけが一覧に出るため、ソースに `@InvocableMethod` があることは一覧に出ることを意味しない |
| 契機のチェックボックス | 契機となる項目が対象オブジェクトの describe に在るか |
| 指示レコード | 指示オブジェクトが組織に在るか |

**経路は作成元（上流）のレコードの側から引く [REQUIRED]。** 受注から発注、発注から検収のように、作る対象の上流にあたるレコードが入口を持つ。作る対象そのものの名前で探して当たらなかったことを、経路の不在の根拠にしない。上流でも当たらないときは、さらに一段上のレコードの契機項目と、総覧が挙げる 3 型の両方を当て直してから結論する。

経路が在れば、それは `function_only` の例外ではなく**機能経由そのもの**で、画面から作ったときと同じ整合が保たれる。無いと確かめられたときだけ、その旨を利用者へ返す（「この組織には無い」と「製品として対応していない」の書き分けは `ti-core references/capability-preflight.md`）。
