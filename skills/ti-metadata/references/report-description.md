# レポートの説明文の型

レポートを作る・直すときに、説明文（description）をどう書くか。

## なぜ型が要るか

**レポートの説明文は、AIが「その数字はどのレポートで見られますか」に答えるときの一次情報になる。** 組織が自分で作ったレポートは、AIが同梱の知識で知ることができない。実行時にレポートの一覧と説明文を読んで答えを組み立てる。

したがって説明文の書き方が揃っていないと、AIは次のように振る舞う。

- 説明文が空・用途だけ → 似た名前のレポートのどれを案内すべきか決められない
- **開き方の例外が書かれていない → 間違った経路を自信を持って案内する**

2つめが最も高くつく。利用者は案内された手順を画面でたどり、たどれずに問い合わせを起こす。

## 型（入れる順に優先度）

説明文は**255文字上限**。上限が厳しいので、収まらないときは下の順で落とす。

| 順 | 要素 | 必須 | 書き方 |
|---|---|---|---|
| 1 | 何が分かるレポートか | 必須 | 業務語で1文。**似た名前のレポートと区別できる粒度**にする。「予算と実績の分析用です」のような、複数のレポートに同じことが書ける文にしない |
| 2 | 集計の軸 | 必須 | マトリックス形式・サマリー形式は「行は◯→◯、列は◯→◯」。表形式は「集計せず明細行を出力する」と書き、並ぶ主な列を業務語で挙げる。AIが利用者の問いと突き合わせる主たる手がかり |
| 3 | **開き方** | **必須** | フォルダーから直接開けるなら「レポートのフォルダから直接開ける」。開けないなら「どのレコードのどのタブから開くか」＋「フォルダから直接開くとデータが表示されない」 |
| 4 | 誰のレコードが出るか（表示範囲） | 該当時 | 表示範囲が「私の◯◯」「私のチームの◯◯」のときは必須で、表示名をそのまま書く。「すべての◯◯」なら書かない |
| 5 | 対象の範囲（結合） | 該当時 | 別のオブジェクトを結合していて、相手を持たないレコードが結果から落ちるとき、何が出ないかを1文で書く（例: 「案件に紐づかない配員は出ない」） |
| 6 | 読むときの前提 | 該当時 | 「実行画面で積み上げ集計をオンにすると1画面に収まる（既定はオフ）」等 |
| 7 | 効いている絞り込み | 余れば | 意味のあるものだけ。製品標準の除外条件は書かない |

### 3を必ず書くのが型の要

**開き方は、例外がないときも1文書く。** 無記載を「例外なし」と読めてしまう状態を作らないため。書いていないだけなのか例外がないのかを、AIも人も区別できない。

### 2は形式で書き分ける

**表形式のレポートには集計の軸が無い**（行のグループも列のグループも持たない）。軸を書こうとして、明細の列の1つを「行」と呼ばない。代わりに「集計せず明細行を出力する」と書き、何が並ぶか（主な列）を挙げる。

### 4と5は、出る集合を絞り込みより先に決める

出る行の集合を決めるのは絞り込み（7）だけではない。**表示範囲（4）と結合（5）は絞り込みより手前で効き、落ちる量が絞り込みより大きいことがある。** 説明文が用途を正しく書いているほど、利用者は「出ないのはデータが無いから」と読む。

- **表示範囲は、同じレポートでも開く人ごとに結果が変わる。** 「私の◯◯」は開いた人が所有するレコードだけを出すので、書き手の画面では正しく見えて、別の人の画面では空になる
- **結合は、相手を持たないレコードを落とす。** 名前も行も列も同じ2本のレポートが、結合の違いだけで別の集合を出すことがある

### 6はマトリックス形式だけに書く

積み上げ集計はマトリックス形式の表示設定。**サマリー形式・表形式のレポートには書かない**（意味がないうえ、あると利用者が探して見つからない）。

### 書かないもの

項目のAPI名、問い合わせ文、実装の都合。利用者が読むものなので業務語だけで書く。

## 2・4〜7はレポート定義から機械的に取れる

推測で書かない。次から取る。

```
GET /services/data/v{最新}/analytics/reports/{レポートId}/describe
```

| 要素 | 取る場所 |
|---|---|
| 集計の軸 | `reportMetadata.groupingsDown` / `groupingsAcross`（表示名は `reportExtendedMetadata.groupingColumnInfo` から引く）。**形式が表形式（`TABULAR`）なら両方とも空** |
| 表示範囲 | `reportMetadata.scope`（`user`＝私の／`team`＝私のチームの／`organization`＝すべての）。表示名は `reportTypeMetadata.scopeInfo.values[].label` にそのまま入っている（「私の案件」等）。**`scope` が空なら、複数ブロック形式では `reportMetadata.blocks[].scope` を見る。`scopeInfo` 自体が空なら、そのレポートタイプは表示範囲を選べない＝書かない** |
| 対象の範囲（結合） | `reportTypeMetadata.hasOuterJoin`（偽なら、結合した相手を持たないレコードが落ちる）。どの相手を結合しているかは `reportMetadata.reportType.label`（「◯◯が関連する△△」の形で名前に出る）と `reportTypeMetadata.objects[]`。カスタムレポートタイプなら `objects[].joinType` が相手ごとに `INNER`／`OUTER` を返す。**`objects` が（所有者・ユーザー・ロールを除いて）1つだけ＝結合なしなら `hasOuterJoin` は偽でも落ちるものは無い** |
| 読むときの前提 | `reportMetadata.presentationOptions.hasStackedSummaries`（積み上げ集計）、`showSubtotals`（小計）、`showGrandTotal`（総計）、`hasDetailRows`（詳細行）。**`presentationOptions` の下にあるのは積み上げ集計だけで、残りは `reportMetadata` の直下** |
| 効いている絞り込み | `reportMetadata.reportFilters`（`isRunPageEditable` が実行画面で外せるかを示す） |
| 期間の既定 | `reportMetadata.standardDateFilter` |
| 形式 | `reportMetadata.reportFormat` |

### 開き方の例外の見つけ方

**絞り込みの値が特定のレコードのId・名前で固定されているものが、その類型。** そのレポートはレコード側の画面からIDを渡して開く作りで、フォルダーから開くと結果が出ない。

**複数ブロック形式（MULTI_BLOCK）では、`reportMetadata.blocks[]` の中の絞り込みまで見る [REQUIRED]。** レポート直下の絞り込みだけを見ると、レコード固定を取りこぼす。ブロック側にだけ固定が入っているレポートが実在する。

## 説明文の不備を検知する

**型を渡すだけでは、書く人が思い出さないと使われない。** レポートを扱うときに次を機械的に照合し、当てはまれば直しを提案する。

| 検知 | 条件 | 提案 |
|---|---|---|
| 開き方の記述漏れ | 定義に特定レコード固定の絞り込みがあるのに、説明文に開き方が書かれていない | **最優先**。誤った経路への案内を防ぐ |
| 用途と表示範囲の矛盾 | 表示範囲が「私の◯◯」なのに、説明文が他者のレコードを見る用途（承認する・部下の分を確かめる等）を書いている | **レポート定義の側の誤りである可能性が高い。** 説明文で補う前に、表示範囲の見直しを提案する |
| 表示範囲の記述漏れ | 表示範囲が「私の◯◯」「私のチームの◯◯」なのに、説明文が範囲に触れていない | 開く人によって空になることへの案内漏れを防ぐ |
| 対象の範囲の記述漏れ | 別のオブジェクトを結合していて外部結合を持たない（`hasOuterJoin` が偽）のに、説明文が対象の範囲に触れていない | 利用者が全件の集計と読み違え、落ちているレコードに気づけないのを防ぐ |
| 読むときの前提の記述漏れ | マトリックス形式で積み上げ集計がオフなのに、説明文に前提が書かれていない | 開いても読めない状態への案内を防ぐ |
| 説明文が空 | 説明文が空、または複数のレポートで同一の文 | 似た名前のレポートの取り違えを防ぐ |

検知したら、定義から取れる要素（2・4〜7）で説明文の案を組み立てて提示する。1文目（何が分かるか）は業務判断が要るので、利用者に確認する。

## 例

**良い例** — 1・2・3・7が入っている。

```
管理会計2の実績（区分5）を案件別×勘定科目別に集計。行は案件→勘定科目コード＋名、
列は計上月。勘定科目コードのない社内振替は「9990 勘定科目なし」に集まる。
レポートのフォルダから直接開ける。売上は管理会計種別「売上」を除いて原価だけに
している（実行画面で解除可）。
```

**良い例** — 3（開き方の例外）が入っている。この1文の有無で案内の正しさが決まる。

```
各案件・受注レコードの管理会計タブのリンクからID指定をして表示するレポートのため、
レポートのフォルダから直接表示するとデータが表示されない場合があります。
```

**直す例** — 用途しか書かれておらず、軸も開き方もない。同じ文が複数のレポートに入っていると、どれを案内すべきか決められない。

```
予算と実績の分析用レポートです。
```
