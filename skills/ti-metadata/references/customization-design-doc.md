# カスタマイズ設計書・カスタマイズ仕様書の継続修正サイクル

カスタマイズを「作って終わり」にせず、**何がどこに入っているか**を設計書で可視化し、**どこをどう変えられるか**を仕様書で示し、指示を反映してまた両ドキュメントを出す。この往復を標準で回してカスタマイズのブラックボックス化を解消する（TIの狙い）。出力フォーマットとサイクル手順は標準・中身（顧客固有の対象/指示）は会社固有層。

射程は**メタデータ＝カスタマイズ全般**（カスタム項目・カスタムオブジェクト・画面〔FlexiPage〕・権限セット・入力規則・承認プロセス・レポートタイプ／リストビュー・Apex・Flow オーバーライド・LWC・カスタムメタデータ・共有ルール／OWD）。帳票は差込点と源データという固有の軸を持つため ti-report が別に持つ（§記録との分界）。

## 機能1: カスタマイズ設計書（現状の可視化）

中核ループの retrieve／diff の結果とプリフライトの判定から、**何を・どこに・なぜ加えたか**を機械的に書き出す。**カスタマイズを1件加える／変更するたびに出力**する。

生成元（推測で書かず正本から取る）:

- **対象と種別**: retrieve した実メタデータ（対象 API 名・メタデータ型・所在オブジェクト）。名前空間接頭辞（`tb_PSA__`／`tb_IMA__`／無印）で管理対象への拡張かサブスクライバ追加かを判別する。
- **中身**: オーサリングした定義そのもの。項目なら型・長さ・参照先・数式、入力規則なら条件式とエラーメッセージ、権限セットなら対象と付与した権限、承認プロセスなら承認者と開始条件、Flow オーバーライドなら置換元と差し替えた分岐。
- **なぜ**: 依頼者から受け取った業務要件。**受け取っていないものを推測で埋めない。「未記入」と出す**（あとから人が埋める欄になる）。
- **影響と前提**: プリフライト6軸の判定結果（軸別の所見・リスクレベル）、依存する既存の設定、同一オブジェクトの既存 VR／トリガ／Flow との発火関係。
- **配備の事実**: 検証（checkonly）と本デプロイの結果、承認者。**AI が配備しない種別（共有モデル設定などアドバイザリー専用のもの）では未確定のまま出し、利用者側が適用した時点で埋める**。

出力の形（カスタマイズ1件ごとに、対象 API 名×メタデータ型×所在オブジェクト×業務上の意味×加えた理由×リスクレベル×依存先×配備日）。**配備日は AI が配備しない種別では「未適用」と出す**（欄を落とさない＝適用済みと読ませない）。末尾に次の2つを必ず並べる。

- **理由が未記入のもの** ── ブラックボックス化の入口。人へ聞き取って埋める対象。
- **バージョンアップで再確認が要るもの** ── 置換型オーバーライド・管理項目に依存する拡張・自動処理経路に載る変更（§安全弁7・§疎結合設計原則 P2／P6）。§アップグレード再検証 の対象一覧になる。

**API 名の扱い [REQUIRED]**: 本設計書は対象を「オブジェクト.API 名」で列挙する**技術ドキュメント**で、**管理者・コンサル層向け**（ti-core 群Aのロール出し分け）。エンドユーザー向けの回答出力では業務語へ翻訳する（出力規律）。両者の射程を混同しない。

## 機能2: カスタマイズ仕様書（指示記入式）

変更できる操作を対象ごとに列挙し、指示記入欄を付けて提示する。設計書（現状）に対する「変更の入口」。

変更操作の標準語彙（この語彙で指示する）: 追加／削除／改名（ラベル変更）／条件変更（入力規則の条件式・承認プロセスの開始条件・Flow の分岐）／権限変更（誰に見せる・誰に編集させる）／配置変更（どの画面のどこに出すか）／既定値変更／無効化（削除せず止める）。

出力の形（対象×現状×変更できること×変更指示の記入欄）。冒頭に記入方法（標準語彙）と、**「変更にプリフライトの再判定が要るもの」**を明記する。

- **削除・無効化は必ずプリフライトを通し直す [REQUIRED]** ── 下流依存（軸5）・自動処理経路（軸3）は、着手時から変わっていることがある。
- 管理対象本体の改変にあたる指示は受け付けず、拡張での代替案を示す（§安全弁4・軸1）。

## 継続修正サイクル

```
(1) カスタマイズの配備（中核ループ 1〜6）
    ※ AI が配備しない種別は、加える内容が確定した時点で(2)へ進む
      ↓
(2) 機能1: カスタマイズ設計書を出力（現状の可視化）
      ↓
(3) 機能2: カスタマイズ仕様書を提示（変更の入口・指示欄）
      ↓
(4) 利用者が指示欄に変更を記入
      ↓
(5) プリフライト（6軸）→ 中核ループで反映 → 版上げ
      ↓
   (2)へ戻る → 設計書・仕様書を再出力 → 収束まで反復
```

- この往復は ti-core の仕様往復プロトコル（`spec-roundtrip.md`）の発火点として回す。**行 ID 付き仕様・Excel と YAML の二面・反映状態の管理は同プロトコルが正本**で、本 reference で再実装しない。
- 各反復で設計書・仕様書は**版を上げて差分を追える**ようにする（最新版だけで内容が完結する自己完結版・末尾に簡潔な変更履歴）。
- org 書込を伴う反映は検証先行＋承認ゲート（§安全弁2・§安全弁3、ti-core `safety-gate.md`）。ローカルで詰め、確定版だけを org へ。
- **§アップグレード再検証 を通したら設計書を出し直す。** 依存先の消失・ドリフト・新設 VR の出現は、設計書の「バージョンアップで再確認が要るもの」の欄に効く。

## 記録との分界（二重ホームにしない）

| 何を | どこが持つ |
|---|---|
| **設計書・仕様書という出力物**（人が読む文書・変更の入口） | 本 reference |
| **意味付けの蓄積**（対象 API 名をキーにした意味付け本文・author 帰属・確信度・鮮度） | ti-spec-view の記録プロトコル（`ip-governance.md`）。配備が成功した時点で記録ペイロードを渡す |
| **既にあるカスタマイズの一覧化・標準との差分ハイライト** | ti-spec-view（`visualization-output.md`） |
| **往復の機構**（行 ID・Excel／YAML・反映状態） | ti-core（`spec-roundtrip.md`） |
| **帳票の項目マッピング設計書・帳票のカスタマイズ仕様書** | ti-report（`report-design-cycle.md`） |

**同じ内容を二か所に書かない。** 本 reference が出力する設計書の「業務上の意味」欄は、ti-spec-view に記録があればそれを引き、無ければ設計書側で聞き取って記録へ返す。**既存分（過去に誰かが加えたカスタマイズ）の棚卸しは ti-spec-view が先**で、本 reference はこれから加える／いま加えたものを扱う。

## この reference を読む発火点

| チェックポイント | すること |
|---|---|
| 中核ループの verify（手順6）を終えた直後 | 機能1 の設計書を出す。あわせて記録ペイロード（対象・意図・author・確信度）を ti-spec-view へ渡す |
| 利用者から「いま何が入っているのか」「どこを変えられるのか」を問われた瞬間 | 機能1・機能2 を出す（既存分の棚卸しは ti-spec-view を先に呼ぶ） |
| §アップグレード再検証 を通した直後 | 設計書を出し直し、「バージョンアップで再確認が要るもの」の欄を更新する |
