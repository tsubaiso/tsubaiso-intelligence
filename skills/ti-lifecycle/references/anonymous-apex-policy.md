# Anonymous Apex をフェーズで切り替える判断

Anonymous Apex（org 上でその場で実行する使い捨てのコード）を使ってよいかは、フェーズで切り替える。

## フェーズ別の可否

| フェーズ | Anonymous Apex | 使う理由・使わない理由 |
|---|---|---|
| 設計・開発 | 使ってよい（アジャイル構築の標準手段・sandbox やトライアル環境に限る） | 反復が速く、ルールが固まる前の試行に向く |
| 運用 | 使わない（正式な実装形態へ移してから運用を始める） | 下記の理由による |

## 運用フェーズで使わない理由

- **org の外でバージョン管理できない**（版管理された成果物が残らない）。
- **テストやカバレッジの枠の外**にある（きちんとした単体テストが付かない）。
- **記録が弱い**。実体は、広い権限を持つ管理者や連携用のアカウントがその場で実行し、版管理された成果物が残らず、実行ログしか痕跡が残らないこと。
- **定期実行や画面からの起動ができない**（常時動かす運用に向かない）。
- **職務の分担を保てない**。実体は、実行するのに「Apex を作成する」権限が要り、一般の利用者には渡せない（渡すべきでない）こと。

> 補足: Anonymous Apex は実行する利用者の権限（参照・編集の可否）を尊重して動く。「高い権限で制限を無視して動く」わけではない。運用で使わないのは権限逸脱の懸念ではなく、上記の保守性・記録・職務分担の理由による。

## 運用移行のゲート

要件のルール（どの実装形態にするか）が固まった時点で、Anonymous Apex による暫定の実装を、判断マトリクスで選んだ正式な実装形態へ移す。**この移行が済んでから運用を始める**。移行が済んでいないうちは運用に入らない。

## Apex を書く職務は誰か（ペルソナと権限）

「Apex を作成する」権限は、宣言的カスタマイズとは別の職務で、母集団が狭く高リスク（デプロイ済みの Apex クラス・トリガはシステムモードで動作しうる＝オブジェクト・項目権限〔CRUD/FLS〕をバイパスし、`without sharing`（または未指定）なら共有設定も無視する。`with sharing` なら共有設定は尊重される。加えてパッケージ動作を壊しうる・テストカバレッジやデプロイの要件が別）。誰にでも配る性質ではない。

> 注: ここでの「システムモードで動作しうる」は、org へデプロイされた Apex クラス・トリガの実行文脈の話。使い捨ての Anonymous Apex は上の補足のとおり実行する利用者の権限を尊重して動くので、両者は別物として読む。

- **Apex を書けるペルソナ**: 提供側のコンサル（コードを書く場合のみ）・外部コンサル（改修担当）・当社開発者に限定する。宣言的カスタマイズだけを行う顧客管理者や、一般利用者・承認者・参照者には配らない。顧客が内製・自走でカスタマイズする場合も、宣言的な範囲が基本で、Apex 開発は別職務として扱う。
- **別建てで付与する**: Apex 開発の権限は、宣言的カスタマイズの権限とは分けて、コードを書く役割にだけ付与する（全管理者に常時持たせない）。
- **強制はサーバー側（org 権限）で**: 誰が Apex を書けるかは接続先 org の権限で強制する（クライアント側のスキル配布の取捨は誤操作低減にすぎない）。Apex を書けない役割は、自分で権限を付け替えて昇格できない構成にしておく（自己昇格の遮断）。
  - **自己昇格の遮断が技術的に成立する前提**: この遮断が成り立つのは、その役割が権限管理系（プロファイル・権限セットの編集／割り当て、ユーザー管理）の権限を持たない場合に限る。宣言的カスタマイズを担う顧客管理者にシステム管理者相当の権限まで与える構成では、その管理者が Apex 開発用の権限を自分に割り当てられてしまうため、担保は技術的な遮断ではなく監査（設定変更の履歴）側に移る。org 側の役割設計（権限の強制境界）は、カスタマイズを担う役割に権限管理系を持たせない前提で組む。
- **フェーズと交差する**: 設計・開発フェーズは sandbox／トライアルで書き、運用フェーズは正式な実装形態へ移してから（上のフェーズ別可否）。同じ人物でもフェーズで書込先 org と危険度ゲートが変わる。なお本番 org では Apex クラスの直接編集はできず（デプロイ経由のみ）、本番での Apex 開発の実質は Anonymous 実行と API 経由のデプロイになる。
