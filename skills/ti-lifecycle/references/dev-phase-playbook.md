# アジャイル構築の着手前ゲートと、機構をいつ呼ぶかの判断

アジャイル構築（設計・開発フェーズで反復しながらカスタマイズを作る）に入るときの、着手前の確認と、能力スキルの機構をいつ・なぜ呼ぶかの判断をまとめる。**機構そのものは能力スキルにあり、本書は「いつ・なぜ使うか」の判断に徹する**。

## 着手前の2ゲート

作り始める前に、順に2つのゲートを通す。どちらも「どう作るかの機構」ではなく「何で・いつ作るかの判断」で、判断層である本スキルが持つ。

### ゲート1: いまどのフェーズか（フェーズ判定）

いまが設計・開発フェーズ（sandbox・トライアル）か、運用フェーズ（本番）かを先に判定する。フェーズによって使える手段が変わる（設計・開発は Anonymous Apex を標準手段として使えるが、運用では使わない。詳細は `anonymous-apex-policy.md`）。フェーズを取り違えると、運用に持ち込んではいけない暫定手段のまま運用を始めてしまう。

### ゲート2: どの実装形態で作るか（実装形態の確定）

そのフェーズで、要件をどの実装形態で作るかを確定する（判断は `implementation-form.md`）。要件の業務モデル・性質を踏まえ、宣言的で足りるか、手続き的な自動化で Apexトリガーを既定にするか、バッチか、製品機能化（別アクター）かを決める。フェーズごとに取れる形態が異なる（設計・開発では Anonymous Apex による暫定実装も可、運用開始前には正式な実装形態へ移す）。形態を決めずに作り始めない。

2ゲートはどちらも判断で、通したうえで構築に入る。org へ書き込む構築では、下の「構築中に機構をいつ・なぜ呼ぶか」で、参照先の有効条件チェックや作れない工程の検出といった書込前の構造チェックを能力スキル側の機構として通す。

## 構築中に機構をいつ・なぜ呼ぶか（適用判断）

構築の局面ごとに、どの機構を呼ぶかを判断する。機構の実体と手順は各能力スキルにあるので、そちらを発火点で参照する。

| 局面・課題 | 呼ぶ機構（能力スキル側） | ここで持つ判断 |
|---|---|---|
| 専用画面・システム経由でしか作れない工程を越える | ti-data-load の「作れない工程を越える手立て」 | 直接作成でも定型の連鎖でも作れない起点は、システム経由の複製で越える。これは正式改修が入るまでの暫定である、と明示して進める |
| 画面ボタンでしか動かない集計・転記を代替する | ti-data-load の「同じ値を直接セットして代替」 | 出力先が直接更新できる項目かを確認してから使う。派生値（計算式）は自動で追随する |
| 既存レコードを複製して作る | ti-data-load の「レコード複製（clone）」 | 複製時に、添付のコピーなど危険なフラグを外してから作る（外さないと参照の照会で失敗しうる） |
| 担当者・工数など人に紐づくものを作る | ti-data-load の「社員→ユーザー→権限・共有の連鎖」 | 単価や見え方は正規の経路でしか埋まらない。直接作成では単価0・管理者からしか見えない等の差が出ることを承知して進める |
| 参照項目を埋める | ti-reference の「有効条件チェック」（書込前の構造チェック） | 無効な参照先を選ばないよう有効条件を適用する。当たったら止めて、有効な参照先を用意してから続ける |
| 組織をまたいで関係を保つ・段階的に移す | ti-data-load の「外部IDによる関係保持」 | 内部の自動採番IDに依存せず、外部IDをリンクの鍵にする。元の組織でしか有効でないIDを直接参照しない |

> **検出と手立ては別スキルに分かれる**。「作れない・無効な参照先の見極め」＝**検出**（書込前の構造チェック）は ti-reference が持ち、「システム経由の複製・外部IDによる関係保持などで越える」＝**手立て**は ti-data-load が持つ。上表でこの2つが混在して見えるが、検出（ti-reference）と手立て（ti-data-load）を取り違えない。これらの機構は現時点で未配置のことがあり、未配置なら呼べない（機構を捏造せず人へ引き継ぐ）。

> ここに挙げた課題は「複数の能力を局面に応じて束ねる」ときの判断で発火する。単独の能力で足りる作業（1件の参照・1件の入力・1件の配備）は、能力スキルを直接使う（本スキルを経由しない）。
