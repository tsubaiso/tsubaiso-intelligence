# 要件→実装形態の判断

顧客orgのカスタマイズ要件を、どの実装形態で作るかを判断する。対象は「顧客が自社org内で実装できる手段」。

## 判断マトリクス

| 要件の性質 | 実装形態 | 判断の要点 |
|---|---|---|
| 宣言的で足りる（入力規則・数式・承認プロセス・ロールアップ集計） | 宣言的（第一選択） | コードと競合しない自然な宣言的構造。迷わず第一選択にする |
| レコードトリガの手続き的な自動化ロジック | Apexトリガー（新規に作る場合の既定） | 下記「宣言的とApexの使い分け」で判断が要る唯一の範囲 |
| 定期・大量・集計や按分 | スケジュールFlow または Apexバッチ | 集計・按分は行トリガに埋め込まず、まとめて動くバッチにする |
| 複雑なロジック（配備前提） | 配備済みの Apex | 版管理・テストが前提 |
| org の外との連携・横断処理 | 外部スクリプト＋API | TIの層で担う処理 |
| 標準機能にすべき汎用的な要件 | マトリクスに並べない（下記「製品機能化」） | 顧客が自社orgで選ぶ手段ではない。別の扱いにする |

## 宣言的と Apex の使い分け（手続き的自動化の範囲だけ）

「宣言的＝第一選択」の"宣言的"の大半（入力規則・数式・承認プロセス・ロールアップ集計）は、コードと競合しない自然な宣言的構造で、第一選択のままでよい。**判断が要るのは「レコードトリガの手続き的な自動化ロジック」だけ**。この範囲では次のように分ける。

- **新規に作る場合は Apexトリガーを既定とする**。理由は、AIが保守する前提で、版管理・差分（diff）・コンパイルと型の検証・きちんとした単体テスト・読みやすいレビューがそろうため。Flow は生成はできても、静的な検証や単体テストが弱く、正しさの担保が劣る。
- **Flow は例外**として選ぶ。(i) 人の管理者が画面で継続的に保守する場合、(ii) Flow でしか使えない機能が要る場合、(iii) 既存が Flow で小さな改修にとどまる場合。
- **既存の Flow は原則として書き換えない**。大きな改修が要る、Flow の限界に当たる、画面を介さずに動かせない、といった時にだけ Apex 化を検討する。

> これは「できる・できない」という能力の話ではなく、**保守性を重視したアーキテクチャの判断**である。プラットフォームでできるかどうかは、能力の出典で確認してから断定する。

## 製品機能化（マトリクスに並べない・別アクター）

「標準機能にすべき汎用的な要件」は、エンドユーザーが自社orgで選べる実装手段ではなく、**製品側のバックログ（管理パッケージ）という別の担い手の領分**である。したがって上のマトリクス（自社orgでの実装）には並べず、**改善のフィードバックとして別の流れに回す**。

- TIをツバイソやパートナーが導入代行で使う局面でのみ、製品化の提案が意味を持つ。よって利用者の立場で出し分ける（ti-core 群A の役割出し分け）。
- 配布物の本文に、社内の開発プロセス（開発カードの起票など）は書かない。
