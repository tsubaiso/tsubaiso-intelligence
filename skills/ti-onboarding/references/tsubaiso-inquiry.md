# tsubaiso-inquiry — ツバイソへの照会と、TIとの役割分担

導入プロジェクトの要件定義・設計では、製品の使い方・仕様・設定方法の問いが数多く出る。その多くは、利用者が TI で確かめれば、TI が根拠つきで回答できる。本書は、**TI で確かめられる問いは利用者側で解決し、TI で回答できない問いだけをツバイソへ照会する**ための分担と、照会の形式（ツバイソ照会票）を定める。

ツバイソへ照会する問いが絞られると、利用者はツバイソの回答を待たずに要件を決められる。ツバイソも早く回答できる。

## いつ読むか

- 導入プロジェクトのキックオフ（計画・管理工程）で、要件定義の進め方を決める瞬間
- 要件定義書・Fit&Gap・課題一覧などの資料に、「ツバイソ社確認」「ツバイソに確認」のような、ツバイソへの確認事項を書こうとした瞬間
- 利用者から「これはツバイソに聞いたほうがよいか」と問われた瞬間
- ツバイソの担当者として、利用者の照会票・確認事項の一覧を受け取った瞬間（回答を書き始める前）

## キックオフで合意する分担

キックオフで、利用者とツバイソが次の分担に合意する。下の文面は、そのまま利用者・ツバイソの双方へ示してよい。

> **要件定義の進め方（TIとの分担）**
>
> 製品の使い方・仕様・設定方法と、それにもとづく進め方の推奨は、まず貴社で Tsubaiso Intelligence（TI）を使って確認し、要件を検討します。確認事項は「A. TIで回答できる」「B. TIで根拠を確認できない」「C. TI範囲外の要確認事項」の3つに区分し、ツバイソへ照会するのは B と C の確認事項です。**区分は TI が判定し、回答の末尾に示します。** ツバイソへの照会には、TI が作成する「ツバイソ照会票」を使います。照会票には、TI が判定した区分と、TI での確認結果が記載されます。
>
> この進め方には、貴社にとって次の利点があります。
>
> - 「A. TIで回答できる」確認事項は、ツバイソの回答を待たずに、その場で製品の仕様を確認して要件の検討を進められます
> - TI が回答の末尾に示す区分を目安に、ツバイソへ照会するかを判断できます
> - ツバイソへの照会が絞られ、照会票に TI での確認結果が記載されるため、ツバイソの回答までの時間を短くできます
> - 「B. TIで根拠を確認できない」確認事項へのツバイソの回答のうち、製品の仕様として一般化できる内容は、TI が参照する意味定義・製品ナレッジに追記されます。追記後は、関連する確認事項や、その回答を前提にした次の要件も、TI に確認しながら検討できます

合意した分担を、プロジェクト計画書と議事録に記録する。

## 問いの区分

問いを次の3つに分ける。ツバイソへ照会するのは B と C だけである。

**利用者へ区分を示すときは、記号と名前を併せて書く [REQUIRED]（例：「B. TIで根拠を確認できない」）。** 記号だけでは、見た人に何の区分かが伝わらない。

| 区分（利用者へ示す形） | 内容 | 扱い |
|---|---|---|
| A. TIで回答できる | 製品の使い方・仕様・設定方法と、そこから導かれる設定・運用の推奨のうち、意味定義（Atlas）か製品ナレッジに根拠がある問い | 照会しない。TI の回答を出典つきで資料に書く |
| B. TIで根拠を確認できない | 意味定義・製品ナレッジに無い、一部しか無い、または両者が食い違う仕様・動作。ツバイソが設計書・ソースコードで確かめて回答し、意味定義・製品ナレッジへ追記する | 照会票を作成して照会する |
| C. TI範囲外の要確認事項 | 製品の今後の計画（項目・機能の廃止や開発の予定）、契約・費用・サポートの範囲、ツバイソが過去に示した回答と異なる内容の確認・訂正 | 照会票を作成して照会する |

**製品ではなく、利用者の業務の進め方の判断は、区分を付けず、照会の対象にしない。** TI は判断の材料を示し、資料には「貴社で決めること」として書く。

**A か B かは、引いた結果で決める。** 問いごとに ti-core `references/knowledge-lookup.md` の手順で意味定義と製品ナレッジを引き、同書 §引けなかったときの立て直し の手順まですべて実行する。根拠が見つかれば A、その手順をすべて実行しても見つからなければ B とする。1 回引いて見つからなかったことを B の根拠にしない。

**B と C のどちらか判定できないときは B とする。** 確認の結果を照会票に書けば、ツバイソの側で区分を訂正できる。

**区分は、照会票を作る瞬間だけでなく、製品の問いに回答するたびに示す。** 回答の末尾に区分を 1 行で書く形は ti-core `references/knowledge-lookup.md` §回答に区分を添える が持つ。利用者が「ツバイソに聞くべきか」を自分で判断しなくてよい状態を、照会の手前で作るためである。

## ツバイソ照会票

1 つの問いにつき 1 枚作成する。複数の照会票をまとめて送ってよい。形式は、メッセージ・資料にそのまま貼り付けられるテキストとする。

```
【ツバイソ照会票】
照会番号: {組織の略称}-{YYYYMMDD}-{連番2桁}
要件: {要件の番号と名称}
問い: {ツバイソに回答を求める問いを1文で}
区分: {B. TIで根拠を確認できない または C. TI範囲外の要確認事項}
TIの確認結果:
- 意味定義（Atlas）: {引いた対象・レシピ} → {結果（例: 該当なし／一部あり: …）}
- 製品ナレッジ: {検索した語・記事名} → {結果}
- 意味定義の版: {Atlas が返した版}
TIの暫定回答: {あれば1〜2文。無ければ「なし」}
ツバイソに求めること: {決めてほしいこと、または確かめてほしい事実}
```

記入の規則は次のとおり。

- **「TIの確認結果」には、実際に引いた結果だけを書く。** 引いていない項目を推測で埋めない
- **区分 A の問いと、業務の進め方の判断は照会票にしない。** A は TI の回答を資料に書き、業務の進め方の判断は「貴社で決めること」として資料に書く
- **ツバイソへの確認事項を資料に書くときは、照会票を作成し、照会番号を併記する。** 照会番号の無い「ツバイソ社確認」は資料に書かない

## ツバイソの側での扱い

ツバイソは、照会票を受け取ったら次の順で処理する。照会票の形式になっていない確認事項の一覧を受け取ったときも、問いごとに区分を判定してから同じ順で処理する。

1. 照会票の「TIの確認結果」を、同じ意味定義・製品ナレッジで引き直し、区分を確かめる
2. 区分が A だった場合は、利用者へ、TI で回答を得るための依頼文を返す
3. 区分が A だった問いについて、TI が根拠を見つけられなかった理由（引き方・意味定義の書き方）を調べ、意味定義の改善に使う
4. 区分が B の場合は、回答したうえで、その内容を意味定義・製品ナレッジへ反映する
5. 区分が C の場合は、ツバイソの判断として回答する

## サポートへの起票との違い

本書は、導入プロジェクトの要件定義・設計で生じる問いの照会を扱う。運用中に生じた未解決の問題（操作で解決できない・想定と異なる動作をする）は、ti-core `references/support-escalation.md` に従ってサポートへ起票する。
