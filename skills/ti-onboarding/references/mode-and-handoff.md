# mode-and-handoff — onboarding モード・poc 引き継ぎ・ロール別

本スキル（契約後寄り）と ti-poc（契約前寄り）は同じ層2能力を違う局面モードで束ねる**連続体**である。本 reference はモードの挙動・poc からの引き継ぎ・ロール別出し分けを定める。

## onboarding モードの挙動軸

契約後の局面に合わせて、層2能力を呼ぶ際の挙動を設定する。

| 設定軸 | onboarding モードの値（poc モードとの対比） |
|---|---|
| データ規模 | 全量移行・期中運用（poc＝サンプル／少量） |
| 書込の厳格度 | checkonly 先行・本番反映は承認後・本番デプロイは Apex カバレッジ要件を満たす（poc＝トライアル破棄前提で緩め） |
| 出力の詳しさ | 実務者・管理者向けの手順の詳しさ（poc＝意思決定者向けの要点） |
| 環境前提 | Sandbox → 本番（poc＝トライアル環境・破棄前提） |

モードプロファイルの正式なパラメータ化は横断基盤側の次版で扱う。それまでは各工程の発火点でこの挙動を注記として適用する。

## poc ⇄ onboarding の引き継ぎ（モード遷移）

- PoC で作った業務モデル・マスタ設計の下書き・マッピング定義は、契約後の本工程へそのまま引き継ぐ（能力は同じ層2なので作り直さない）。
- **契約成立が判明した時点で局面モードが poc → onboarding へ遷移**する（相互排他の切替でなく連続体上のモード遷移）。
- **未判定既定**: 契約状態・環境が読めないときは、フェーズを確定せず、参照・可視化のみで応答し、書込・環境前提を要する段に入る前に契約状態と環境を能動的に確認する。onboarding モード（全量・本番前提）を安易に既定にしない（本番 org への誤書込を避ける）。
- トライアル環境であっても「契約後の設計・移行の予行」なら onboarding モードで動く余地を残す（環境だけでモードを断定しない）。

## ロール別の進め方

ロールは工程分類に直交する横断軸で、強制境界は org 権限（横断基盤のロール出し分けがディスパッチ・権限セットが強制）。

| ロール | 進め方（呼ぶ層2・関与工程） |
|---|---|
| 一般ユーザー | 業務操作・運用テストの実施（ti-update 入力支援＋テスト実行）。内部構造・カスタマイズには立ち入らない |
| 管理者・コンサル（社内外） | 設計・カスタマイズ・メタデータ操作・帳票開発まで（ti-metadata・ti-report・ti-lifecycle 参照・ti-spec-view）。全工程に関与 |

ペルソナの細分（プロジェクトメンバー／評価者／導入コンサル／プリセールス等）と権限マッピングは、ロール軸の設計トラックで詰める。オンボーディング環境は立場に応じてスキル・ナレッジを出し分ける。

## 段階導入と二層モデル

- **段階導入**: 第1段＝設計工程の対話ループと工程マップの順序づけ（進行の中核）を、揃った層2能力の範囲で効かせる。第2段＝現状可視化（ti-spec-view）・運用テスト支援（ti-update）を工程へ結線。第3段＝モードプロファイルの正式化で poc⇄onboarding のモード遷移を正式表現・ERP 工程の詳細拡充。層2の実装状況に段階が律速される。
- **二層モデル**: 道具と型（7工程マップ・設計対話ループの6段・onboarding モードの挙動軸・ロール別出し分けの枠組み・大量 I/O のスクリプト経路）は**標準**、あてはめ（顧客の業務プロセスの中身・実帳票・マスタ設計の具体・移行データ・課題表の中身）は**顧客ごとに AI が都度生成**。取り違えない（進行の枠組み＝標準／導入内容＝顧客固有）。
- **評価軸**: 進行の十分性は「工程を正しい順で回せたか」だけでなく「**本稼働へ着地したか（現場ギャップを残さず運用テストを通せたか）**」で測る。
